# カードの生成・点検スキルの詳細設計

- 作成: 2026-09-22
- 状態: 設計案。オーナーが AskUserQuestion で選んだ点（下の「このセッションで決めたこと」）を反映した。
  決定は decisions.md の 2026-09-22 のエントリ（「例文はスキル 3 つ…」から「難易度は TOEIC を目安にした 10 段階…」まで）に、残る論点は open-questions.md に記録した。
- 実装先: `nextjs-app-template` から切り出すプロダクト側リポジトリ。スキルは Claude Code で動かす
- 前提の決定（decisions.md 2026-09-22）: 実行時に LLM を使わない / 例文はすべて LLM で作り LLM で点検、作るスキルと点検するスキルは分ける、スクリプトで済むところはスクリプト / 例文はファイル、SQLite は○×と秒数の記録だけ / 表は日本語、裏は模範解答・別解 2〜3 個・要点 1 行 / タグは大トピック・サブトピックの 2 段と難易度

## このセッションで決めたこと（オーナーの選択、2026-09-22）

| 論点 | 決めたこと | 退けた案 |
| --- | --- | --- |
| カードの置き場 | JSON ファイル + git（既存の決定どおり）。記録は SQLite にカード ID で紐づける | SQLite のテーブル（変更履歴を追いにくい）/ ファイルを正本にして SQLite に写す（同期の処理が増える） |
| 量の考え方 | 目標の枚数は置かない。あればあるほどよく、上限はない（オーナー「10000 種類ある！も売りになる」「学習は終わらなくていい」） | サブトピック × 難易度ごとに目標数を置く表 |
| 「足りない」の決め方 | 既定では SQLite の記録を読み、自分が選んだ範囲・今の難易度の近くで、まだ出ていないカードが少ないマスから埋める。記録がないときや範囲を指定したときは、その範囲で枚数が一番少ないマスから埋める | 枚数の薄いマスだけを見る（自分が今やっている範囲が先に尽きうる） |
| 大きく変わったカード | 元を削除して新しい ID で作り直す。削除したものは墓標に残す | 削除するだけ（似た文がまた作られる）/ 退役フラグ（使わないカードがファイルに溜まる） |
| 点検の反映 | 微修正も削除もすべて自動で反映する。作業用ブランチでバッチごとにコミットし、戻すときは git で戻す | 削除だけ確認する / 報告だけ |
| 点検の範囲 | 未点検のカードと、点検の後に変わったカードだけを見る。引数で範囲を広げられる。lint は毎回全件にかける | 毎回全部（1 万枚では現実的でない）/ 範囲を毎回指定する |
| トピックの一覧 | 固定の一覧を正とする。呼び出し時に指定したときだけ新しいサブトピックを足す | 生成スキルが自分で提案して足す（名前の近いものが増える） |
| 難易度 | TOEIC の点数を目安にした 10 段階。CEFR（B1- のような独自の刻みを含む）・IELTS・TOEFL の目安を添える。あくまでアプリ内の共通の目安 | 5 段階（オーナー「足りん」）/ 3 段階 / CEFR だけ |
| 文法項目のタグ | 固定の一覧から 1〜2 個をカードに付ける。ユーザーには見せない（文法を意識させない決定はそのまま） | 付けない（偏りを数えられない）/ 自由記述（表記が揺れる） |
| 未点検のカード | アプリで出さない。生成スキルは最後に点検スキルへ続ける | 生成直後から出す |
| 項目の後付け | 既存カードに新しい項目を埋める 3 つ目のスキルも設計に入れる | 生成と点検の 2 つだけにする |

## 全体像

```
                   ┌─ content/taxonomy.json   大トピック・サブトピック
  固定の物差し ────┼─ content/levels.json     難易度 10 段階
                   ├─ content/grammar.json    文法項目
                   └─ content/guides/*.md     書き方・同一性の規則・点検の観点

  /generating-cards 20 [範囲]
     │  pnpm cards:gaps（カード + SQLite の記録 → どのマスに何枚）
     │  書き手のサブエージェント（マスごと、並列）
     │  pnpm cards:lint / cards:dupes（機械で落とす）
     ▼
  content/cards/<topic>/<subtopic>.json  ← 未点検（アプリには出ない）
     │
  /reviewing-cards [範囲]   ← 生成の最後にも自動で呼ばれる
     │  pnpm cards:queue（未点検・変更・観点の版が古いもの）
     │  独立した審査 3 本（ブラインド作文 / 自然さと正しさ / タグと要点）
     │  裁定: そのまま / 微修正（同じ ID） / 作り直し（削除 + 新 ID） / 削除
     │  pnpm cards:stamp（点検済みの印）
     ▼
  点検済み → アプリが出題する        削除 → content/tombstones.jsonl

  /backfilling-card-fields <項目>   項目を足したときに既存カードを埋める → 点検へ
```

## データの形（プロダクト側リポジトリ）

### 置き場

```
content/
  taxonomy.json            大トピック → サブトピック（id・日本語名・場面の説明）
  levels.json              難易度 10 段階（下の表）
  grammar.json             文法項目（id・日本語名・使える難易度の範囲・例）
  cards/<topic>/<subtopic>.json   カードの配列（id 順に並べる）
  tombstones.jsonl         削除したカードの墓標（1 行 1 件、追記のみ）
  guides/
    writing.md             例文の書き方（生成と点検の共通の物差し）
    identity.md            同一性の規則（微修正か作り直しか）
    review-perspectives.md 点検の観点と、その版番号
scripts/cards/             lint・gaps・dupes・new-id・queue・stamp・stats
.agents/skills/            generating-cards / reviewing-cards / backfilling-card-fields
```

- ファイルはサブトピックごとに分ける。1 万枚になっても 1 ファイル数百枚に収まり、git diff が読める。1 枚 1 ファイルにすると数千ファイルになり、差分が追いにくい。
- `taxonomy.json` と `levels.json` はアプリの設定画面や表示でも使う。スキルのためだけの資料にしない。
- テンプレートの規約: スキルは `.agents/skills/<name>/` に書き、`pnpm agents:sync` で `.claude/skills/` に写す。frontmatter は `name` と `description` の 2 キーだけで、英語で書く。スクリプトはテンプレートの `writing-repo-scripts` に従って `scripts/` に置き、`pnpm cards:*` で呼ぶ。

### カード 1 枚

```json
{
  "id": "c_7k2m9x4q",
  "ja": "明日の会議、10 分遅れて始めてもいいですか？",
  "en": "Is it okay if we start tomorrow's meeting ten minutes late?",
  "alternatives": [
    "Can we start tomorrow's meeting ten minutes late?",
    "Would it be okay to start tomorrow's meeting ten minutes late?"
  ],
  "point": "Is it okay if ～ で許可を求める。未来のことでも if 節は現在形",
  "topic": "work",
  "subtopic": "meetings",
  "level": 4,
  "grammar": ["if-clause-present-for-future", "asking-permission"],
  "createdAt": "2026-09-22",
  "stamps": {
    "core": { "hash": "sha256:…", "perspectivesVersion": 1, "at": "2026-09-22" }
  }
}
```

- `id`: 中身から導かない、ランダムな短い ID（`c_` + base32 の 8 文字）。微修正で中身が変わっても ID は変わらない。墓標にある ID は二度と使わない（`cards:new-id` が確かめる）。
- `stamps`: 点検済みの印。部分ごとに持つ。`core` は ja・en・alternatives・point・topic・subtopic・level・grammar のハッシュ。後から足した項目（例: `sceneNote`）は `stamps.sceneNote` を別に持つ（backfilling の節）。
  - アプリは `stamps.core.hash` が今の中身のハッシュと一致するカードだけを出す。後付けの項目は、その項目の印が一致するときだけ表示する。
  - これで「未点検のカードを出さない」が仕組みで守られ、手で JSON を直したカードも自動で未点検に戻る。
- 秒数は英文の長さから決まるので、カードに持たせない（式はアプリ側、open-questions.md「カウントダウンの秒数の式」）。

### 墓標（tombstones.jsonl）

```json
{"id":"c_7k2m9x4q","ja":"…","en":"…","topic":"work","subtopic":"meetings","level":4,"reason":"表の日本語から時制が決まらず、直すと問いが変わる","deletedAt":"2026-09-30","replacedBy":"c_p3h8w2zn"}
```

- 役割は 3 つ。ID を再利用させない。生成の書き手に「このマスで削除した文」として渡し、同じ文を作り直させない（english-vocab-app で「落とした語の台帳」が要った理由と同じ）。削除の経緯を後から読めるようにする。
- SQLite に残った古い ID の記録は消さない。アプリでの扱いは下の「アプリ側に求めること」（decisions.md 2026-09-22「削除・作り直しになったカードの『できた』は数え続け…」）。墓標の `topic`・`subtopic` は、削除したカードの「できた」を到達度に数えるときにも使う。

### 難易度 10 段階（levels.json の中身の案）

根拠は `research/level-scale-benchmarks.md`。どれも目安で、TOEIC は聞く・読むの試験なので、話す難しさとの対応は自称である。

| Lv | TOEIC | CEFR | IELTS | TOEFL iBT (1–6) | 文の目安（案） |
| --- | --- | --- | --- | --- | --- |
| 1 | 300 | A1+ | – | 1.5–2 | 中 1 相当。現在形・be 動詞・命令文の短い単文 |
| 2 | 400 | A2 | – | 2 | 中 2 相当。過去・未来・助動詞・比較 |
| 3 | 500 | A2+ | 3.5 | 2.5 | 中 3 相当。現在完了・受動態・不定詞と動名詞の基本 |
| 4 | 600 | B1- | 4.0 | 3 | 関係詞・間接疑問・後置修飾 |
| 5 | 730 | B1+ | 5.0 | 3.5 | 仮定法過去・使役・基本の句動詞 |
| 6 | 800 | B2- | 5.5 | 4 | 仮定法過去完了・分詞構文 |
| 7 | 860 | B2 | 6.0 | 4–4.5 | 婉曲・譲歩・複文の組み合わせ |
| 8 | 900 | B2+ | 6.5 | 4.5 | 節の入れ子・句動詞の選び分け |
| 9 | 950 | C1- | 7.0 | 5 | 倒置・強調・細かなニュアンス |
| 10 | 990+ | C1 | 7.5+ | 5.5 | 入り組んだ文（TOEIC の上限の先） |

- `levels.json` には段階ごとに、上の目安スコア、英文の語数の目安（lint の上限・下限）、代表的な文法項目を持たせる。文法の割り当ては日本の学校文法の順序にもとづく当方の案で、出典はない。
- 文法項目（`grammar.json`）は 30〜40 個の固定一覧にし、項目ごとに「使える難易度の範囲」を持たせる（例: 現在完了は Lv3〜）。一覧の初版は実装の最初に LLM で下書きを作り、オーナーが目を通す。

## 同一性の規則（微修正か、作り直しか）

判断の軸は 1 つ。**直す前の○×と秒数を、直した後と同じ問いへの記録として比べられるか。** 比べられるなら同じ ID で微修正、比べられないなら作り直し（元を墓標にして新しい ID）。

| 微修正（同じ ID） | 作り直し（削除 + 新 ID） |
| --- | --- |
| 誤字、句読点、冠詞などの誤りの訂正 | 表の日本語の意味が変わる（誰が・何を・いつ・肯定か否定か・依頼か提案か） |
| 表の日本語を、意味を変えずに自然にする | 模範解答の骨格が変わる（時制、文型、主節の構造） |
| 表の日本語に、骨格を決める手がかりを足す（「もう」を足して完了形に絞るなど）。ただし、元の模範解答がすでにその骨格だった場合に限る | 狙う文法項目の主なものが変わる |
| 模範解答の語の入れ替え（start → begin）、より自然な言い回しへの置き換えで骨格が同じもの | 英文の長さが大きく変わり、秒数がおおむね 1.5 倍以上・3 分の 2 以下になる |
| 別解の追加・削除・差し替え | |
| 要点の書き直し | |
| タグの付け替え（トピック、サブトピック、難易度、文法項目） | |

- 難易度のタグを直しても ID は変えない。問いは同じだからである。アプリの難易度の自動調整は、その時点のタグで動く。
- 直しても通らないカード（下の点検の 2 周目で再び指摘されたもの）は、作り直さずに削除する。

## スクリプト（機械で決められることはすべてここ）

| コマンド | 役割 |
| --- | --- |
| `cards:lint` | 形の検査。全件に毎回かける。ERROR はブロック、WARN は報告だけ |
| `cards:gaps` | 生成の計画を作る。どのマスに何枚、どの文法項目を狙うか |
| `cards:dupes` | 重複・近い文の候補を出す（全カード + 墓標が相手） |
| `cards:new-id` | ID を払い出す。既存・墓標と重ならないことを確かめる |
| `cards:queue` | 点検の対象を並べる |
| `cards:stamp` | 点検を通したカードに印を付ける |
| `cards:stats` | 枚数の集計（トピック × 難易度 × 文法項目、点検済みの割合、墓標の数と理由） |

`cards:lint` の ERROR（初期値。閾値は 1 か所に置き、運用しながら変える）:
- 必須の項目が揃っている。別解は 2〜3 個
- id が一意で、墓標にない
- topic・subtopic・grammar が一覧にあり、grammar の項目が、そのカードの難易度で使える範囲に入っている
- 英文の語数が、その難易度の範囲に収まる
- `en` と `alternatives` に日本語の文字がない。`ja` に英字の単語がない（固有名詞の許可リストを除く）
- `...` と `…` を使っていない。英文は終止符・疑問符・感嘆符で終わる
- 別解が、模範解答や他の別解と、正規化（大文字小文字・句読点・縮約形の展開）した後で同じでない
- 要点が 1 行で、長さの上限内に収まる

`cards:dupes`: 英文と日本語をそれぞれ正規化し、語の n-gram の近さで、近い組を候補として出す。1 万枚でも総当たりにせず、同じサブトピックと、隣り合う難易度の中だけを比べる。墓標とは全件と比べる。出力は候補の一覧で、生成時は新しい側を落とし、点検時は審査の材料にする。

`cards:gaps` の手順:
1. 範囲の指定（大トピック・サブトピック・難易度）があれば、その範囲の中で「サブトピック × 難易度」のマスを作る。なければ SQLite から今の設定（選んだ大トピック、重点、推定難易度）と、出題済みのカード ID を読み、選んだ大トピックのサブトピック × 推定難易度 ±1 のマスを作る。記録がなければ全マスを対象にする。
2. マスごとに「まだ出ていない点検済みのカード + 未点検のカード」の枚数を数える。記録がない、または範囲の指定があるときは、単にカードの枚数を数える。重点のサブトピックは、重点が新規の半分までを占める決定に合わせ、不足の重みを 2 倍にする。
3. 枚数が少ないマスから順に、依頼の枚数を割り振る。1 回で 1 マスに割り振るのは 5 枚までにし、同じ場面の文が固まらないようにする。
4. マスごとに、その難易度で使える文法項目のうち、そのサブトピックで数が少ないものを 2〜3 個「狙う文法」として添える。

SQLite の読み方はアプリの実装に合わせる。スクリプトはアプリのデータアクセスの関数を読み取り専用で呼ぶ形にし、テーブルを直接叩かない。スキーマを頻繁に変える前提なので、そのほうが壊れにくい。

## スキル 1: generating-cards（生成）

- 呼び出し: `/generating-cards 20`、`/generating-cards 30 topic=work level=5-6`、`/generating-cards 10 subtopic=work/job-interview new`（`new` を付けたときだけサブトピックを taxonomy.json に足す）、`--no-review`（点検へ続けない）
- 成果: カードファイルへの追記、コミット 1 つ、報告

手順:
1. 作業用ブランチ（`cards/<日付>`）にいることを確かめる。main にいれば作る。作業ツリーに関係ない変更があれば止まる。
2. `new` の指定があれば、taxonomy.json にサブトピック（id・日本語名・場面の説明 1〜2 文）を足す。
3. `pnpm cards:gaps <枚数> [範囲]` で計画を得る。
4. マスごとに書き手のサブエージェントを並列で立てる。渡すもの:
   - `guides/writing.md`、そのマスの難易度の定義（levels.json）、狙う文法項目（grammar.json）、サブトピックの場面の説明
   - そのマスの既存カードの ja と en の一覧（重複を避けるため）と、そのマスの墓標
   - 出力はスキーマどおりの JSON（id と stamps は付けない）
5. メインが ID を払い出して書き込む。`cards:lint` で ERROR になったものは、機械的に直せるもの（句読点など）だけ直し、残りは落とす。`cards:dupes` で既存・墓標に近いと出たものは落とす。
6. 落として依頼の枚数に届かなければ、足りない分だけ 1 回だけ作り直す。それでも足りなければ、足りないまま報告する。
7. `--no-review` でなければ、今回作った ID を渡して reviewing-cards を続けて回す。
8. コミットし、報告する（作った枚数、マスごとの内訳、落とした枚数と理由、点検の結果）。

`guides/writing.md` に書くこと（生成と点検の共通の物差し）:
- 状況のある、実際に言いそうな文にする（公開の声で最も強かった不満は「不自然な例文・状況のない教科書的な文」、`research/user-needs/instant-composition-pains.md`）
- 表の日本語は自然な日本語にし、英語の直訳調にしない。そのうえで、英文の骨格（主語・時制・肯否・丁寧さ）が一つに決まる手がかりを日本語の中に入れる。決まらない文は、自己採点の「合っているか分からない」を再発させる
- 別解は、同じ場面でそのまま通る言い方だけにする。意味や丁寧さがずれるものは入れない
- 要点は、この文で間違えやすい 1 点だけ。文法用語は最小限にする
- 同じマスの中で、主語・場面・文型が偏らないようにする

## スキル 2: reviewing-cards（点検と修正）

- 呼び出し: `/reviewing-cards`（既定の対象）、`/reviewing-cards topic=travel`、`/reviewing-cards --ids c_xxx,c_yyy`、`/reviewing-cards --ids c_xxx --note "この別解は不自然では"`（使いながら気づいた 1 枚を直す入口）、`--limit 100`
- 既定の対象（`cards:queue`）: 優先順に、lint の ERROR があるカード → 未点検（印がない）→ 点検の後に中身が変わったカード → 点検の観点の版が古いカード。1 回の上限は既定で 50 枚。
- 成果: カードファイルの修正、墓標の追記、印の更新、コミット 1 つ、報告

手順:
1. `cards:lint` を全件にかける（毎回）。`cards:queue` で対象を決める。
2. 対象を 10〜20 枚ずつのバッチに分け、独立した審査を 3 本立てる。どの審査も、カードを書いたのとは別のサブエージェントで行い、互いの結果は見せない。
   - **R1 ブラインド作文**: `ja` と難易度だけを見せ、英文を 1〜3 通り書かせる。メインが模範解答・別解と突き合わせる。骨格が違う英文が出たら、表の日本語が一つに決まっていない（`ja` に手がかりを足す）か、別解が漏れている（別解に足す）。判断ではなく観察に変えることで、審査がゴム印になるのを防ぐ（english-vocab-app 2026-09-11 の「ブラインド解答」と同じ考え方）
   - **R2 自然さと正しさ**: `ja`・`en`・`alternatives` を見せる。模範解答と各別解が文法的に正しいか、その場面で実際に言うか、日本語と意味・丁寧さが合っているか、日本語が直訳調でないか
   - **R3 タグと要点**: カード全体と levels.json・grammar.json・taxonomy.json を見せる。難易度・文法項目・サブトピックが合っているか、要点が正しく役に立つか。`cards:dupes` の候補も渡し、実質同じ問いのカードがないかを見させる
   - どの審査も、違反のあったカードだけを `{id, 観点, 判定: FIX | REBUILD | DROP, 確信度, 直し方の案}` で返す。
3. 裁定（メイン）: カードごとに、そのまま・微修正・作り直し・削除のどれかに決める。`guides/identity.md` の規則で、微修正か作り直しかを決める。審査の判定を覆したときは、理由を報告に書く。
4. 反映:
   - 微修正: 同じ ID のまま書き換える
   - 作り直し: 元を墓標に移し（`replacedBy` 付き）、同じマスで書き手のサブエージェントに新しい 1 枚を作らせる。直し方の案と墓標を渡す。新しいカードはこの回の対象に加える
   - 削除: 墓標に移す
5. 2 周目: 中身が変わったカードと新しく作ったカードに、R1 と R2 をもう一度かける。再び指摘されたら削除する（直しても通らないものは残さない）。3 周目はしない。
6. `cards:lint` を通し、通ったカードに `cards:stamp` で印を付ける。
7. コミットし、報告する（見た枚数、そのまま / 微修正 / 作り直し / 削除の件数、削除と作り直しの一覧と理由、覆した判定、まだ残っている対象の数）。

観点の版: `guides/review-perspectives.md` に点検の観点と版番号を書く。観点を足したら版を上げる。既存のカードは「観点の版が古い」として少しずつ `cards:queue` に並ぶ。上限の 50 枚ずつ、好きなときに回して追いつかせる。

## スキル 3: backfilling-card-fields（項目の後付け）

- 呼び出し: `/backfilling-card-fields sceneNote`、`--limit 200`、`topic=work`
- 前提: 項目のスキーマ（zod）を先に足してあること。項目の仕様を `.agents/skills/backfilling-card-fields/references/fields/<項目>.md` に書いてあること（何を書くか、長さ、例、点検の観点）

手順:
1. その項目が空のカードを並べる（点検済みのカードを優先）。
2. 書き手のサブエージェントに、バッチごとにカードと項目の仕様を渡して埋めさせる。
3. lint を通して書き込む。印は `stamps.<項目>` が空のままになる（`core` の印は変わらないので、カードはアプリから消えない。後付けの項目だけが未点検として表示されない）。
4. reviewing-cards に、その項目の観点だけの審査を回させる（`cards:queue` は「項目の印がない」も対象に並べる）。
5. コミットし、報告する。

この形にすると、1 万枚に項目を足しても、アプリの出題は止まらない。点検が追いついた項目から表示されていく。

## 役割の分け方と実行の形

- 書き手と審査役は、必ず別のサブエージェントにする。書いた本人の点検が効かないことは、english-vocab-app の参照実装で実測されている（196 枚中 25 枚が違反したまま通過、decisions.md 2026-09-11 の出典）。
- モデルの割り当て（案）: 書き手と R1 は `executor`（Opus 5.5 low）。型が決まっていて、量が多い。R2・R3 と裁定は `architect`（Opus 5.5 high）。判断が要る。プロダクト側リポジトリにこの 2 つのエージェント定義があることを前提にする。
- git: 作業用ブランチの上でバッチごとにコミットする。push・プルリクエスト・マージはしない。取り込むかはオーナーが決める。1 回ごとの差分は `git diff` で読める。
- 無人で回す（`/goal` やルーティン）のは、同じ条件なら可能な作りにしておく。最初の 300 枚前後は対話で回し、報告の中身を見てから決める。

## アプリ側に求めること（スキルの設計から出てくる要件）

- 出題するのは `stamps.core` が一致するカードだけにする。後付けの項目は、その項目の印が一致するときだけ表示する。
- カードファイルにない ID の記録（削除されたカード）は消さない。使い分けは次のとおり（decisions.md 2026-09-22「削除・作り直しになったカードの『できた』は数え続け、記録は出題・復習・成長の比較からだけ外す」）。
  - 使わない: 出題、復習の候補、今日の成長の比較
  - 数え続ける: 到達度（「できた」になっていた分。大トピック・サブトピックは墓標の値で数える）。作り直した新しいカードには引き継がない
  - カードの有無に左右されない: ストリーク・ポイント・累計。その日に終えた回の記録で決まる
  - 同じ日の再開で、残りのカードが削除・未点検になっていたら外し、同じ配合の規則で同じ枚数だけ補う（decisions.md 2026-09-22「枚数 5〜30 に合わせた画面の細部…」）
- `cards:gaps` から読めるように、今の設定（選んだ大トピック、重点、推定難易度）と、出題済みのカード ID を返す読み取り専用の関数を用意する。

## 残る論点・リスク（オーナーの確認が要るもの）

- **同じモデルの見落とし**: 書き手も審査役も Claude なので、同じ不自然さを見逃す危険は残る（open-questions.md「LLM 同士のチェックで例文の不自然さを取り切れるか」は、この設計でも解決しない）。R1 のブラインド作文は「一つに決まらない表」を観察で拾えるが、「文法的には正しいがネイティブは言わない」の見落としには弱い。
- **到達度の見せ方と、上限のない量**: 解決。到達度は「できた文の数」と次の節目までのリングで見せる（decisions.md 2026-09-22「到達度は『できた文の数』と次の節目までのリングで見せる」）。点検で削除したカードの分も数え続ける（同日「削除・作り直しになったカードの『できた』は数え続け…」）。称号は取り消さない（同日「称号は取り消さず、同じ称号は二度出さない」）。
- **1 日の目標カード数を個人で設定する**: 解決。今日の分は 5 / 10 / 15 / 20 / 30 枚から選び、既定は 10 枚（decisions.md 2026-09-22「今日の分の枚数を自分で決められるようにする」）。
- **難易度のタグの揺れ**: LLM が付ける難易度は揺れる。記録がたまったら、「Lv5 の○の率が Lv6 より低い」のような逆転を `cards:stats` で見つけ、タグを付け直す仕組み（4 つ目のスキルか、点検の観点の 1 つ）が要るかもしれない。最初の版には入れない。
- **費用**: 1 枚あたり、書き手 1 回と審査 3 本、直したカードはさらに 2 本かかる。1 万枚まで作ると呼び出しの回数は大きいが、見積もりはまだしていない。
- **文法項目の一覧と、段階ごとの文法の割り当て**は出典のない案である。初版を作ったら、オーナーが一度目を通す前提にしている。
