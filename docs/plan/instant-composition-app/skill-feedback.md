# skill 改善メモ（instant-composition-app の検討で拾ったもの）

このアイデアの検討（2026-09-22、1 セッション）で skill が邪魔になった・足りなかった・曖昧だった点と、
オーナーの進め方から読み取れた好み。検討が一区切りついたら改善案にまとめ、オーナーが決めた分だけ skill を編集する。

## オーナーの進め方（今回観察したもの）

- **記録の前に対話する。** Claude がヒアリング直後に、ヒアリング記録・decisions.md・open-questions.md・索引をオーナーに見せずに書いて push したところ、「記録の前に私と対話しましょうね」と指摘された。以後は「書く中身をチャットで見せる → 合意 → 書く」に切り替え、オーナーはこれで進めた。「Claude の読み（オーナー未確認）」を記録に入れる前に、その読みを選択式で確認するのが有効だった（3 つとも確認でき、うち 1 つに追加の要望が付いた）。
- **質問は選択式を好む。** 規模（1 回何分・何文・難易度）を「オーナーの言葉で」自由記述で聞いたところ、「選択式できいてほしいや」と言われた。intaking-ideas の「規模はオーナーの言葉で」は、選択肢に推奨と理由を付けた選択式で十分だった（オーナーは推奨を選び、記録には「Claude が出した選択肢から」と明記した）。
- **何ラウンドでもよいので、面で聞いてほしい。** 最初の依頼が「何ラウンドもかけていいからヒアリングして。複数選択式ね」。4 ラウンドで、前回（english-saas-venture, 2026-09-14）の記録と食い違う答え（音声、ストリーク）が 2 つ出た。前回の記録を先に読んでいたので、食い違いとして示して確認できた。
- **大きな方向転換を途中で入れる。** シナリオ形式の思いつきを自分で出して自分で没にした。LLM 判定・音声の推奨を「覆すようでアレだけど」と、シンプルな表裏カード + 自己採点に切り替えた。推奨が退けられても、その場で次の論点に移れる形にしておくと進みが止まらなかった。
- **シンプルさと楽しさを優先し、検証は後回しにする。** 既存アプリ・Anki との機能比較（Claude の推奨）、使えるかの基準（同）、自分で例文を抜き取る点検（同）を、いずれも選ばなかった。Claude はこれらを弱点として open-questions.md に残し、各所で明記した。english-vocab-app の没理由と同じ場所なので、実装前にもう一度出す余地がある。
- **楽しさは見た目で。** 「文章とかで示されるよりは、ライブラリとか使っていいから視覚的、グラフィカル、直感に訴えかけるような楽しさがほしいね」。「ドーパミン」という言葉も使った。選択肢に「見せ方」の軸を早めに入れるとよい。

## discovering-user-needs

- 手順 4 が「調査結果をファイルに書く」で、手順 6 で初めてオーナーに選択肢を出す。オーナーは記録の前に対話することを求めるので、**手順 3 と 4 の間に「結果をチャットで共有し、書き方の合意を取る」段が要る**。今回は結果をチャットで先に出し、合意の後に書いた。
- skill はスイープの前にヒアリングすることを前提にしていないが、今回はオーナーが「まず私の困りごとをヒアリングして」から始めた。ヒアリング記録（`research/user-needs/owner-pain-hearing.md`）は discovering-user-needs でも intaking-ideas でも作られず、どの skill の担当か曖昧だった。
- Jev の API キーが cloud の環境になく（zsh も無い）、triage は飛ばした。`sources.py quotes` はキー無しで動いたので、README に「quotes はキー不要」と明記するとよい。
- `sources.py quotes` の not_found の多くは、App Store の長い引用や改行を含む引用だった。短い断片で手作業で照合すると大半が見つかった。一方で、ワーカーの引用に言い換えが 2 件混じっていた（ページに無い文を引用として記録）。**「ページに無い」と「照合の失敗」を区別する手順**（断片での再照合）を skill に書くとよい。
- 安全上のルールで個人ブログは開けず、H1（飽き）の中心の声がメインで未確認のまま残った。ルールは妥当だが、ある仮説の支持がほぼ全部「開けないホスト」になったときの扱い（確度を下げる、オーナーに手で開いてもらう）が skill に無い。
- X と Reddit のセルは記録 0 件だった。批評役が指摘するまで気づけない。collect の段で 0 件のセルを早めに知らせる仕組みがあるとよい。
- オーナーの痛みの核心（「単語・句動詞・構文が選べない」）を仮説に入れず、瞬間英作文の製品への不満だけを仮説にした。結果「その声は 0 件」になったが、探すセルが無かったためで不在の証拠ではない。**オーナーの痛みそのものを 1 つは仮説に入れる**、を手順に書くとよい。

## intaking-ideas

- 規模（1 回何分・何文・水準）を「オーナーの言葉で」聞く規則が、選択式を好むオーナーと衝突した（上記）。「選択肢に推奨と理由を付け、選ばれたら『Claude の選択肢から』と記録する」を許す書き方にするとよい。
- 既存アイデア（english-saas-venture, 保留）と痛みが地続きだった。手順 1 の重複確認は機能した（新アイデアとして立てるかをオーナーが選んだ）。
- overview.md より先にヒアリング記録・decisions・open-questions を作ってしまい、「overview.md が未作成」を未決事項に入れる状態が生まれた。調査から始まるアイデアの場合の順序が skill に無い。

## shaping-experience

- オーナーの「ローカル db とブラウザだけで」は、ブラウザ内保存と PC のローカルサーバー + DB のどちらとも取れた。確認すると「スキーマは頻繁に変える」という新しい制約が出て、推奨がひっくり返った。**技術の形を聞くときは、配布の形より先に「試しながら何を頻繁に変えるか」を聞く**と早かった。
- 「ok」の一言で、体験の書き出しと技術の形の決定の両方を了承と受け取った。1 つのメッセージに 2 つの確認を入れると、どちらへの同意か曖昧になる。確認は 1 回 1 つにするか、AskUserQuestion で分けるべきだった。
- 推奨が 3 回退けられた（点検、評価の基準、当初の技術の形）。skill には「推奨が退けられたとき、そのリスクをどこに残すか」の指針が無い。今回は decisions.md の却下理由と open-questions.md の両方に残した。

## shaping-experience（2 回目、2026-09-22 の追記）

- オーナーの依頼は「体験・流れを決める要件定義をしっかり」で、画面・ワイヤー・デザインシステムは別セッションに回す、だった。skill の 4 つの軸（利用場面・中核のループ・便利さ・最初の版の範囲）だけでは、**中断したとき・終えた後・初回・×の見せ方・数え方（到達度やストリークの条件）** といった流れの要件が拾えなかった。今回は ui-ux-designing の references（`app-type-ux-patterns.md` の学習/教育アプリ、`questions-app-type.md` の導入 UI・終了演出・フィードバック密度）を知見として借りて問いを作った。skill に「流れの要件（初回・中断・終了後・失敗の見せ方・数え方）」の観点を足すとよい。
- ui-ux-designing を「知見だけ使う」使い方をした。この skill は成果物（design-concept.md / tokens.css）と競合調査を前提にしているが、references の学習アプリのパターン（ストリークの猶予、中断位置の復元、誤答を累積表示しない、報酬は進捗の可視化まで）は、概念レベルの推奨の根拠としてそのまま効いた。shaping-experience から「アプリの種類に応じて ui-ux-designing の references を読む」と参照させる価値がある。
- 「リサーチはしなくていい」で始まったが、報酬の上限の問いで「知識だけに基づかない方がいい。workflow なり Chrome なりで調べて」に変わった。**オーナーは問いによって調査の要否を切り替える**。最初の「調査なし」を会話全体の制約として扱わず、根拠の弱い問いでは調査を提案してよい。
- 排他の問いに「全部おねがい」が返った。skill の規則（全部入りは決定ではない。コストと副作用を並べて削るものを聞く）どおりに扱ったが、オーナーは同じ答えの中で調査を求めていたので、「調査の後で並べる」に回した。規則に「根拠が要るなら調査の後で並べてよい」と足すとよい。
- 共通の知識の置き場（LLM 基盤以外）がリポジトリに無かった。今回 `docs/knowledge/` を作った（`docs/decisions.md` 2026-09-22）。recording-research の書き先がアイデアの research/ しか想定していないので、共通ノートの場合の書き先を skill に足す必要がある。
