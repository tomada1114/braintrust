# english-opinion-trainer 体験の構想

設計レベル（画面、配色、トークン）には入らない。ここで決めるのは「どんな体験を
成立させるか」と「それは現実的か」まで。

## 利用場面

- 1 回の利用は 5 分以内。短文モードでも長めモードでも、お題 1 つに PREP などで答えてフィードバックを読むまでで完結する。
- 日々の隙間時間に 1〜数問。使い始めるきっかけはアプリを開くだけ（現在の単元の次のお題が、型とモードつきで出る）。
- やめるタイミングは 1 問のフィードバックを読み終えた時点でいつでも。
- 想定する場面は対面で軽い問いに自分の意見を分かりやすく伝える場面であり、試験対策ではない。

## 中核の体験

現在の単元（組み立て方の単元コース）の次のお題（日常の軽い問い）が出る。お題には組み立ての型（PREP / 譲歩型 / 比較型のいずれか）とモード（短文 / 長め）が紐づいており、どちらも単元コースが指定する。アプリが「今回はこの型で」と提示し、お題に固定されたモード（短文 1〜2 文 / 長め 4〜6 文）で英語で答える。意見が浮かばなければボタンでタネ（切り口 + キーフレーズ 1〜2 語、3 候補）を出せる。回答 1 つに対してレベルに合わせた決まった形式のフィードバックが返る（タネを使ったかどうかでフィードバックは変えない）。添削後の自分の一文（言い直し）が、お題のカテゴリと型のタグつきで「自分の言い回しリスト」に溜まり、見返せる。各単元は短文 8 問 → 長め 8 問、16 問で修了。スキップは可だが一巡には数えない。単元（型ごと 3 単元 + ミックス）を進む進捗が残る。お題・タネ・テンプレート説明は英語のみで持ち、日本語切替で日本語になるのは UI とフィードバックだけ。

- お題が出る → お題に紐づいた組み立ての型（PREP / 譲歩型 / 比較型）が提示される
- お題に固定されたモード（短文 1〜2 文 / 長め 4〜6 文）で英語で答える（詰まればボタンでタネ 3 候補: 切り口 + キーフレーズ）
- 回答 1 つに決まった形式のフィードバックが返る
- 添削後の言い直しがカテゴリ・型のタグつきで「自分の言い回しリスト」に溜まる
- 単元は短文 8 問 → 長め 8 問の順で 16 問。修了するとミックス単元へ進む

## 便利さの定義

- 便利さの定義: 「さっと出せて、かつ相手に伝わりやすいまとまった文章が書ける」ようになること。物差しはスピードではなく質。単純なタイムアタックは内容の質に直結しないので採らない。
- ChatGPT に比べて楽になるのは、場面設定・レベル指定・フィードバック形式の指示を毎回しなくてよいこと、発言 1 つ単位でフィードバックが返ること、設定と言い直しが消えないこと。
- できなくてよいもの: 会話の継続（追い質問のやりとり）、試験の採点、音声。
- 単元の進捗は動機づけであって上達の物差しではない。

## 最初の版で成立させる体験

最初の版に含める: 短文モードと長めモードの両方、3 テンプレート（PREP / 譲歩型 / 比較型）の提示、タネ（ボタンで表示、3 候補）、レベル選択、決まった形式のフィードバック、組み立て方の単元コースと進捗・修了、言い直しのブラウザ内保存（カテゴリ・型のタグつき）、UI 英語既定 + 日本語切替。

フィードバックの形式は固定 3 項目（伝わるか＝構成、直すべき 1〜2 箇所、レベル相応の言い直し）に加えて文法・語法の指摘。JSON Schema で固定し UI が描画する。段階評価（スコア）は入れない（decisions.md 2026-09-07）。「伝わるか」は型の要素ごとに 有 / 弱 / 無 と一言で返す（短文モードは先頭 2 要素）。型から外れた組み立てでも要素が拾えれば減点しない。

捨てるもの（理由つき）:
- ログイン・サーバー保存 — 外部システムで後から足せる。
- 出力済みフィードバックの言語再生成 — LLM の無駄。
- お題の LLM 生成 — 偏りの制御が難しい。
- 音声入出力 — チャット専用と決めた。
- 日本語以外の多言語 — 後で。
- ストリーク・ポイント — 隙間時間の利用と衝突し、スコアを入れない決定とも衝突する。
- ユーザーによる型の選択 — 開くだけで始まる体験を優先する。
- タネの実行時生成 — 事前生成で足りる（decisions.md）。
- ユーザーによるモード選択 — コースが指定する。短文だけで修了できないようにするため。
- 静的データ（お題・タネ・テンプレート説明）の日本語版 — シンプルさとイマーシブさを優先（decisions.md）。

## 実現性

- 難しいところ（技術）: ほぼなし。静的 SPA + LLM 中継 + ブラウザ内保存という構成で、技術的な難所は薄い。
- 難しいところ（コンテンツ）: お題 48 件（型 3 × カテゴリ 8 × モード。各セル 2 件を短文 1・長め 1 に割り当て）と 3 レベル分のタネ 432 行を Claude Code に生成させ、偏りは生成仕様（グリッド）と機械検証で、質はお題全件とタネ抜き取りで検収すること。生成仕様は `generation-spec.md` に書く。「伝わるか」は型の要素ごとの enum で返すのでスキーマで縛れる。プロンプト側に残るのは各要素の 有 / 弱 / 無 の判定基準と、指摘件数・言い直しの長さの粒度。レベル別にぶれないフィードバック基準（ルーブリック）の設計。日英両言語でフィードバックの質を揃えること。
- 難しいところ（運用）: ログインなしで公開すると LLM 呼び出しの鍵とコストが無防備になるので、公開範囲に応じてレート制限か入口が要る。
- 技術スタック候補: 決定は decisions.md（静的 SPA + 薄いサーバーレス関数で LLM を中継、TypeScript）。
  - 却下: ローカルサーバー + ブラウザ — 他人に配れない。
  - 却下: フルスタックフレームワークで最初から DB 前提 — 最初の版に重い、ブラウザ内保存の決定とかみ合わない。
- AI の構成とベンダーは assessing-ai-architecture で扱う。

## 想定ユーザーの広がり

まずオーナー自身の観測を一次情報とする。他人にも当てはまるかは open-questions.md の「オーナー以外に同じ痛みがあるか」に残す。
