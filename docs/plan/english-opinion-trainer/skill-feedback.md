# skill 改善メモ（english-opinion-trainer の検討で拾ったもの）

このアイデアの検討で skill が邪魔になった・足りなかった・曖昧だった点。検討が一区切りついたら改善案にまとめ、オーナーが決めた分だけ skill を編集する。

## intaking-ideas
- 手順1「重複なら既存を拡張」と断定している。実際は「別アイデアとして立てるか拡張するか」をオーナーが選ぶ論点。選択肢+推奨で確認する手順に直すべきか。今回はオーナーが先に「独立」と決めたため手順は走らなかった。
- slug の命名ルールがない（英語ケバブ、何を表すか）。README にもない。
- 既存アイデアを読む指示は「named slug のとき」だけ。近接アイデアがあるときに既存側を読むかどうかが曖昧。
- 質問ラウンド1で「観測された痛み」「既存の代替」は multiSelect で有効に機能した。ただしオーナー回答に新要件（UI 言語 EN 既定 + JP 切替）や、既存要件と矛盾する観測（「毎回リセットされるのが続かない要因」vs「最初の版はステートレス」）が混ざる。skill には「回答中に出た新要件・矛盾を拾って次ラウンドで確認する」手順がなく、4 軸の質問だけに閉じている。
- 「最初の版で捨てるもの」を聞く質問が 4 軸に含まれていない。overview テンプレートの見出しにはあるので、質問側に軸が足りない。
- skill 改善メモの置き場所について skill / CLAUDE.md に定めがなく、初回に確認が要った（今回の決定: docs/plan/<slug>/skill-feedback.md。ただしオーナーは docs の書き換え運用を嫌う）。
- 手順3「一文で言い換えて明示的に確認」で、オーナーは「合っている」ではなく修正案（両モード）を選んだ。skill には「修正が入ったら修正版で再確認するか、選択をもって合意とみなすか」の指針がない。今回は選択をもって合意とみなした。
- 「LLM が要る理由」の軸は、フィードバックとヒントが自由英文を扱う時点で自明で、質問として立てる価値が薄かった。質問の前提として置き、お題の出所（固定リスト vs 生成）に論点を移したほうが有効だった。skill の 4 軸は「LLM 前提の理由を問う」ではなく「LLM が要る部分と要らない部分を切り分ける」に書き換える余地がある。
- 決定の粒度: ラウンド 2 の 4 問に答えた時点で決定 6 件が一気に出た。skill には「質問回答の中の決定を decisions.md に落とすタイミング」が手順5（ファイル書き出し時）にしかなく、ラウンド間で拾う指示がない。

## shaping-experience

- 質問の選択肢ラベルに私（アシスタント）の想定「長めモード（IELTS Part 2 相当）」を書き、オーナーがそれを選んだ結果、想定がそのまま decisions.md に入った。次のラウンドで水準の乖離が判明し訂正エントリが要った。skill には「規模・分量・水準（1 回何分、何文、何問）の当たり付けを、オーナーの言葉で確認してから記録する」手順がない。選択肢ラベルはアシスタントの言葉なので、記録前にオーナーの言葉で言い直すべき。
- 実現性のパス（難しい点 3 種）は AskUserQuestion の中に入れられず、質問の前の本文に書いた。skill は「feasibility pass を走らせよ」とだけ言い、どこに出すか（質問前の本文か、experience.md に書いてから見せるか）を決めていない。
- フィードバック形式の問いで、オーナーは排他の選択肢に対して「全部入り」と答えた。skill には「オーナーが全部欲しいと言ったときにコストと副作用を示して絞り込む」指針がない。今回はスコアの懸念だけ open-questions に残した。
- 「他人にも当てはまるか」を必ず open に残せ、という指示は intaking-ideas 側で既にエントリを作っているため、shaping で二重に作りかけた。両 skill で担当を一本化するか、shaping 側は「既存エントリを指す」に変えるべき。
- 利用場面の問いで、オーナーの回答に「あなたと私にレベル感の乖離があるかも」という指摘が含まれた。skill の 4 軸は場面・ループ・便利さ・範囲だが、「対象の難度・水準」が軸として独立していない。intaking の restatement と合わせて、水準の確認を早い段階に置くべき。
- 排他の質問に対し、オーナーが選択肢にない第 4 の形（複数テンプレートをアプリが提示）を返し、別の問いでは記録済みの決定 3 件と衝突する答え（コース形式）を返した。skill には「答えが記録済みの決定と衝突したとき、どの決定が譲るかを次ラウンドで示して折り合いを付け、改める決定を『関係』行で明示する」手順がない。今回は次ラウンドで衝突を列挙し、両立する形を推奨して解消した。
- 4 論点を AskUserQuestion の上限 4 問に合わせ 2 ラウンドに分けた。後段の論点（お題リストの規模）が前段の答え（テンプレートの数、レベル数）で規模が変わるため、この順序が効いた。skill の「1〜2 ラウンド」は妥当だが、「後の問いの規模が前の答えで決まるものは後ろに回す」という順序の指針はない。
- 「全部入り」の罠は今回は出なかったが、コース + ストリーク + ポイントという足し算の選択肢を作り、各項目の衝突先を書いたことで絞れた。足し算の選択肢には衝突先の決定を書く、が有効だった。
- 「決定の間に落ちて、どこにも書かれていない論点」を洗い出す手順が skill にない。今回は前セッションが次セッション用プロンプトに仮説 7 件を渡し、裏取りして 1 件を外し 6 件を足した。決定が 20 件を超えたあたりで「決定同士の隙間」を一度棚卸しする段を置く余地がある。
- 推奨と違う選択肢（モードはコースが指定）が選ばれたとき、その選択の細部（指定の規則、修了条件、上書き可否）が新たな問いを生んだ。skill の「1〜2 ラウンド」には「推奨外が選ばれたら、その選択の細部を次ラウンドで詰める」という指針がない。
- 「今決める / handoff に持ち越す / 実装側に預ける」の 3 分類で漏れを仕分けてから質問に進む形が有効だった。skill の質問手順の前段として置ける。

## surveying-competitors

- 手順 4 は「実機パスはこのセッションで、ワーカーに任せない」と断定している。オーナーは「サブエージェントでやるのが望ましい。ただし並列で Chrome を動かすと壊れる」と明示した。メインが Fable のとき（orchestrating-models の姿勢）とも矛盾する。「実機パスは 1 体のサブエージェントに直列で任せてよい。並列起動は禁止。観察の書式を指定して返させ、メインが原典と突き合わせる」に書き換える余地がある。
- オーナーの呼び名（Languark）と実際の製品名（Langua by LanguaTalk）がずれていた。既知製品を種にする前に URL で製品名を確定する一手が skill にない。発見段の KNOWN_PRODUCTS に誤名が入ると重複統合が効かない。
- 範囲提案の 4 問（候補リスト / 軸 / 実機 / コスト）は 1 ラウンドで収まり、うまく機能した。ただし「実機で触る製品」はロングテールが分かる前に聞くことになり、「発見段の結果を見てから決める」という選択肢を用意する必要があった。skill の手順 1 と 2 の順序（実機候補の合意 → 発見段）は、発見段を回す場合は逆になる。
- 発見段と実機パスは互いに独立なので並行できたが、skill にはその旨がない（実機パスは手順 4 で、Workflow の後に置かれている）。
- 実機パスを Sonnet 1 体に直列で任せた結果、テンプレートの一次観察の節に沿った観察（仕組みの一文つき）が返り、メインで触るより安く済んだ。ただし副作用が 2 つ出た: (1) ChatGPT の「Work」タブにあった既存チャットへ誤送信、(2) 依頼範囲外のグローバル skill（operating-chrome の learnings.md）への追記。サブエージェントに実機パスを任せるなら「既存の会話・タスクに書き込まない」「依頼したファイル以外を編集しない」を明示する必要がある。
- 実機パスで「発言 6 回以上でないとフィードバックレポートが出ない」など、製品側のしきい値で核の観察に届かないことがある。skill の「止めた地点」の選択肢（サインアップ壁 / 課金要求 / 到達）に「製品のしきい値未達」がない。
- オーナーは「全部を実機で触らなくてよい。公式説明で分かるものはそれで済ませるほうが効率がいい」と明言した。skill の既定（上位 1〜3 件を実機）は合っていたが、実機の目的（フィードバックの仕組みを見る）を先に言語化しておくと絞りやすい。
- 一次観察（2 ターン）がオーナーの繰り返しの観測と食い違ったとき、私は一次観察を優先して overview の修正を推奨し、オーナーが「よく崩れる」と押し戻した。skill には「一次観察のサンプルサイズが小さいときはオーナーの観測を覆さない」「食い違いはどちらかを選ばず条件つきで両方残す」という指針がなく、「一次観察は Web の主張より優先」のルールだけが効いて過剰に振れた。

## assessing-ai-architecture

- 「SDK の指名は必要性の証拠ではない」の規則が実際に効いた（オーナーが Agent SDK を指名 → Step 0/1 で単発呼び出しと判定 → 指名を却下して従量課金 + 抽象化に着地）。規則は有効。ただし押し戻しの根拠として landscape の「サブスク転用はグレー」を使ったので、landscape がなければ記憶から主張する誘惑があった。「landscape に値がなければ recording-research」の規則は守れたが、規約系の値は landscape に「未確定」と書いてあるだけでも役に立った。
- tier チェック（Step 0/1/2）は質問の前に私が本文で先に判断を示し、質問は「呼び出し構成 / 構造化出力 / ベンダー」の 3 問に絞れた。skill の手順 1〜3 は「判断してから聞く」で運用できる。手順 4「選択肢 + 推奨 1 つ」は AskUserQuestion の形式と一致する。
- Step 2「最小の呼び出し」で「タネはお題固定リストなので事前生成できる」という削減が出た。これは体験（shaping）の決定を前提にした削減で、skill の「体験が決まらないと呼び出しは決まらない」という順序の根拠がそのまま効いた例。
- ベンダー比較で「レスポンス速度」がオーナーの軸に上がったが、landscape の 7 軸に速度（レイテンシ）がない。tiers.md の比較軸にも「応答速度」がない。単発呼び出しの対話アプリでは効く軸なので追加候補。
- 「フォーマットが崩れる」というオーナーの痛みが、構造化出力の要否という技術判断に直結した。intaking の段で拾った痛みを assessing まで持ち越して技術要件に落とす経路が skill 間に書かれていない（各 skill は前段の md を読むだけ）。

## recording-research

- 比較調査（3 社）を「1 社 1 体」の事実確認 3 本として回した。skill の「1 トピック 1 ワーカー、最大 3」に収まり、fact-check.md のブリーフはそのまま使えた。ただし成果は 1 ファイル（vendor-comparison.md）にまとめており、「1 トピック 1 ファイル」との整合は「トピック = 比較の問い」と解釈した。skill に「比較調査は 1 社 1 体で回して 1 ファイルにまとめてよい」と明記する余地がある。
- ワーカーは WebFetch（小型モデルの要約）経由で一次資料を読むため、フィールド名の表記揺れ（Google の responseSchema）や「and later」の解釈のような細部で確度が落ちる。メインの原典確認（手順 3）で 1 社 1 点ずつ確認したが、それでも要約経由である点は同じ。規約・API 仕様の逐語確認が要る点は、要約ではなく該当箇所の逐語引用を返させる指示をブリーフに足すと改善する。
- ワーカー結果の受け渡しに、サブエージェントの出力ファイル（JSONL 全文）から最終メッセージだけを切り出す作業が要った。skill は「ワーカーの返答を転記する」としか書いておらず、書き出しを別のサブエージェントに委譲する流れ（メインの節約）が想定されていない。
- `research/anthropic-structured-outputs.md` の結論「粒度はスキーマで縛れない」は自由文の長さ・件数についての結論だったが、open-questions と experience では「伝わるかの判定基準もスキーマで縛れない」と広く読まれていた。今回 enum / required の対応を読み直して判定の形を変えれば縛れると分かった。research の結論には「何について言えるか（適用範囲）」を 1 行添える指針が要る。
