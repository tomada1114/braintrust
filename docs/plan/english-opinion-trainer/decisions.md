## 2026-09-07 中核は一発の反復ドリル、短文・長めの 2 モード

- 決定: 中核は「ランダムなお題に意見を出す一発の反復ドリル」で、短文モード（1〜2 文）と長めモード（IELTS Part 2 相当）の 2 モードを持つ。
- 理由: 対面での一言と、時間をもらって長く喋ると支離滅裂になる、の両方の答え合わせが欲しい。
- 却下した案: 短文の一発のみ — 長く喋る練習ができない。
- 却下した案: お題のあと追い質問が 1〜2 往復入る形 — small-talk-trainer に寄り、ドリルの反復速度が落ちる。

## 2026-09-07 ログインなし、ブラウザ内保存

- 決定: 最初の版はログインなし、レベル・表記言語・直近の履歴はブラウザ内保存。将来は外部システムで認証と DB を持てるようにする。
- 理由: 「毎回リセットされると続かない」は自分で観測した離脱要因なので、バックエンドなしで消せる分は最初から消す。
- 却下した案: 完全ステートレス — 観測済みの離脱要因を持ち込む。
- 却下した案: 最初からアカウント + サーバー保存 — 認証・DB・課金の設計が先に必要で小さく始められない。

## 2026-09-07 表記言語は英語既定、日本語切替でフィードバックも日本語

- 決定: 表記言語は英語が既定、日本語に切り替えると UI もフィードバックも日本語になる。出力済みフィードバックをその場で何度も言語切替はしない。
- 理由: レベルの低い学習者はフィードバックが日本語で読めるほうが理解が速い。再生成は LLM の無駄遣い。
- 却下した案: UI だけ日本語でフィードバックは常に英語 — 読めないと直せずレベル選択の意味が薄れる。
- 却下した案: フィードバック言語を表記と独立に選べる — 設定が増え最初の版には過剰。

## 2026-09-07 お題は固定リスト、フィードバックとヒントは LLM

- 決定: お題（シチュエーション）は人手で作った固定リストからランダムに出す。フィードバックと意見のタネ（ヒント）は LLM に任せる。
- 理由: 体系的に学びたいので場面・難度の偏りを制御したい。LLM 呼び出しも減る。
- 却下した案: 毎回 LLM 生成 — 偏り・重複・難度のばらつきを制御しにくい。
- 却下した案: 固定リストを土台に LLM で肉付け — 最初の版には過剰、後から足せる。

## 2026-09-07 長めモードの水準を訂正

- 決定: 長めモードは軽い日常の問いに PREP で 4〜6 文でまとまって答えるもの。短文モードは同じ問いに 1〜2 文。IELTS Part 2 の 2 分独白と Writing は対象外。
- 理由: 本来の目的は対面で意見を分かりやすく伝えること。先のエントリの「IELTS Part 2 相当」は質問側の文言がそのまま入った誤り。
- 却下した案: 長めモードをディスカッションで時間をもらって話す 8〜10 文にする — 5 分に収まらずフィードバックも長くなる。
- 却下した案: お題の軽重をレベルで変える — お題リストをレベル別に作る負担が増える。

## 2026-09-07 両モードを最初の版から入れる

- 決定: 両モードを最初の版から入れる。
- 理由: オーナーの判断。どちらも 5 分で完結する水準なので最初の版が大きくならない。
- 却下した案: 短文モードのみで始める — 長めモードの水準が軽いと分かった時点で分ける理由が薄い。

## 2026-09-07 利用は 5 分以内、お題 1 つ単位で完結

- 決定: 1 回の利用は 5 分以内、お題 1 つ単位で完結する。
- 理由: 対面の軽い場面での力を想定しており、腰を据えた学習ではない。
- 却下した案: 15〜20 分で両モードを混ぜるセッション — 毎日続きにくい。
- 却下した案: レッスン直前のウォームアップ専用 — 場がない日に使われない。

## 2026-09-07 ループに残るのは「自分の言い回しリスト」

- 決定: ループの残るものは、添削後の自分の一文をブラウザ内に溜める「自分の言い回しリスト」。
- 理由: 体系性の最小単位で、見返すだけなら LLM 不要。
- 却下した案: フィードバックを読んで終わり — ChatGPT への「体系的に学べない」不満を持ち込む。
- 却下した案: 弱点傾向の蓄積 — フィードバックの構造化設計が先に要り、ブラウザ保存だけでは弱い。

## 2026-09-07 便利さの物差しは質

- 決定: 便利さの物差しは質。「さっと出せて、かつ伝わりやすいまとまった文章が書ける」こと。タイムアタックは採らない。
- 理由: 速さは内容の質に直結しない。
- 却下した案: お題から最初の一文までの時間 — 質を測れない。
- 却下した案: 続いた日数・こなしたお題数 — 続いてもさっと出せるようになったかは別。

## 2026-09-07 レベルが変えるのは言い直しの水準と指摘の厳しさ

- 決定: レベル（B1 など）が変えるのは、言い直しの語彙・構文の水準と、指摘の厳しさ。お題は共通。
- 理由: B1 の人に C1 の言い直しを見せても使えない。コンテンツ負担はプロンプト側だけ。
- 却下した案: お題の難度もレベルで変える — お題リストにレベルタグが要り作る量が増える。
- 却下した案: フィードバックの言語のやさしさだけ — 日本語切替があるのでレベル選択の意味が薄い。

## 2026-09-07 技術スタックは静的 SPA + サーバーレス中継

- 決定: 技術スタックは静的 SPA + 薄いサーバーレス関数で LLM を中継、TypeScript。
- 理由: ブラウザ内保存と相性がよく、鍵を隠せ、配布は URL を渡すだけ。後から認証・DB を外部サービスで足せる。
- 却下した案: ローカルサーバー + ブラウザ — 他人に配れず「ブラウザで動くアプリ」の像とずれる。
- 却下した案: フルスタックフレームワークで最初から DB 前提 — 最初の版に重く、ブラウザ内保存の決定とかみ合わない。

## 2026-09-07 最初の版ではフィードバックに段階評価（スコア）を入れない

- 決定: 最初の版のフィードバックは固定 3 項目（伝わるか / 直すべき 1〜2 箇所 / レベル相応の言い直し）と文法・語法の指摘で構成し、段階評価（スコア）は入れない。
- 理由: LLM の採点はぶれて数字が信用できず、「質重視」という便利さの物差しとも合わない。上達は溜まった言い直しリストで見える。
- 却下した案: スコアを入れて「目安」と明記する — 目安と書いても数字は追われ、ぶれが不信になる。
- 却下した案: 未決のまま AI 構成の段で決める — 構成の前提になるので先に決めた。

## 2026-09-07 立ち位置は「構成支援つきの意見ドリル」

- 決定: 既存製品に対する立ち位置は案 A「構成支援つきの意見ドリル」。お題 → 意見のタネ → PREP 型 → レベル別の言い直し、という「組み立て」の支援に立つ。
- 理由: 競合調査（`research/competitors/_comparison.md`、6 製品）で、PREP テンプレート / タネ / CEFR レベル選択で言い直し水準が変わる / ログインなし即開始、の 4 点はどの製品も未対応と確認できた。全製品共通の未解決課題「ヒントがあっても何を言えばいいか分からない」に直接当たるのがタネ + テンプレート。
- 却下した案: 案 B「ChatGPT の薄いラッパー」（差分をセットアップ不要と保存だけに置く） — GPTs やカスタム指示で代替され、価値が薄い。
- 却下した案: 案 C「対面の一言に特化した瞬発ドリル」（短文モードのみ） — 「長めモードを最初から」の決定と衝突し、「長く喋ると支離滅裂になる」痛みを扱えない。
- 併せて: 素の ChatGPT はプロンプト 1 つで形式・レベル・説明言語を 2 ターン維持した（一次観察）。守れる差分は「即開始」「言い回しリストが溜まる」「お題の体系」という運用面であることを認識したうえでの決定。

## 2026-09-07 overview の「既存プロダクトとの違い」から「形式が守られない」を外す

- 決定: ChatGPT に対する不満のうち「フィードバックが思った形式で返らない」は実機で再現しなかったので overview から外し、確認できた弱点（毎回のセットアップ、履歴が白紙、言い直しが溜まらない、添削が甘い〈第三者記事〉）と、確認できた 4 つの空白を差分として書く。
- 理由: 一次観察（`research/competitors/chatgpt.md`）が推測より優先。

- 却下した案: overview は直さない — 差分の主張が推測のまま残る。

## 2026-09-07 訂正: 「形式が守られない」は条件つきで残す

- 決定: 直前のエントリを修正する。ChatGPT の「フィードバックの形式が崩れる・安定しない」はオーナーの繰り返しの観測として overview に残す。2 ターンの一次観察で維持されたことは併記し、それを覆す根拠にはしない。
- 理由: オーナーが「フォーマットはよく崩れるし、安定しない」と明言した。短い実機サンプルより、繰り返しの利用で得た観測を優先する。
- 却下した案: 外したまま — 実機 2 ターンをオーナーの経験より重く扱うことになる。
- 却下した案: 「長い会話でのみ崩れる」と条件を断定する — 崩れる条件は未確認なので断定しない（open-questions へ）。

## 2026-09-07 AI の形は単発呼び出し 1 種。タネは事前生成の静的データ

- 決定: 実行時の LLM 呼び出しは「回答 1 つへのフィードバック」の 1 種だけ。意見のタネ（ヒント）は、お題が固定リストであることを使い、お題ごと・レベルごとに事前に一括生成して静的データとして同梱する。エージェント構成は採らない。
- 理由: 経路が事前に列挙できる（お題 → 回答 → フィードバック）のでエージェントの条件を満たさない。タネを実行時に生成する理由がなく、呼び出し数と品質のぶれを減らせる。
- 却下した案: タネを押したときだけ実行時生成 — 呼び出しが最大 2 倍、タネの質が実行ごとにぶれる。
- 却下した案: フィードバックと次のお題のタネを 1 回にまとめる — 次のお題を先に決める必要があり、ランダム出題とかみ合わない。
- 却下した案: エージェント構成（Agent SDK など） — 単発呼び出しに過剰。ツールループも権限制御も要らない。

## 2026-09-07 フィードバックは JSON Schema で固定し UI が描画

- 決定: フィードバックの出力はスキーマ制約つきの構造化出力（伝わるか / 直すべき 1〜2 箇所 / レベル相応の言い直し / 文法・語法の指摘）で受け取り、UI 側が描画する。言い回しリストへの保存は「言い直し」フィールドをそのまま使う。
- 理由: オーナーの観測「ChatGPT ではフォーマットがよく崩れ、安定しない」への構造的な対策。モデルが形式を守るかどうかに依存しない。
- 却下した案: Markdown の型をプロンプトで指示してそのまま表示 — ChatGPT で起きた崩れを持ち込む。
- 却下した案: 自由文をサーバー側でパース — 最も壊れやすい継ぎ目になる。

## 2026-09-07 最初から従量課金の API キーで開発する。サブスク転用は前提にしない

- 決定: 開発段階から従量課金の API キー + 少額の支出上限で進める。個人サブスク（Pro/Max など）を Agent SDK 経由で開発に使う「ローカルなら無料」は前提にしない。
- 理由: landscape（2026-09-06）でサブスク転用は「Agent SDK 経由のみ・規約上グレー」「claude.ai ログインや無料枠を第三者製品に提供することは事前承認なしに禁止」と記録されている。短文の単発呼び出しなので従量課金でも額は小さい。
- 却下した案: グレーを承知でサブスクを使う — 規約違反のリスクをオーナーが負う。
- 却下した案: 規約を事実確認してから決める — 従量課金にすれば確認自体が不要になる。

## 2026-09-07 ベンダーは Claude に限定しない。リポジトリ層で抽象化し、コスパと速度で選ぶ

- 決定: LLM ベンダーは特定しない。単発呼び出し 1 種なので、リポジトリ層（LLM クライアントの抽象）を分けてアダプタで差し替え・組み合わせできる構造にする。選定の軸はコストパフォーマンスとレスポンス速度、それにスキーマ制約つき構造化出力の強さ。将来 OpenAI や Gemini に移る可能性を前提にする。
- 理由: API 利用ならどのベンダーでも同じ形で呼べ、ロックインは低い。オーナーの言葉「API 利用ならなんでも変わらん。コスパとレスポンスの速さは大事」。
- 却下した案: Claude Agent SDK を指名どおり採用 — 単発呼び出しに過剰で、静的 SPA + サーバーレスの決定と相性が悪い。指名は習熟の証拠であって必要性の証拠ではない（assessing-ai-architecture の規則）。
- 却下した案: Anthropic Client SDK に固定 — strict スキーマは魅力だが、速度と単価の比較をせずに固定する理由がない。
- 却下した案: OpenAI 互換インターフェースで書いてベンダーは実装時に選ぶ — 抽象化の考え方は採用するが、互換レイヤーに寄せると構造化出力の保証が最小公約数に落ちる。抽象はアプリ側のリポジトリ層で持つ。
