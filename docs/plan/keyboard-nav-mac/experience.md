# keyboard-nav-mac(Hintjump)体験の構想

設計レベル(画面、配色、トークン)には入らない。ここで決めるのは「どんな体験を
成立させるか」と「それは現実的か」まで。

## 利用場面

- 使うのはオーナー本人がまず想定。Mac で作業中、両手がキーボードにあり、どこかを 1 か所押したいが、ポインタを持っていくのが億劫なとき。ブラウザ、Claude Desktop や Slack などの Electron 系、ネイティブアプリで使う
- 1 回の利用は数秒。ショートカットを押し、ラベルを 1〜2 文字打って終わる
- 頻度は現状 1 日に数十回(Homerow での実感)。オーナーは 1 日 100 回以上使うようにしたいと述べている
- 弱いところ: オーナーは分割キーボードにトラックボールが一体化した機材を使っており、現状は「ポインタをそのまま動かすほうが早い」と感じる場面が多い。つまり最初の想定ユーザー自身にとって、代替手段(トラックボール)が強い。Hintjump がトラックボールより速いと感じられなければ、回数は増えない
- 使い始めるきっかけは、押したい場所が目に入ったとき。やめるタイミングは、押した瞬間(自動で終わる)か、Esc で取り消したとき

## 中核の体験

決まったショートカットを押すと、対象の範囲にある押せる要素に英数字のラベルが出る。
ラベルを打つと、その要素が押されてラベルが消える。あとには何も残らない(記録も統計も持たない)。
「どこを押したいか」で入口を選ぶ判断はするが、ラベルが出たあとに範囲や動作を選び直すことはない。

- 入口を選ぶ(4 つ。すべて別のショートカット)
  - アクティブウィンドウを左クリック
  - アクティブウィンドウを右クリック
  - メニューバー左(アプリのメニュー)
  - メニューバー右(ステータスアイコン)
- ラベルが出る。メニューバーの入口ではほぼ確実に 1 文字。アクティブウィンドウでは、押されやすい要素に 1 文字を優先して配り、残りは 2 文字
- ラベルを打つ → 押される → 終わる
- メニューやアイコンを押して何かが開いたあとは、macOS 標準のキー操作(矢印キー、頭文字の入力、Enter)に任せる。開いたものにラベルを出し直す仕組みは持たない
- 「アクティブウィンドウ」の入口が対象にするのは、いま一番手前に出ているもの。開いているメニューや小さなパネルがあれば、それを対象にする。ステータスアイコンを押して開いたパネルの中を押したいときは、入口を押し直す(2 回の独立した操作)

## 便利さの定義

- 合格の基準: オーナーが Homerow を止めて Hintjump だけで 1 週間過ごし、Homerow に戻らなかった
- 戻ってしまう決定的な要因(オーナーの言葉)
  - ラベルが出るのが遅い
  - 押したい要素にラベルが出ない
- 速さの目安(オーナーの言葉): ショートカットを押してからラベルが出るまで 0.3 秒なら許せる。0.5 秒かかるとモヤっとする
- 大事だが最優先ではないもの: ラベルの見やすさ
- できなくてもよいもの: マウスを完全に使わなくなること(コピーなどでは必要、とオーナー)。利用回数の表示や記録(オーナーが一度挙げて取り下げた)

## 最初の版で成立させる体験

含めるもの

- 4 つの入口と、左クリック・右クリック
- 1 文字ラベルの優先配分(規則は推測から始め、実測で直す)
- アプリ単位の除外
- テキストファイルの設定(ショートカット、ラベルに使う文字、除外アプリ)
- Homebrew での配布
- 更新があることと、何が変わったかを利用者が確認できること(変更履歴をアプリ内に持つ形でもよい、とオーナー)
- 解析通信をしない

捨てるもの(理由は decisions.md)

- スクロール、テキスト検索、連続クリック、⌘クリック、Mission Control、Dock
- ドラッグ、ホバー、コピー、マルチモニター対応
- ターミナルやエディタ内のリンク検出
- 日本語入力での絞り込み、日本語ラベル
- 覚えられるラベル(固定ラベル)、画面内の範囲で絞る入口
- 開いたメニューへのラベルの出し直し
- 利用回数の記録、効果音、テーマ、Hyperkey

## 実現性

難しいところ

- 技術
  - 速さ。0.3 秒以内にラベルを出す。アクセシビリティのツリーは要素ごとにプロセス間通信が発生するため、素朴に全部読むと遅い。見えている範囲だけ走査する、属性をまとめて読む、という既知の対策がある(research/electron-ax-support.md)。ブラウザや Electron 系の大きなツリーで間に合うかは実測しないと分からない
  - 取りこぼし。「押したい要素にラベルが出ない」は決定的な離脱要因だが、アプリごとの例外処理が本体になる領域。Electron / Chromium はツリーを外から起こす必要があり、起こしても出ない部分がある(Homerow の issue #148。Claude Desktop のチャット部分)。初版に入れるかは実機検証で決める
  - 「いま一番手前に出ているもの」の判定。開いているメニューやパネルを確実に見つけられるかは未検証
  - 1 文字ラベルの優先順位。推測で始めるしかない。外れても 2 文字になるだけなので害は小さいが、効果が体感できるかは作ってみないと分からない
  - App Sandbox を切る前提。テンプレートは有効になっている。未確認の前提として open-questions.md にある
- 中身
  - 設定ファイルの初期値(4 つのショートカットの既定のキー、ラベルに使う文字)。他のアプリのショートカットと衝突しない既定値を選ぶ必要がある
  - 「入口を分ける」「押されやすい要素が 1 文字」という売りが、説明文と動画 1 本で伝わるか。オーナーは売り出し方の工夫が必要と述べている
- 運用
  - 署名。正規の開発者署名がないと、更新のたびに利用者がアクセシビリティ権限を付け直すことになる(neru の issue #737 で作者が報告。メインが原文確認)。無料の OSS でも、作者側に Apple の開発者プログラムへの加入が事実上必要。オーナーの加入状況は未確認(open-questions.md)
  - アプリごとの不具合報告が継続的に来る。Homerow の issue の多くが「特定のアプリで動かない」で、数年放置されているものもある(research/user-needs/hint-nav-pain-points.md)。一人で追い続けられる範囲を決めておく必要がある
  - macOS の更新で壊れる可能性。先行ツールは OS の更新のたびに修正を出している

技術スタック候補

- 実行の形: macOS の常駐アプリ(メニューバー常駐)。他の形は成立しない
- 言語と土台: Swift、オーナーの macos-app-template(薄いアプリ本体 + ローカルパッケージ、ロジックと UI の分離、テストとカバレッジの門)。決定済み(decisions.md)。ラベルの割り当て、優先順位、キー入力の状態遷移をロジック側に置けばテストで固められる。アクセシビリティの読み取りとクリックの合成は、ロジックでも UI でもない第 3 の層として足す
- 設定の保存先: テキストファイル 1 つ(決定済み)。形式の候補は TOML / YAML / JSON。選ぶ軸は、手で書きやすいこと、コメントが書けること、Swift で依存を増やさず読めること。推奨は TOML(手で書きやすくコメントが書ける。先行の OSS も採っている)。弱点は Swift 標準に読み込みが無く、依存を 1 つ足すか小さな読み込みを自作する必要があること。未決
- 更新の知らせ方: 候補は (a) Homebrew に任せ、アプリ内には変更履歴だけ持つ、(b) アプリ内更新の定番フレームワークを入れ、静的な更新情報ファイルを定期的に見に行く(専用のサーバーや API は要らない)。推奨は (b) を Homebrew と併用。オーナーの希望(更新があれば知らせる、何が変わったか分かる)を満たし、解析通信なしの約束とも両立する。未決
- AI: 使わない(決定済み)。assessing-ai-architecture は通さない

## 想定ユーザーの広がり

まずオーナーの観察を一次情報とする。他人にも当てはまるかは open-questions.md の
「オーナー以外に同じ痛みがあるか」に残してある。材料として、既存ツールの利用者の
不満を集めたメモがある(research/user-needs/hint-nav-pain-points.md)。1 文字ラベルを
求める声、メニューバーが 1 文字ラベルを独占するという不満、解析通信への懸念、
入力ソースとの相性の不具合は、公開の issue として確認できた。
