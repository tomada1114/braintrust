# macOS Accessibility API における要素の安定識別とヒントナビゲーションツールの命名方式

- 調査日: 2026-09-21
- 調査手段: Sonnet サブエージェント + メインによる原文確認(メインが確認した原典: Chromium ax_platform_node_cocoa.mm の AXDOMIdentifier(kHtmlId 由来)と AXDOMClassList(kClassName 由来)の実装、WebKit WebAccessibilityObjectWrapperMac.mm で NSAccessibilityDOMIdentifierAttribute / NSAccessibilityDOMClassListAttribute が前提条件なしで登録されていること。それ以外はサブエージェントの報告のまま)
- 問い: macOS の Accessibility API (AXUIElement) で、ネイティブ AppKit/SwiftUI アプリとブラウザ内の Web コンテンツについて「同じ UI 要素」を起動・呼び出しをまたいで安定的に識別できる属性は何で、どの程度信頼できるか、また既存のヒントナビゲーションツールは同一要素に同一ラベルを与える仕組みを既に持っているか。

## 結論

- **(a) ネイティブ属性**: `AXRole` / `AXSubrole` / `AXRoleDescription` はAppKit標準コントロールでは自動的に付与される(Appleの一次ドキュメントで明言)。一方 `AXTitle` / `AXDescription` / `AXHelp` / `AXIdentifier` はAppleドキュメント自身が「開発者が追加で設定すべき」と明言しており、既定値だけでは不十分なケースが多い。実際の母集団でどの程度埋まっているかを定量的に述べた一次資料は見つからなかった。
- **(b) Web領域属性**: `AXDOMIdentifier` / `AXDOMClassList` はWebKit(Safari)・Chromium(Chrome/Arc等)の両ソースコードで確認でき、それぞれDOMの `id` / `class` 属性から1対1で生成される。WebKitではこれらは無条件(precondition無し)でサードパーティAXクライアントに公開される一方、`AXIdentifier`(=`accessibilityIdentifier`)はWeb領域については既定で無効化されたフラグの裏にあり、既定では `nil` を返す、という重要な非対称性がソースコードで確認できた。Firefox/Geckoが同様の属性をmacOS AX APIに公開しているかは一次資料で確認できなかった。
- **(c) AXUIElementの永続性**: Appleの一次ドキュメントには「起動をまたいで永続しない」と明示的に書かれた文は見つからなかった。ただし `AXUIElementCreateApplication` はOSが起動ごとに割り当て直す `pid_t` から生成される、という構造的事実と、コミュニティ側の傍証(無効化エラー・非公開APIへの依存例)から、実務上は永続しないと推測される。これは「確認」ではなく「間接証拠からの推測」である点を明記する。
- **(d) 既存ヒントツールの命名方式**: 調査した範囲では、「同じ要素に毎回同じラベルを付ける」ことを掲げて実装している既存ツールは確認できなかった。Tridactylの `words` モードはランダムな3文字英単語を使う(要素名由来ではない)。Vimiumのfiltered hintsはページ内のリンクテキストで絞り込む機能であり、要素の永続的識別子ではない。Homerow公式(閉鎖ソース)がSNSで「要素ツリーが変化しなければヒント文字を一定に保つ」と言及したとされる投稿を検索経由で見つけたが、一次ソースへ到達して直接確認することはできなかった。

## 根拠

### (a) ネイティブAppKit/SwiftUI要素

- 事実: `kAXRoleAttribute`, `kAXSubroleAttribute`, `kAXRoleDescriptionAttribute`, `kAXTitleAttribute`, `kAXDescriptionAttribute`, `kAXHelpAttribute`, `kAXURLAttribute` はいずれも `AXAttributeConstants.h`(Apple ApplicationServices/HIServicesフレームワーク付属ヘッダ)に定義されている。`kAXRoleAttribute`("AXRole")は「要素の基本的な型を識別する」等。
  - URL: https://github.com/phracker/MacOSX-SDKs/blob/master/MacOSX10.7.sdk/System/Library/Frameworks/ApplicationServices.framework/Versions/A/Frameworks/HIServices.framework/Versions/A/Headers/AXAttributeConstants.h
  - 出典日付: 記載なし(macOS 10.7 Lion SDK由来のヘッダのGitHubミラー)
  - 確度: 中(Apple純正ヘッダの内容だが、要約はミラー経由のAIサマリで取得しており逐語確認はしていない)

- 事実: `kAXIdentifierAttribute` はmacOS 10.7(Lion)で追加された。Apple公式ドキュメントのメタデータで `"platforms":[{"name":"macOS","introducedAt":"10.7","current":"15.4"}]` と明記。
  - URL: https://developer.apple.com/documentation/applicationservices/kaxidentifierattribute
  - 出典日付: 記載なし(ドキュメントの`current`プラットフォームはmacOS 15.4まで確認)
  - 確度: 高(Apple公式ドキュメントAPIから直接取得したJSONメタデータ)

- 事実: `accessibilityIdentifier()` の説明:「アクセシビリティ要素の一意なIDを返す。多くの場合、自動テストに使用される」。原文引用: “Returns the unique ID for the accessibility element. It is often used in automated testing.”
  - URL: https://developer.apple.com/documentation/appkit/nsaccessibilityelementprotocol/accessibilityidentifier()
  - 出典日付: 記載なし(ページの著作権表示は2026年)
  - 確度: 高(Apple公式ドキュメントAPIから逐語取得)

- 事実: 標準AppKitコントロールは `NSAccessibility` プロトコルに準拠し、既定値・既定実装を自動的に持つ。原文引用(要約経由だが公式Guide本文からの抽出): "AppKit views and controls adopt the `NSAccessibility` protocol. This provides appropriate default values and implementations for all the information properties and action methods." および "an `NSButton` object's `accessibilityLabel` property automatically defaults to the button's title... They are accessibility-enabled straight out of the box."
  - URL: https://developer.apple.com/library/archive/documentation/Accessibility/Conceptual/AccessibilityMacOSX/EnhancingtheAccessibilityofStandardAppKitControls.html
  - 出典日付: 記載なし(developer.apple.com/library/archive配下のアーカイブ文書。Swift以前の記法を含み、比較的古い可能性がある)
  - 確度: 中(Apple公式Guideだが、archiveされた古い文書であり最新のSwiftUI事情を反映していない可能性)

- 事実: 同じGuideは「既定値は完全だが、常に有用とは限らない」とし、`accessibilityLabel`・`accessibilityHelp`・`accessibilityRoleDescription` を開発者が調整すべき対象として挙げている。原文引用(要約): "However, while the AppKit's default properties are complete, they are not always as useful as we would like... Every element that the user can interact with must have a meaningful value set for its `accessibilityLabel` property."
  - URL: 同上(https://developer.apple.com/library/archive/documentation/Accessibility/Conceptual/AccessibilityMacOSX/EnhancingtheAccessibilityofStandardAppKitControls.html)
  - 出典日付: 記載なし
  - 確度: 中(同上の理由)

  - URL: https://developer.apple.com/documentation/swiftui/view/accessibilityidentifier(_:) (および複数のサードパーティ解説記事)
  - 出典日付: 記載なし

### (b) Web領域属性(WebKit/Chromium)

- 事実: WebKitソースは `NSAccessibilityDOMIdentifierAttribute` を基本属性リストに precondition無しで登録し、`handleDOMIdentifierAttribute` はDOMの `identifierAttribute()`(=id属性)をそのまま返す。逐語引用(WebKit/WebKitリポジトリ main branch, `Source/WebCore/accessibility/mac/WebAccessibilityObjectWrapperMac.mm`):
  ```
  { NSAccessibilityDOMIdentifierAttribute, { handleDOMIdentifierAttribute, { } } },
  { NSAccessibilityDOMClassListAttribute, { handleDOMClassListAttribute, { } } },
  ...
  static id handleDOMIdentifierAttribute(WebAccessibilityObjectWrapper*, AXCoreObject& backingObject)
  {
      return backingObject.identifierAttribute().createNSString().autorelease();
  }
  static id handleDOMClassListAttribute(WebAccessibilityObjectWrapper*, AXCoreObject& backingObject)
  {
      return createNSArray(backingObject.classList()).autorelease();
  }
  ```
  - URL: https://github.com/WebKit/WebKit/blob/main/Source/WebCore/accessibility/mac/WebAccessibilityObjectWrapperMac.mm
  - 出典日付: 記載なし(mainブランチの現行コード、取得日2026-09-21時点)
  - 確度: 高(メインが curl で生ソースを直接取得・grep確認。preconditionが `{ }` = 常に登録される)

- 事実: WebKitでは `accessibilityIdentifier`(macOSの`AXIdentifier`に相当)がWeb領域では既定で無効(`false`)で、`AXObjectCache::accessibilityDOMIdentifiersEnabled()` フラグがtrueの場合のみDOM idを返す。逐語引用:
  ```
  - (NSString *)accessibilityIdentifier
  {
      if (AXObjectCache::accessibilityDOMIdentifiersEnabled()) {
          if (RefPtr<AXCoreObject> backingObject = self.updateObjectBackingStore)
              return backingObject->identifierAttribute().createNSString().autorelease();
      }
      return nil;
  }
  ```
  および `AXObjectCache.cpp`: `std::atomic<bool> AXObjectCache::gAccessibilityDOMIdentifiersEnabled = false;`
  - URL: https://github.com/WebKit/WebKit/blob/main/Source/WebCore/accessibility/mac/WebAccessibilityObjectWrapperMac.mm , https://github.com/WebKit/WebKit/blob/main/Source/WebCore/accessibility/AXObjectCache.cpp
  - 出典日付: 記載なし
  - 確度: 高(生ソース直接確認)。ただし「何がこのフラグをtrueにするか」(Safari実運用で有効かどうか)は特定できず→グレーゾーンへ

- 事実: Chromiumソースは `AXDOMClassList` / `AXDOMIdentifier` をそれぞれDOMの `kClassName` / `kHtmlId` 属性から生成する。逐語引用(`chromium/chromium` master, `ui/accessibility/platform/ax_platform_node_cocoa.mm`):
  ```
  - (NSArray*)AXDOMClassList {
    ...
    if (_node->GetStringAttribute(ax::mojom::StringAttribute::kClassName, &classes)) { ... }
  }
  - (NSString*)AXDOMIdentifier {
    ...
    if (_node->GetStringAttribute(ax::mojom::StringAttribute::kHtmlId, &id)) {
      return base::SysUTF8ToNSString(id);
    }
    return @"";
  }
  ```
  - URL: https://github.com/chromium/chromium/blob/master/ui/accessibility/platform/ax_platform_node_cocoa.mm
  - 出典日付: 記載なし(masterブランチ現行コード)
  - 確度: 高(メインが curl で生ソースを直接取得)

- 事実: Chromium自身のテスト用ツール(`ax_element_wrapper_mac.mm`)も `kAXDOMIdentifierAttribute` をmac AXツリーから読み取る形でDOM IDを取得しており、この属性がChromium内部でも正規の識別手段として扱われている。逐語引用: `std::string AXElementWrapper::DOMId() const { id domid_value = *GetAttributeValue(base::apple::CFToNSPtrCast(kAXDOMIdentifierAttribute));`
  - URL: https://chromium.googlesource.com/chromium/src/+/refs/heads/main/ui/accessibility/platform/inspect/ax_element_wrapper_mac.mm
  - 出典日付: 記載なし(コード内コピーライト表記2022年、mainブランチ)
  - 確度: 高(base64生データを直接デコードして確認)

- 事実: 実運用での傍証として、Electron/Chromiumベースアプリ(Microsoft Teams, com.microsoft.teams2)で、`microphone-button` 等の識別子が `AXDOMIdentifier` 経由で取得でき、`AXIdentifier` は存在しなかったという報告。引用: “Chromium surfaces the Windows automation ids on `AXDOMIdentifier`, not `AXIdentifier` (that attribute is absent).” macOS 26 / Apple Silicon上のTeamsで検証。
  - URL: https://github.com/danswett/streamdeck-teams-control/issues/4
  - 出典日付: 2026-09-21 (Issue作成日として表示。ただし今回の調査基準日と完全一致しており、内容の信頼性は単独報告に留まる点に注意)
  - 確度: 中(サードパーティの単発実地報告。ソースコード上の裏付けとは整合している)

- 事実: Firefox/Geckoのmac AX実装がDOM id相当の属性を公開しているかどうかは、一次資料(Mozillaソース)から直接確認できなかった。
  - URL: https://firefox-source-docs.mozilla.org/accessible/index.html (概要のみで属性の詳細記述なし)
  - 出典日付: 記載なし
  - 確度: 低(未確認、グレーゾーンに記載)

### (c) AXUIElementの永続性

- 事実: `AXUIElementCreateApplication` は「指定したプロセスID」に基づいてトップレベルのアクセシビリティオブジェクトを生成する(上記(a)の同項目と同じ)。Apple公式ページ内には起動をまたいだ永続性についての明示的な記述は存在しなかった(空白)。
  - URL: https://developer.apple.com/documentation/applicationservices/1459374-axuielementcreateapplication
  - 出典日付: 記載なし
  - 確度: 高(「言及がない」こと自体は直接確認済み)

- 事実: サードパーティ調査によれば、AXUIElementとCGWindowIDをアプリ再起動をまたいで安定対応させる公開APIは存在せず、AeroSpace(ウィンドウマネージャ)は非公開関数 `_AXUIElementGetWindow` に依存している。
  - URL: https://github.com/conveen/context-manager/pull/113
  - 出典日付: 記載なし
  - 確度: 中(サードパーティの議論。AeroSpaceの一次ソース自体は未確認)

- 事実: `AXUIElementRef` はCore Foundationの `CFEqual` 等で比較可能なCFTypeRefであり、`kAXErrorInvalidUIElement` は「渡されたAXUIElementRefが無効」な場合に返るエラーコードとして定義されている(プロセス終了等で無効化されることを示唆)。
  - URL: https://developer.apple.com/documentation/applicationservices/axuielement_h
  - 出典日付: 記載なし
  - 確度: 中(検索エンジン要約経由、逐語確認はできていない)

- 事実: Hammerspoonの `hs.axuielement` に対し、「`==` で等しいと判定される2つのaxuielementオブジェクトが、Luaのテーブルキーとしては別物として扱われる」ため、安定したハッシュ/IDが欲しいという未解決の機能要望が出ている。逐語引用: "the comparison `currentElment1 == currentElement2` would return `true`, while after `table[currentElement1] = true` the entry `table[currentElement2]` is still `nil`."
  - URL: https://github.com/Hammerspoon/hammerspoon/issues/3532
  - 出典日付: 記載なし(メンテナ・コントリビュータの返信なし、未解決)
  - 確度: 中(サードパーティラッパーでの実地報告。AXUIElement自体の等価性とラッパーオブジェクトの等価性は別問題である点に注意)

- 事実: Apple Developer Forumsで、`AXUIElementCreateApplication` → `AXUIElementCopyAttributeValue` がmacOS Big Sur以降、エラー-25204で失敗するという報告が2021年から2025年まで繰り返されており、Apple担当者の返信はスレッド内に存在しない。
  - URL: https://developer.apple.com/forums/thread/687965
  - 出典日付: 記載なし(スレッド内の各投稿は2021年8月〜2025年6月ごろと要約に記載)
  - 確度: 中(未解決のユーザー報告の集積。AX API全般の不安定さの傍証として)

### (d) 既存ヒントナビゲーションツールの命名方式

- 事実: Vimiumの "filtered hints" は、ヒントをアルファベットではなく数字にし、リンクのテキストを直接入力してヒントを絞り込める機能。既定ではないオプトイン設定。これは「セッション内でのテキストによる絞り込み」機能であり、「同じ要素に常に同じ固定ラベルを与える」永続識別の仕組みではない。
  - URL: https://github.com/philc/vimium/wiki/Using-Link-Hints
  - 出典日付: 記載なし
  - 確度: 中(検索エンジンによるWiki内容の要約。逐語ページは未取得)

- 事実: Tridactylの `hintnames` 設定は `short` / `numeric` / `uniform` / `words` の4モードを持ち、`words` モードは「ランダムな3文字の英単語」をヒント名として使う。逐語引用(config.tsのコメント): "Whether to optimise for the shortest possible names for each hint, or to use a simple numerical ordering. If set to `numeric` or `words`, overrides `hintchars` setting. `words` uses random three letter English words (and therefore works badly with hintfiltermode vimperator*)" 重要: "words" モードは要素名(リンクテキスト等)由来ではなく**ランダム**割当てであることが明記されている。ユーザーの仮説にある「name-derivedなヒント」ではない。
  - URL: https://raw.githubusercontent.com/tridactyl/tridactyl/master/src/lib/config.ts

- AXUIElementRefが起動をまたいで永続しないことを明示的に述べたApple一次ドキュメントは見つからなかった。ユーザーの前提「(they do not across launches?)」は、`pid_t`ベースの生成方式・`kAXErrorInvalidUIElement`・AeroSpaceが非公開APIに頼っている事実などの間接証拠から支持されるが、Apple自身が明文化した文は発見できなかった。「調べたが分からなかった」に該当。
- WebKitの `AXObjectCache::gAccessibilityDOMIdentifiersEnabled` フラグを実際に何が(いつ)`true`にするか(Safari本体の既定挙動でtrueになるのか、Web Inspector/テスト専用機能なのか)は、ソースコード内の設定箇所を発見できず未確認。

- Firefox(Gecko)がmacOSのAXツリー上でDOM idに相当する属性(AXDOMIdentifier等)を公開しているかどうかは一次資料から確認できなかった。「調べたが分からなかった」に該当。

## 影響する論点

- WebKit/ChromiumのソースコードレベルではWeb領域の `AXDOMIdentifier`/`AXDOMClassList` は安定してDOM idを反映する設計になっている一方、WebKit側では `AXIdentifier` 自体はWeb領域では既定で無効という非対称な実装になっている。属性名を取り違えると「ブラウザでは属性が存在しない」という誤った結論に至りうる。
- ネイティブ側は「標準AppKitコントロールは既定でラベル付けされる」一方、「開発者による明示的な設定が推奨される」という二重の状況があり、Apple自身のドキュメントも定量的な充足率を明言していない(グレーゾーン)。
- AXUIElementの起動間永続性は、Apple一次資料の「明言の不在」+間接証拠という構成であり、「確認された事実」ではなく「複数の傍証から支持される推測」である点は、事実確認としては重要な区別。
- 調査した範囲のヒントナビゲーションツール(Vimium, Vimium-C, Tridactyl, Surfingkeys, vimac, Shortcat, neru, mousemaster, warpd, Scoot, Wooshy)のうち、公式ドキュメント・ソースコードから「同一要素に毎回同一の固定ラベルを与える」設計を明示的に確認できたものは一つもなかった。Tridactylの"words"モードは明示的に**ランダム**割当てである。Homerowの関連する挙動は一次ソースに到達できず未確認のままである。
- open-questions.md の「覚えられるラベル(同じ要素に同じラベル)を看板機能にするか」に効く。
