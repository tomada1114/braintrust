## 2026-09-21 既存アイデアの作り直しではなく、新しいアイデアとして立てる

- 決定: small-talk-trainer / english-opinion-trainer の作り直しではなく、全く新しいアプリとして考える。
- 理由: オーナーの判断（セッション開始時の前提）。
- 却下した案: 却下済みの英会話アイデアを再開する — 却下理由は技術ではなく体験設計で、再開条件も書かれていない。

## 2026-09-21 macOS 27 以降、オフラインで動く macOS アプリ

- 決定: 対象は macOS 27 以降。オフラインで動くこと。画面はシンプルなウィンドウ 1 つ。
- 理由: オーナーの判断（前提）。オーナーの Mac は調査時点で macOS 26 系だったが、オーナーが上げると明言した。
- 却下した案: macOS 26 のまま先に旧モデルで質を試す — 27 で結果が変わる可能性が高く二度手間。オーナーは事前検証自体をしないと決めた（下のエントリ）。

## 2026-09-21 会話はキャッチボール式。話し終わりはクリックで明示

- 決定: 話し終わりの自動検知と、相手の発話中の割り込みはやらない。自分の番の終わりはクリックなどで明示する。「会話をスタート」を押すと相手（AI）から話しかけてくる。
- 理由: オーナーの判断（前提）。
- 却下した案: 自動検知・割り込みありの自然な音声会話 — オーナーが初版の範囲外とした。

## 2026-09-21 中核の言い直し

- 決定: 作るのは英会話の練習装置（添削・採点・コース）ではなく、Mac の中だけで英語の雑談が声で往復できる土台。初版の成果は使えるアプリではなく、動く土台と会話ログ。
- 理由: アシスタントの言い直しにオーナーが「合っている」と回答。
- 却下した案: なし（言い直しへの修正は出なかった）。

## 2026-09-21 初版は土台の検証。将来の構想は計画に入れない

- 決定: 初版の目的は土台作り（macOS アプリを作れるか、ローカルでチャットが気持ちよく回るか）。単語帳、続きの会話、複数キャラクター、複数人会話などの構想は一旦計画に入れない。
- 理由: オーナーの言葉「将来の目標とか構想とかは一旦何も計画には入れずに、まずとりあえずローカルで成り立つようにしよう」。
- 却下した案: 初版の時点でオーナーが日常で使う道具にする — ChatGPT の音声モードの代わりに開く理由が初版から要り、ハードルが上がる。
- 却下した案: 検証版と日常利用版の条件を 2 段で書く — オーナーは検証だけを選んだ。

## 2026-09-21 段階はテキストチャット → 読み上げと音声入力。完了は「機能として完成」

- 決定: まずテキストのチャットをローカルで成り立たせ、その後に読み上げと、クリックで区切る音声入力をスムーズに動かす。各段の完了は「機能として完成すること」とし、数値基準や調整回数の上限は置かない。実際に使ってみて調整する。
- 理由: オーナーの言葉。いきなり音声まで行くと難しいが、チャットだけでは目標として小さすぎる。
- 却下した案: オーナーの「次へ進む」宣言で区切り、プロンプト調整は各段最大 3 周までという止め具を置く（アシスタントの推奨） — オーナーは初版では使いながら調整するとして採らなかった。
- 却下した案: 段ごとの動作チェックリスト — 同上。
- 補足（アシスタントの提案、オーナー未確認）: 第 2 段の中では読み上げを先、音声入力を後にするのが安全。

## 2026-09-21 「会話が成り立った」の合否基準は置かない。ログを Claude Code で振り返って調整する

- 決定: 会話のログを取っておき、後から Claude Code で振り返れるようにする。それをもとにシステムプロンプトなどを変えていく。
- 理由: オーナーの判断。
- 却下した案: 体感（10 往復 × 3 回を止めたくならずに終える）と計測の併用（アシスタントの推奨） — オーナーは基準を置かずログからの調整を選んだ。
- 却下した案: 数値だけで判定 / ChatGPT 音声モードとの比較 — 同上。

## 2026-09-21 LLM は Apple のオンデバイスモデル。事前の質の検証はしない

- 決定: 返答を作るのは Apple のオンデバイスモデル（Foundation Models framework）。事前検証はせず、会話の質が微妙だったとしてもまずこれを使う。
- 理由: オーナーの言葉「会話の質は微妙だったとしてもとりあえず使うしかない」。
- 却下した案: 先に `fm` などで質を確かめてからスタックを決める（アシスタントの推奨） — オーナーは検証を挟まないと決めた。
- 背景: `research/2026-09-21-on-device-voice-chat-stack.md`。

## 2026-09-21 譲れない制約はオフライン・無料。Apple 純正は第一候補だが固定しない

- 決定: Apple のモデルの質やコンテキスト長が将来の構想に足りなかった場合は、オフライン・無料を優先し、ローカルで動く OSS モデルへの差し替えを検討する。
- 理由: オーナーの判断。「無料で一つに完結、OSS として」という動機と一致する。
- 却下した案: Apple 純正だけでやり切り、モデルの限界に合わせて構想を削る — 依存ゼロで配布は楽だが、構想が成立しない可能性を受け入れることになる。
- 却下した案: 今は決めない — オーナーは優先順位を決めた。
- 背景: 差し替えの層（`LanguageModel` プロトコル）があることは Apple 公式で確認済み。手元の Mac で OSS モデルが快適に動くかは未確認（open-questions.md）。

## 2026-09-21 設計の原則: ログが正、モデルのセッションは使い捨ての窓

- 決定: 会話の状態はアプリ側のログが持ち、モデルのセッションはログから組み立て直せる作りにする。各往復のトークン数とコンテキスト長もログに記録する。
- 理由: オンデバイスモデルのコンテキスト長が短く、オーナーが「今後の方針にめちゃめちゃ関わる」として相談した論点。この原則なら、上限は「1 回の窓に入る量」の制約にとどまり、ミッション・続きの会話・複数キャラクターの道をどれも塞がない。
- 却下した案: 初版は素直に 1 セッションを使い続け、上限に当たったら考える — 最短で動くが、後で状態の持ち方を作り直すことになる。

## 2026-09-21 1 回の会話は 5〜10 分

- 決定: 1 回の会話は 5〜10 分の短い会話を基本とする。
- 理由: オーナーの判断。コンテキストの窓に収まる長さ（アシスタントの概算で、窓が埋まるのは早くて 15〜20 分）を踏まえたもの。
- 却下した案: 使ってみてから決める（アシスタントの推奨） — オーナーは長さを決めた。
- 却下した案: 15 分以上 — 窓の作り直しが毎回起き、要約の質が体験に効いてくる。

## 2026-09-21 話し終わりをクリックしたら即送信

- 決定: 認識結果の確認を挟まず、クリックしたらそのまま相手に渡す。聞き取りミスは認識結果がログに残るので、後で頻度を振り返る。
- 理由: 会話のテンポを優先。オーナーの選択。
- 却下した案: 認識結果を見てから送信 — 毎回 1 手増えてテンポが落ちる。
- 却下した案: 即送信 + 直前の取り消し — 実装と状態管理が増える。

## 2026-09-21 自分と相手の発話は常に画面に文字で出す

- 決定: 自分の発話（認識結果）も相手の返答も、常に文字で表示する。
- 理由: 検証版なので、認識結果と返答が目で見えるほうが原因を切り分けやすい。第 1 段のチャット画面をそのまま使える。オーナーの選択。
- 却下した案: 相手の文字を隠せるトグル — 初版に UI が 1 つ増える。
- 却下した案: 音声のみで文字はログだけ — 聞き取れなかったときの逃げ道がなく、不具合も見えにくい。

## 2026-09-21 ログは会話ごとの JSONL ファイル。振り返りの仕掛けは入れない

- 決定: 1 会話 1 ファイル、1 発話 1 行の JSONL でローカルに記録する。会話中の印や会話後のメモなど、振り返りを楽にする仕掛けは初版には入れず、記録だけにする。
- 理由: Claude Code がそのまま読め、将来の単語帳や続きの会話にも変換しやすい。オーナーの選択。仕掛けについてはオーナーの言葉「とりあえず初版では何もいれない。ただ記録でいい」。
- 却下した案: SwiftData（SQLite） — 初版は一覧画面を持たないので利点が出にくく、Claude Code で読むには書き出しが要る。
- 却下した案: ログ + ワンクリックの印（アシスタントの推奨） / ログ + 会話後のメモ — オーナーは初版に入れないと決めた。
- 補足（アシスタントの提案、実装時に調整可）: 1 行に持つ項目は、話者・本文・時刻、認識の生テキスト、各段の所要時間、システムプロンプトの版、トークン数、コンテキスト超過などの出来事。

## 2026-09-21 読み上げは AVSpeechSynthesizer + Premium 音声から始める

- 決定: 読み上げの最初の一手は AVSpeechSynthesizer と、システム設定から手動で入れる Premium の英語音声。不満なら後で Kokoro に差し替える。
- 理由: 実装が数行で依存がない。オーナーの選択。
- 却下した案: 最初から Kokoro（MLX） — 依存、モデル同梱、音声再生の自前実装が要り、初めての macOS アプリで最初に背負うには重い。
- 却下した案: 今入っている標準音声で始める — 機械的な声で「気持ちよく回るか」の判断を悪い方へ歪めやすい。

## 2026-09-21 自分専用、サンドボックスなし

- 決定: 初版は自分専用。App Sandbox は使わず、署名や公証も考えず Xcode から直接動かす。ログは `~/Library/Application Support/<アプリ名>/` に置く。
- 理由: Claude Code から権限の確認なしでログを読める。配ると決めたら後でサンドボックスを入れる。オーナーの選択。
- 却下した案: 自分専用だがサンドボックスあり — ログが `~/Library/Containers/` 配下になり、ターミナルから読むときにアクセス確認が出ることがある。
- 却下した案: 他人に配る前提で始める — 署名・公証、初回セットアップの案内まで範囲に入り、土台の検証に対して重い。

## 2026-09-21 利用場面は「決まった時間に習慣として」。会話は自分で終了ボタンを押して終わる

- 決定: オーナーが決まった時間に習慣として 1 回話す。会話は自分で終了ボタンを押すだけで終わり、時間制限も終わりの合図も置かない。
- 理由: オーナーの選択。終了ボタンだけなら最小で、実際に何分話すかがログから分かる。
- 却下した案: 作業の合間に自宅で / 英語を使う予定の直前 / 決めていない — オーナーは習慣としての利用を選んだ。
- 却下した案: 時間が来たら相手が締める — 小さいモデルが自然に締められるかは未知で、初版の範囲が広がる。
- 却下した案: 終了ボタンで相手が一言返して終わる — 1 呼び出し増える。
- 補足: どの時間帯かは決まっていない。初版に習慣化の仕組みはないので、続くかはオーナーの意志に依る（experience.md の運用の難しさ）。

## 2026-09-21 技術スタックの大枠は Swift + SwiftUI、普通の Xcode プロジェクト

- 決定: Swift + SwiftUI で、普通の Xcode プロジェクトとして作る。
- 理由: 音声認識・オンデバイス LLM・読み上げの 3 部品がすべて Swift の API で、橋渡しが要らない。マイク権限の宣言も素直。「macOS アプリを作れるか」という検証目的にも合う。オーナーの選択。
- 却下した案: Python SDK + 簡易 UI — 音声認識と読み上げは Swift の API なので橋渡しが要り、検証目的から外れる。
- 却下した案: Electron / Tauri + Swift の補助プロセス — 3 部品のために結局 Swift のプロセスを別に作ることになり、継ぎ目が最も多い。
