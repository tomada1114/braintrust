# offline-voice-chat-mac 体験の構想

設計レベル（画面、配色、トークン）には入らない。ここで決めるのは「どんな体験を
成立させるか」と「それは現実的か」まで。

## 利用場面

- オーナー自身が、声を出せる場所で Mac の前にいるとき。決まった時間に習慣として 1 回、5〜10 分（decisions.md）。どの時間帯かは未決
- 使い始めるきっかけはオーナー自身の習慣で、アプリ側に促す仕組みは持たない（初版では習慣化の仕組みを捨てている）。「会話をスタート」を押すと相手から話しかけてくる
- やめるタイミングは、自分で終了ボタンを押したとき。時間制限も終わりの合図もない

## 中核の体験

「会話をスタート」を押すと、相手（AI）が英語で話しかけてくる。自分はクリックで話し始め、クリックで話し終わりを示す。認識された文が確認なしでそのまま相手に渡り、返答が文字で出て読み上げられる。自分の発話も相手の発話も常に画面に文字で見えている。これを 5〜10 分往復し、終了ボタンで終わる。残るのは会話 1 回分のログファイルで、後から Claude Code で読んで、相手への指示（システムプロンプト）などを直す材料にする。

- スタートを押す → 相手が話しかけてくる → クリックして話す → クリックして渡す → 返答を読み、聞く（繰り返す） → 終了ボタンで終わる → ログが残る
- 外側のループ（アプリの外）: 溜まったログを Claude Code で振り返る → 相手への指示や部品を直す → また話す

## 便利さの定義

初版は土台の検証であり、既製の音声モードより便利であることは求めない（decisions.md）。初版で「できた」と言えるのは次の状態。

- ネットワークを切った状態で、声の往復が途中で止まらずに 5〜10 分続く
- 会話が終わると、Claude Code がそのまま読めるログが欠けなく残っている
- 既存の代替（既製の音声モード）と比べて楽になる点は、初版では「課金・接続・アカウントを気にしなくてよい」「記録が自分の手元のファイルに残る」の 2 つだけ。オーナーが本当に欲しい「一つで完結」は初版に入らない
- できなくてもよい: 返答の賢さが既製品に並ぶこと、声の自然さ、聞き取りミスがないこと、会話らしい終わり方、聞き取り練習としての厳しさ（文字は常に出す）

## 最初の版で成立させる体験

段階を踏む（decisions.md）。各段の完了は「機能として完成すること」。

1. テキストのチャットがローカルで成り立つ: スタートで相手が先に書き出し、文字で往復でき、ログが残る
2. 読み上げと音声入力が加わる: 相手の返答が読み上げられ、自分はクリックで区切って声で話せる。テキスト入力は予備として残す（アシスタントの提案）

含めるもの（アシスタントの叩き台。オーナーから異論は出ていない）: 会話の終了ボタン、モデルが使えないときとマイクが拒否されたときの表示、相手の直前の発話を「もう一度聞く」。

捨てるもの:
- 話し終わりの自動検知と割り込み — オーナーの前提。キャッチボール式で足りる
- 添削、採点、話題・シナリオ・ミッション、レベル設定 — 練習装置の部品。却下された 2 つのアイデアが詰まった場所であり、土台の検証には要らない
- 単語帳、続きの会話、複数キャラクター — 将来の構想は計画に入れない（オーナーの決定）
- 振り返りの仕掛け（会話中の印、会話後のメモ） — オーナーの決定。記録だけでよい
- 認識結果の確認、相手の文字を隠すトグル — テンポと単純さを優先
- 習慣化の仕組み、設定画面、声の選択、日本語の補助 — なくても往復は成立する
- 配布に必要なもの — 自分専用

## 実現性

難しいところ:

- 技術: 最も重いのは音声入力。マイク権限、言語アセットの初回ダウンロード、非同期の結果ストリームをクリックの開始・終了とつなぐ状態管理がある。次に、オンデバイスモデルのコンテキスト長が短いこと。これは「ログが正、セッションは使い捨ての窓」の原則（decisions.md）で初版から備える。返答を作るモデルの会話の質と、日本語訛りの認識精度は、動かすまで分からない（open-questions.md）。オーナーにとって macOS アプリ開発そのものが検証対象でもある
- コンテンツ: ほぼない。相手への指示文 1 つだけで、これはログを見て直していく前提。お題やシナリオのようなコンテンツ作りを持たないことが、却下された 2 案との大きな違い
- 運用: **ここが最も弱い。** 合否の基準を置かず、痛みも弱く（overview.md）、習慣化の仕組みもないので、土台が動いた時点で話す理由が薄くなり、ログが溜まらず、「ログから調整する」外側のループが回らなくなる危険がある。調整に終わりの条件がないことも同じ危険の裏面。english-opinion-trainer の失敗（部品は決まったが体験がまとまらない）は、部品が少ない初版では起きにくいが、土台の上に構想を足し始める段でそのまま再来しうる。足す前に shaping-experience をもう一度通すこと
- 運用（環境）: 初回に OS の設定が要る。対象 OS への更新、Apple Intelligence の有効化とモデルのダウンロード、Premium 音声の手動ダウンロード、音声認識アセットのダウンロード。自分専用なので手作業で済ませる

技術スタック候補:

| 候補 | 習熟度 | 配布形態 | コスト | AI 側との相性 |
| --- | --- | --- | --- | --- |
| Swift + SwiftUI、普通の Xcode プロジェクト、ログは JSONL ファイル（**決定**） | オーナーの Swift 経験は未確認。Claude Code がビルドしながら進める前提 | Xcode から直接実行。自分専用 | 無料 | 音声認識・オンデバイス LLM・読み上げがすべて Swift の API で、橋渡しが要らない |
| Python SDK + 簡易 UI | 慣れた言語の可能性 | ローカル実行 | 無料 | LLM は呼べるが、音声認識と読み上げは Swift の API なので橋渡しが要る。「macOS アプリを作れるか」という検証目的から外れる |
| Electron / Tauri + Swift の補助プロセス | UI は TypeScript | アプリとして配れる | 無料 | 3 部品のために結局 Swift のプロセスを別に作ってつなぐことになり、継ぎ目が最も多い |

- 構造の方針（アシスタントの提案、オーナー未確認）: 音声認識・返答・読み上げの 3 部品をそれぞれ差し替え可能な境界の背後に置く。読み上げの Kokoro への差し替え、返答モデルのローカル OSS への差し替え（decisions.md）が画面側に波及しない
- AI の呼び出し設計（会話用のセッションの組み立て方、窓の作り直し、将来の判定用の別セッション）は assessing-ai-architecture で扱う。ベンダーの比較は不要（端末内のモデルと決まっている）

## 想定ユーザーの広がり

最初のユーザーはオーナー自身で、主な動機は「作ってみたい」。オーナーは OSS として無料で出せれば嬉しいと述べているが、他人にも同じ痛みがあるかは open-questions.md の「オーナー以外に同じ痛みがあるか」に残してある。今回のラウンドで新しい材料は出ていない。
