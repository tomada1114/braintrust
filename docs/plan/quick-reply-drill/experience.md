# quick-reply-drill 体験の構想

設計レベル（画面、配色、トークン）には入らない。ここで決めるのは「どんな体験を
成立させるか」と「それは現実的か」まで。

## 利用場面

- PC で、朝か夜に座って使う。1 回の長さは決めない。やる気が続く限り 1 問ずつ続け、1 日何問・何分という目標は初版では持たない。
- 始めるきっかけはトップページを開いて「開始」を押すこと。やめるタイミングはユーザーが閉じるとき。
- スマホでの隙間時間利用（通勤・待ち時間）は当初の推奨だったが、初版はローカルで動かす方針のため PC に直した（decisions.md 2026-09-15「利用場面は PC。スマホは将来」）。
- 弱い点として明記しておく。「座ってやる」は習慣になりにくく、記録のある過去アイデアもここで止まった。入力欄とタイマーは最初からスマホ幅で成立する作りにしておき、公開時にすぐスマホで使えるようにする。

## 中核の体験

開始すると架空の相手（内部でランダムに組み合わせた相手・場面・話題）から 1 行の英語の質問が出て 30 秒のカウントダウンが始まる。1〜2 文で返す。途中送信も可、時間切れなら強制送信。送信後、4 観点 × 下位項目 2 つ = 8 項目を 0〜5 で採点した結果と、観点ごとの英語のコメント、模範の返信例（自分の文を直した版、英語）が返る。合計は 100 点換算で表示し、すぐ次の質問へ進む。残るものは直近数回分の採点（ブラウザ内保存）と、ダッシュボードで直近の傾向を AI に聞いたときの全体像の文章の 2 つ。

ループ:
- 開始する
- 質問が出る（30 秒開始）
- 1〜2 文で返す（途中送信 or 強制送信）
- 8 項目の採点 + 観点ごとのコメント + 模範例を読む
- 次の質問（繰り返し）
- 好きなときにダッシュボードで直近の傾向を聞く

観点と下位項目:

| 観点 | 下位項目 |
| --- | --- |
| 伝わるか | 質問に答えているか / 意図が一読で分かるか |
| 正確さ | 文法 / スペル・句読点 |
| 語彙と自然さ | 語の選び方の的確さ / コロケーション・直訳臭のなさ |
| 場面への適切さ | 相手との関係に合うトーン・丁寧さ / チャットとしての長さと形 |

尺度: LLM は下位項目 8 つを、各段階の具体的な記述で固定した 0〜5 で採点する（根拠つき）。観点の点、100 点換算の合計、重み（最初は均等）はアプリ側で計算する。過去の採点は LLM に見せない（decisions.md「採点は過去を見せず単発」）。枠組みの出典は research/scoring-rubrics.md（TOEFL Write an Email の 0〜5、Cambridge の 0〜5、CEFR の Sociolinguistic appropriateness を参考にした）。

## 便利さの定義

ChatGPT + 手元のタイマーと比べて楽になるのは 3 つ。

- 30 秒が強制される（自分で守れない）。
- 毎回同じ 8 項目で採点されるので、直近数回と数値で比べられる。
- 質問の相手・場面・話題が内部でばらけて、自分でお題を考えなくてよい。

できなくてよいもの: 複数往復、構成の指導、日本語での説明（フィードバックは英語と決めた）、長い履歴、綺麗な画面。

正直な留保: 差分は強制力と記録だけで、採点の賢さでは ChatGPT と差がつかない。記録の比較に価値が出なければ、作る理由は 30 秒の強制だけになる。

## 最初の版で成立させる体験

含める: 上のループ全部、8 項目採点、観点ごとの英語コメント、模範返信例、次の質問の即出し、ブラウザ内保存で直近数回、ダッシュボード（直近数回の傾向を AI に聞くボタン、出力はざっくり全体像の文章）。

捨てるもの（理由つき）:
- ログイン・サーバー側 DB — 初版は採点の信頼性を試す段。
- 複数往復・構造指定・長めモード — 挫折が見える。
- 音声 — 文章の質で成否が決まる。
- 「何を返すか」のヒント — 前回ここで複雑になった。
- 全履歴との比較 — 古い成績と比べても意味が薄い。
- 単語学習機能 — 将来。
- 1 日の目標・回数制限 — まずはシンプルに。
- フィードバック言語の切替 — 初版に設定項目を増やさない。
- スマホ最適化の検証 — 公開時。
- ダッシュボードの構造化項目 — 型を決めすぎると使いにくい、とオーナー。

## 実現性

難しいところ:
- 技術: 30 秒タイマーと強制送信の確実さ（画面を離れた・通信が遅いときの扱い）。採点の待ち時間が反復のテンポを切ること（次の質問を採点中に先に作っておく、などの手はある。設計は assessing-ai-architecture）。ブラウザ内保存に採点基準のバージョンを刻んでおくこと（基準を変えたら比較できないことを記録側で分かるように）。API キーをサーバー側だけに置くこと（ブラウザに露出する環境変数の接頭辞に注意、とオーナー）。
- コンテンツ（一番重い）: 8 項目 × 6 段階 = 48 個の記述を、1〜2 文のチャット返信向けに書くこと。既存ルーブリックはメールや投稿を想定していて、そのままでは使えない（research/scoring-rubrics.md）。質問生成の相手・場面・話題の組み合わせ表を作り、難易度がばらけすぎないようにすること。模範返信例が毎回同じ調子にならないこと。
- 運用: モデルの版を固定しても、いずれ提供終了で変わり、そのとき採点の連続性が切れる。費用は自分だけが使うので小さいが、反復は無制限なので上限は把握しておく。公開するときは簡易な鍵と、将来のサブスク課金（Stripe を想定、とオーナー）が要る。

技術スタック候補と軸: オーナーが決めた（decisions.md 2026-09-15「技術スタック」参照）— Next.js、Vercel AI SDK（docs/decisions.md 2026-09-15 の前提）、UI は AI Elements、ローカル実行で API キーは .env に置きサーバー側だけで使う、保存はブラウザ内。将来は Vercel に公開。

比較した候補:
- ローカル Next.js を LAN でスマホから使う — 利用場面と矛盾。
- 初版から Supabase — 認証が付いてきてログインなしと衝突。

選定の軸は習熟度（english-vocab-app で Next.js に触れている）、配布（当面は自分だけ）、コスト（ローカルならモデル利用料のみ）、AI 側との相性（AI SDK 前提）。AI の呼び出し設計とモデル選定は assessing-ai-architecture へ。

## 想定ユーザーの広がり

オーナーが「私が一番のユーザー。まず自分の痛みを解消する」と明言（2026-09-15）。他人に当てはまるかは open-questions.md の既存エントリに残し、初版では扱わない。競合調査もオーナーの判断で行わない。
