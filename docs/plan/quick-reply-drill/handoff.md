## 何を作るか

quick-reply-drill は、英語チャットの採点機ではなく、1 行の質問に 30 秒で 1〜2 文を返す反復を、毎回同じ観点で採点して積み上げる練習装置。ブラウザで動くチャット形式のアプリで、ログインなし。ループは、開始する → 質問が出る（30 秒のカウントダウン開始）→ 1〜2 文で返す（途中送信可、時間切れなら強制送信）→ 8 項目の採点・観点ごとの英語コメント・模範返信例を読む → すぐ次の質問へ、を繰り返す。好きなときにダッシュボードのボタンを押して直近の傾向を AI に聞ける。

採点は 4 観点 × 下位項目 2 つ、計 8 項目で構成する。

| 観点 | 下位項目 |
| --- | --- |
| 伝わるか | 質問に答えているか / 意図が一読で分かるか |
| 正確さ | 文法 / スペル・句読点 |
| 語彙と自然さ | 語の選び方の的確さ / コロケーション・直訳臭のなさ |
| 場面への適切さ | 相手との関係に合うトーン・丁寧さ / チャットとしての長さと形 |

尺度: LLM は下位項目 8 つを、各段階の具体的な記述で固定した 0〜5 で採点する（根拠つき）。観点の点、100 点換算の合計、重み（最初は均等）はアプリ側のコードで計算する。過去の採点は採点する LLM に一切見せない。フィードバック（観点ごとのコメント・模範返信例）はすべて英語で、言語切替はなし。直近数回のスコアはブラウザ内保存で残す（DB なし）。ダッシュボードは押したときだけ、直近数回の採点と文を渡して全体像の文章を返すボタンを置く。

## 決まっていること

decisions.md から、実装に効くものだけを抜き出す。すべて 2026-09-15 の決定。

**体験**
- 利用場面は PC。1 回の長さ・回数は決めない。ただし入力欄とタイマーはスマホ幅で成立させておく（experience.md）。
- セッション単位は 1 問。採点は 1 問ごとに行い、次の質問を即出しする。

**採点**
- 質問は毎回 LLM 生成。相手・場面・話題の組み合わせをアプリ側で持ちランダムに引く。数問まとめて生成し、残りが少なくなったら採点中に補充する。
- 4 観点 × 2 下位項目（上表）。初版で固定し、後から変えない。
- 尺度: 下位項目 8 つを 0〜5、各段階の具体的な記述で固定。観点の点・100 点換算・重み（均等）はアプリ側。合計は 100 点換算で表示する。
- 採点は過去を一切見せず単発で行う。比較はアプリ側が数値を並べて出す。

**AI 呼び出し**
- 採点呼び出しは 1 回: スキーマの順序は 8 項目の根拠 → 点数 → 観点ごとのコメント → 模範返信例。
- 相手の返事を生成する会話呼び出しは持たない。
- ダッシュボードは押したときだけ 1 回、直近数回の採点と文を渡して全体像の文章を返す。

**モデルと設定**
- モデルは OpenAI GPT-5.6 Luna（docs/landscape/2026-09-model-intelligence.md 参照）。推論強度は 採点 = high、質問生成 = none、ダッシュボード = high。
- 用途ごとのモデル名・強度は Git 管理の設定ファイルで管理し、環境変数には置かない。API キーだけ .env に置く。

**スタックと環境**
- Next.js、Vercel AI SDK（docs/decisions.md 2026-09-15）、UI は AI Elements。
- 初版はローカル実行、保存はブラウザ内、ログインなし、DB なし。
- API キーはサーバー側のみで使う。公開接頭辞つき環境変数には置かない。当分は全体公開しない。
- 将来 Vercel 公開 + サブスク課金（Stripe 想定）に耐えられる環境変数の扱いにしておく。

**記録**
- 直近数回のスコアをブラウザ内保存する。全履歴との比較はしない。
- Cookie を使う場合は同意ボタンを置く。

**方針**
- 実装時の人手検証（採点のブレ計測、high/medium の比較など）は計画に入れない。AI に作りきらせ、使いながら気になった点を直す。

**捨てるもの**（experience.md「最初の版で成立させる体験」）
- ログイン
- サーバー側 DB
- 複数往復
- STAR 等の構造指定と長めモード
- 音声入出力
- 「何を返すか」のヒント（タネ）
- 全履歴との比較（直近数回のみ）
- 単語学習機能
- 1 日の目標・回数制限
- フィードバック言語の切替
- スマホ最適化の検証
- ダッシュボードの構造化項目

## 決まっていないこと

open-questions.md から未決のもの。実装側で決める前提のものと、使ってから
オーナーが決めるものを分けてある。

**(a) プロダクト側リポジトリで決める（実装の一部として）**
- 質問の組み合わせ表の中身（相手・場面・話題の候補）
- 8 項目 × 6 段階 = 48 個の記述（AI が下書きしてそのまま使い、気になったら直す。検証手順は計画に置かない）
- ブラウザ内保存の手段（localStorage 等）と、各記録に刻む項目（モデル別名・推論強度・採点基準バージョン）
- モデル版の固定と再現性の担保（日付つきスナップショットが無い可能性、温度が指定できない可能性 → 記述で固定した尺度 + 推論強度の固定に頼る。research/luna-api-constraints.md）
- AI SDK 実装上の注意（Zod の `.optional()` は使えず `.nullable()` を使う、強度は `providerOptions.openai.reasoningEffort`、v7 現行の API 名で書く）
- 採点の待ち時間をどう見せるか（採点中に次の質問を先に作っておく、等の手がある）

**(b) 使ってから決める（オーナー）**
- 30 秒という数字の妥当性
- 採点の推論強度を high のまま続けるか
- 4 観点の重み付け（均等のままにするか）
- PC で座ってやる習慣が続くか（続かなければ公開を早める）
- ダッシュボードの表示を構造化するか
- 「何を返したらいいか分からない（母語でも悩む）」の扱い
- 「前回と比べたコメント」を採点とは別の呼び出しで出すか
- 公開時の鍵の方式とサブスク課金（Stripe 想定）の導入時期
- 将来版の扱い（複数往復、STAR 等の構造指定つき長めモード、単語学習機能の統合、外部 DB への記録）
- オーナー以外に同じ痛みがあるか（保留。今回は扱わない）

## 制約

- コスト: 使うのはオーナーのみ。モデル利用料のみが発生する。反復は無制限なので、利用しながら上限を把握しておく。
- データ: 送るのはオーナー自身の英文。OpenAI API の入力は既定では学習に使われず、一定期間保持される（docs/landscape/2026-09-llm-apis.md）。API キーをブラウザに出さないこと。
- 技術: Vercel AI SDK は約 6 ヶ月ごとにメジャーが出て破壊的変更が入る（docs/decisions.md 2026-09-15）。現行の API 名で書き、古い snippet（`input` / `handleInputChange` / `message.content` / `system:` 等）を見分けること（docs/landscape/2026-09-chat-ui-stack.md）。モデルは日付つきスナップショットが無い可能性があるため、記録側で版を追うこと。
- 体験: 結果画面は吹き出しの続きにしない。採点・コメント・模範例は分けて見せる。合否や比較の判断はすべてアプリ側が持つ。参考: グローバル skill `building-chat-uis`（~/.claude/skills）の session-architecture。
- 採点の観点・下位項目・尺度は初版で固定し、変えるときは採点基準バージョンを上げて記録と紐づけること。
- このリポジトリには実装を置かない。
