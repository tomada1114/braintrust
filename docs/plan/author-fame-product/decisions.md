# 決定の記録

追記のみ。過去のエントリは書き換えない。新しいものを下に足していく。
決まったら open-questions.md の該当論点の状態も更新する。

## 2026-09-20 探索の前提(第 1〜2 ラウンド時点)

- 決定: 市場はグローバル(英語)。まず無料/OSS で出し、収益化は当たってから。スクショか GIF 1 枚で伝わるものに限る。既存主力ツールの置き換え(ターミナル、エディタ)、エディタ拡張、スマホアプリは対象外。
- 理由: オーナーの決定。配布網は日本語圏にしかないが、母数と指標(GitHub スター、HN)はグローバルで取る。
- 却下した案: ブラウザ拡張 — 拡張のヒットだけで作者の名が通った例が見つからず、後回しにした(`research/2026-09-devtool-demand.md`)。

## 2026-09-20 対象を開発者から Mac のパワーユーザー一般へ広げる

- 決定: 利用者を開発者に限定しない。プロダクト自体は Claude Code や AI とあえて無関係にする。
- 理由: 開発者限定だとニッチすぎるとオーナーが判断した。Raycast や Homerow のような「Mac の操作を効率化する」系を好む。
- 却下した案: 開発者向けツールに絞り続ける — 候補は `research/2026-09-devtool-demand.md` に残してあるが、優先しない。

## 2026-09-20 第 3 ラウンドの調査条件(ヒアリングの結果)

- 決定: Swift ネイティブで作る。半年級の規模もプライベート API も許容する。飽和領域(ランチャー、ウィンドウ管理、クリップボード、メニューバー管理)は、信頼喪失の隙間か明確な勝ち筋がある場合のみ狙う。日本語圏だけの痛みでも勝ち筋ならよい。
- 理由: AI コーディングエージェントを使う前提で規模の制約が緩い。飽和領域は前回ノートで確認済み。
- 却下した案: 軽量 OSS ランチャー(Raycast の信頼喪失の席) — 代替が既に複数あり、Spotlight の強化も重なって勝ち筋が見えない。

## 2026-09-20 需要データと既存事例に依存しすぎない

- 決定: 「需要がありそうだが誰も埋めていない穴」は、根拠が推測でも候補に入れる。推測と明記し、確信度を付ける。
- 理由: オーナーの指示。票数や成功事例で裏が取れるものだけに絞ると、既に埋まりつつある場所しか残らない。

## 2026-09-20 ゴールを「開発者イベントに呼ばれる知名度」から「人気のアプリを作る」へ変更

- 決定: 開発者イベントに限定しない。単純に人気のアプリを作ることをゴールにする。
- 理由: オーナーの判断。調査では、一般向け Mac アプリのスター数は作者名の認知に変換されておらず(Rectangle 30.0k★ の作者の GitHub フォロワー 1,359 など)、イベントに呼ばれることを軸にすると候補が開発者寄りに偏る。
- 却下した案: 「日本の開発者が自分ごととして使うか」を英語圏での伸びと同格に置く評価 — ゴール変更により外した。この軸での推奨(キーボードナビ、Enter 誤送信ガード、権限と署名者の監査)は調査ノートの「6. 推奨 3 つ」に残してある。人気を軸にした順位は同「7. 追補」。

## 2026-09-21 候補 4(メーカー純正ソフトの置き換え)を外す

- 決定: 候補 4 を検討対象から外す。
- 理由: オーナーの判断。プロトコル解析と機種追従が中心になり、作っていて楽しいと思えない。
- 残る候補: タスクバー型 Dock(候補 14)、Finder のコマンドパレット(候補 5)、キーボードナビ(候補 1)。

## 2026-09-21 タスクバー型 Dock(候補 14)を外し、Finder のコマンドパレット(候補 5)を保留、キーボードナビ(候補 1)を残す

- 決定: 候補 14 を外す。候補 5 は保留。候補 1 を本命の候補として残し、ほかの案と並べ直す。
- 理由: オーナーの判断。候補 14 は boringBar の機能の厚みに勝てる気がしないうえ、オーナーはブラウザのタブ中心で複数ウィンドウを使わないため、自分で欲しいと思えない。候補 5 は技術より便利さの中身(どういうキーワードで何を呼ぶか、英語か日本語か)が詰め切れず、オーナー自身も Finder をあまり使わない。Homerow のようなキーボードナビを自分で実現することには関心がある。
- 評価軸の追加: 「オーナー自身が欲しいか」を、人気の天井と並ぶ軸として扱う。
