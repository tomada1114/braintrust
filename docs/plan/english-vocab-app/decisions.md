## 第 1 部: 語彙データとスキーマについての決定（旧 english-vocab-list）
## 2026-09-07 製品の軸は目的別を主、CEFR レベルを従とする

- 決定: 入口は「IELTS 用」「TOEIC 用」のような目的で切る。CEFR レベルは絞り込みや並べ替えに使う従属的な軸として持つ。目的とレベルのマッピングは、準備段階で LLM の判断に委ねる。
- 理由: 学習者の動機は目的に紐づいており、「B1 レベル」では何のために使うかが伝わらない。日本の学習者に CEFR の実感が薄いことも効いている。
- 却下した案: CEFR レベルを主軸にする — データは最も素直で A1〜C2 が約 9,900 語そのまま使えるが、なぜ使うかがユーザーに伝わらない。
- 却下した案: 軸を決めずにデータだけ統合して先に進む — 後戻りはしないが、体験の設計が始められない。

## 2026-09-07 最初に掘るのは IELTS 用とする

- 決定: 3 つの初期案（IELTS 用 / TOEIC 用 / はじめての人と仲良くなるための語彙）のうち、IELTS 用を最初の一本にする。IELTS のバンドと語彙のレベル対応は LLM に作らせる。
- 理由: 市場が大きく学習者の動機が強い。公式リストが存在しない点はどの案でも同じ条件になる。
- 却下した案: はじめての人と仲良くなるための語彙 — 既存リストが埋めていない唯一の領域で差別化の余地は大きいが、収録すべき語の定義がゼロからになる。
- 却下した案: TOEIC 用 — TSL 1,250 語という既製の答えがあり最も早く形になるが、日本で最も競合が濃く mikan や abceed と正面衝突する。
- 却下した案: 競合調査をしてから決める — 判断の精度は上がるが、この段階では時間がかかりすぎる。

## 2026-09-07 語彙リストは LLM 生成のみで完結させ、既存の公開リストは一切使わない

- 決定: 配布する語彙データは LLM の知識から生成したものだけで構成する。CEFR-J・NGSL ファミリー・Octanove などの既存公開リストは、配布物にも検証用の物差しにも使わない。根拠のなさは「あくまで目安・参考」として明示する。
- 理由: 外部データセットへの依存を避けたい。ライセンス表示義務・ShareAlike・出典管理といった運用コストが一切発生しない状態を優先する。
- 却下した案: 既存リストを配布物に同梱する — 無料かつ商用可だが、CC BY-SA の ShareAlike と CEFR-J の引用義務がついてくる。
- 却下した案: 既存リストを配布しない検証用の物差しとして手元に置く（メインセッションの推奨だった） — ShareAlike も帰属表示も配布時にしか発動しないため義務はゼロで、「TSL の何 % をカバー」といった品質指標が出せる利点があった。オーナーは依存を完全に断つことを優先して却下。
- 補足（オーナーが認識した上で受け入れたリスク）: 生成物は「なぜこの語が入っているか」を外部の基準で説明できない。生成のたびに内容が変わるため回帰テストが書けない。免責文は期待値を下げるが品質は上げない。

## 2026-09-07 IELTS アプリを先に作り、語彙ライブラリは後から切り出す

- 決定: 語彙データはまず IELTS アプリの中に持つ。必要なフィールドと粒度が固まった段階で、npm / pnpm で配布する TypeScript ライブラリとして切り出す。
- 理由: アプリが 1 本もない状態で複数アプリ向けの API とスキーマを決めるのは早すぎる抽象化になる。語彙データに何が必要かはアプリを作ってみないと分からない。
- 却下した案: ライブラリを先に作る — データ層が最初から独立するが、利用者不在でスキーマを決めることになる。

## 2026-09-07 次の一手はオーナーへのヒアリング、その後に競合・市場調査

- 決定: まず IELTS の単語学習でオーナー自身が何に困ったかを聞き取り、overview.md を起こす。その後で競合調査と市場調査を行う。競合アプリの実操作までは行わない。
- 理由: 一人称の痛みが最も早く、かつ最も強い出発点になる。調査はその裏付けに使う。
- 却下した案: 先に競合調査から入る — 根拠は強くなるが、何を探すべきかが定まらないまま調査コストを払うことになる。

## 2026-09-07 訂正: 主題は語彙リストのライブラリ。IELTS アプリ関連の 3 件は仮定への回答であり決定ではない

- 決定: このアイデアの主題は「レベル情報を持つ語彙リストを npm / pnpm のライブラリとして作る」ことである。上の 2026-09-07 のうち「最初に掘るのは IELTS 用とする」「IELTS アプリを先に作り、語彙ライブラリは後から切り出す」「次の一手はオーナーへのヒアリング、その後に競合・市場調査」の 3 件は決定として扱わない。
- 理由: オーナーの訂正（原文）「最初はライブラリとして語彙リスト(レベル感とかをもつ)だけ作ろうと思っていたが、IELTS英単語アプリを作るなら？という会話に途中で移っていったので、その答えとして回答しました」。アシスタントが「3 つの初期案のうちどれを最初に掘るか」と問うた時点でアプリ前提に会話を寄せており、オーナーはその仮定に答えていた。
- 有効なまま残る決定: 「製品の軸は目的別を主、CEFR レベルを従とする」と「語彙リストは LLM 生成のみで完結させ、既存の公開リストは一切使わない」。どちらもライブラリの設計に直接効くため維持する。
- 残るもの: IELTS 学習者としてのヒアリング結果（`overview.md` に記録）は、ライブラリが誰の何に使われるかの要件入力として有効。ただし overview.md は現在アプリを主語に書かれており、書き直しが要る。
- 注: 追記のみの原則により過去のエントリは書き換えていない。上記 3 件を読むときは必ずこのエントリと併せて読むこと。

## 2026-09-07 語の同一性のキーは「見出し語 + 品詞」とする

- 決定: 語彙データの主キーを (headword, pos) にする。同じ見出し語でも品詞が違えば別レコードとし、レベルも品詞ごとに付ける。語義（sense）では分けない。
- 理由: CEFR-J が 7,801 行の実運用でこの粒度を採っており、手元でパースして確認したところ 6,868 のユニーク見出し語のうち 848 が品詞違いで複数行に分かれていた（`research/vocab-data-schemas.md` のメインセッション確認節）。`fine` は形容詞 A1 / 名詞 B1 / 副詞 B2 / 動詞 B2 と品詞でレベルが割れるため、見出し語だけをキーにすると正しいレベルを付けられない。
- 却下した案: 見出し語だけをキーにする — 最も単純でデータ量も小さいが、`fine` を A1 と B2 のどちらに置くか決められず、レベル付与の精度が落ちる。
- 却下した案: 語義単位（WordNet 方式） — `bank` の「銀行」と「土手」を分けられて最も正確だが、生成量が数倍になる。外部の物差しを持たないと決めた以上、その量の品質を担保する手段がない。
- 承知した上での割り切り: `bank` の「銀行」と「土手」は同じ名詞レコードに畳み込まれる。CEFR-J も同じ割り切りをしている。

## 2026-09-07 目的は語のレコードに属性として持たせる

- 決定: 1 語 1 レコードを保ち、目的（IELTS / TOEIC / 日常会話など）は語のレコード上の属性として持つ。目標スコアを持つ目的については、その目標値をオブジェクトで持つ。目的ごとに独立したリストのファイルを作らない。
- 理由: 重複が構造的に起きない。将来「目標スコア」という第 3 の軸を足すときも、属性の形を変えるだけで済む（`decisions.md` 第 2 部 2026-09-07 の方向づけ）。npm で配布する静的データとして結合が不要で最も素直。
- 却下した案: NGSL 式の排他階層（コアリスト + 目的別の差分リスト） — 学習順序が自明になる利点があり、NGSL プロジェクトが実際に採用している設計だが、目的別リストが単体で完結せず常にコアとの合成が要る。
- 却下した案: 語マスタ + 所属関係に正規化 — 目的ごとの順位や重みを持てるが、公開データセットに確立した実例が見つからず、同梱 JSON としては結合が必要で重くなる。
- 材料: `research/vocab-data-schemas.md`

## 第 2 部: アプリの体験についての決定（旧 ielts-vocab-app）
## 2026-09-07 IELTS 英単語アプリを独立したアイデアとして切り出す

- 決定: `english-vocab-list`（語彙リストのライブラリ）の検討中に派生した IELTS 英単語アプリの構想を、独立したアイデアとして分ける。ライブラリとアプリを並行して持つ。
- 理由: オーナーの当初からの計画はライブラリ単体を作ることであり、アプリの話はアシスタントが会話を寄せた結果として出てきた。同じディレクトリに混ぜると、どちらの決定なのかが読めなくなる。
- 引き継ぎ: `english-vocab-list/decisions.md` の 2026-09-07 のエントリ群、特に訂正エントリを併せて読むこと。ヒアリング結果は本ディレクトリの `overview.md` にある。
- 却下した案: このディレクトリを作らず、アプリの話を捨てる — 最も軽いが、ヒアリングと競合調査 8 製品分の成果を失う。
- 却下した案: ライブラリのディレクトリに同居させたまま進める — 分ける手間はないが、主題が二重になる。

## 2026-09-07 直近は IELTS 特化アプリ。将来は目標設定型の統合アプリに拡張しうる（方向づけ）

- 決定: 直近に作るのは IELTS 特化の英単語アプリとする。将来、アカウント設定で目標（IELTS 7.0、TOEIC 800 など）を設定し、それに応じた語彙学習を出す 1 つの統合アプリへ拡張する道を、あり得る展開として想定しておく。
- 理由: オーナーの言葉「たとえば一つの巨大な英単語アプリというのを作り、アカウント設定として目標としてたとえばIELTS7.0、とかTOEIC800とか、そういうのを設定し、それに適切な単語学習をできるように、といった場面があるかもしれない。直近は一旦IETLS特化のアプリを作って、そこから拡張などがあり得ると思ってる」。
- 位置づけ: 統合アプリ側は「あり得る展開」であって決定ではない。IELTS 特化アプリを作ることだけが直近の方向づけ。
- 設計への影響: 目標スコアを軸にすると、CEFR レベルでも目的別リストでもない第 3 の軸（目標スコア）が要る。IELTS 7.0 や TOEIC 800 と語彙の対応には公式の根拠が存在しないため（`research/wordlists-exams.md`）、この対応表は完全に自作の主張になる。`english-vocab-list` のスキーマは、この 3 軸目を後から足せる形にしておく必要がある。

## 2026-09-07 書いた文への返しは LLM の添削と講評とする

- 決定: ユーザーが書いた文に対して、LLM が添削と講評を返す。模範解答を見せるだけで済ませない。
- 理由: 自分の文に対する返しがなければ産出練習は成立しない。既存 8 製品がここをやっていないことは競合調査で確認済み（`research/competitors/_comparison.md`）。
- 却下した案: 模範解答を見せるだけで LLM を使わない — 安くて速いが、自分の文のどこが悪いか分からない。
- 却下した案: 選んだ語がその場面で自然かだけを返す — 応答が短く安いが、文全体の質に踏み込めない。
- 残る論点: コストと応答時間、モデル選定、出力形式の安定。`open-questions.md` に追加する。

## 2026-09-07 次は IELTS アプリの体験を先に詰める

- 決定: `english-vocab-list` の収録範囲とフィールドより先に、IELTS アプリの体験を詰める。
- 理由: 体験が決まらないとライブラリが持つべきフィールドが決まらない。候補語群を出す設計なら、語に類義関係や場面タグが要ると分かる。
- 却下した案: ライブラリの収録範囲とフィールドを先に決める — データから埋められるが、使われ方が未確定のままフィールドを決めることになる。

## 2026-09-07 語彙データはアプリ内に持つ。ライブラリ化は必要が生じてから

- 決定: 当面は IELTS 専門のアプリだけを考える。語彙データはアプリの中に持つ。他アプリでこの単語データを使いたくなった時点で、はじめてライブラリとして切り出す。将来 TOEFL など他の目的に対応する余地は残す。
- 理由: オーナーの言葉「とりあえず、一旦IELTS専門(将来はTOEFLなど他目的も対応)のアプリだけ考えよう。そしてデータはもち、そこから他アプリに単語データを活用したい、となったらはじめてライブラリ化しよう」。利用者が 1 アプリしかない段階でライブラリを切り出す理由がない。
- 引き継ぐもの: `decisions.md` 第 1 部 の 4 件はアプリ内データの設計としてそのまま有効。
  - 語の同一性のキーは「見出し語 + 品詞」
  - 目的は語のレコードに属性として持たせる（将来の TOEFL 対応と目標スコア軸はこの属性で表す）
  - 語彙リストは LLM 生成のみで完結させ、既存の公開リストは一切使わない
  - 製品の軸は目的別を主、CEFR レベルを従とする
- 却下した案: 先にライブラリを作る — データとアプリが最初から分離するが、利用者不在でスキーマと API を決めることになる。
- 影響: `../english-vocab-list` は保留にする。再開の条件はそちらの `open-questions.md` に書く。

## 2026-09-07 出題は「候補語群から選ぶ → 即時に正誤 → 確定した語で自分の文を書く」

- 決定: 場面と候補語群を提示し、ユーザーが語を選んだ瞬間に正誤を返す。正誤が確定してから、その語を使って自分の文を書かせる。選択と執筆を分ける。
- 理由: オーナーの指摘「仮に正解がひとつだったとしても、その選択肢で合っているかどうか不安になりながら文を書かせるのは心理負荷が高い」。選択の不安を執筆に持ち越さないため、正誤を先に確定させる。即時フィードバックは英語学習アプリでありふれた作りであり、独自性はないが確実に効く。オーナーからは「独自性だけで考えない方がいい」という釘も刺されている。
- 却下した案: 正解を一つにせず、候補すべてを使える語にする — 心理負荷はゼロになるが、「場面に合う語を選ぶ」訓練が消える。オーナーの痛みが「語が出てこない」である以上、その部分は練習の対象から外せない。
- 却下した案: 選択をやめて語を 1 つ与えて書かせる — 最も負荷が低いが、想起の練習がすべて復習側に寄る。
- 却下した案: 場面だけ渡して自由に書かせる — オーナーが明確に辛いと述べた形。

## 2026-09-07 復習は手がかりを弱めながら間隔も開ける

- 決定: 一度書いた語を再び出すとき、手がかりを一段階弱め、かつ出題の間隔も開ける。両方を併用する。手がかりの段階は「候補語群あり → 意味のヒントだけ → 場面だけ」の 3 段階とする。
- 理由: オーナーの要望「学習曲線的なのもなんか取り入れられるといいかもね」に、手がかりの段階が直接応える。間隔反復は定着に実績がある。両方を併用すると、同じ語を何度も見せるのではなく毎回少しずつ難しくなるので、オーナーが辛いと述べた「詰め込み感」を薄められる。
- 却下した案: 手がかりを弱めるだけ — 仕組みが 1 つで軽いが、定着の間隔が制御できない。
- 却下した案: 間隔反復だけ — 実績はあるが、Anki / iKnow! と同じになり、オーナーが辛いと述べた反復そのものの体験に近づく。
- 残る論点: 2 つの仕組みを同時に入れると最初の版が重くなる。段階の上げ下げの条件と間隔の決め方は未決。

## 2026-09-07 進捗は語ごとの手がかり段階の積み上げで見せる

- 決定: 進捗を「覚えた語数」ではなく「どの手がかり段階で使えたか」の積み上げで見せる。たとえば候補ありで使えた語、ヒントだけで使えた語、場面だけで使えた語をそれぞれ数える。
- 理由: オーナーが書籍をやめた理由が「進捗の実感がわかないし、達成感もない」だったため、進捗の可視化は捨てられない。語数だけを数えると mikan と同じ「単語と意味だけ」の指標になる。手がかり段階で数えれば、使える深さが伸びていることが見える。復習の設計とも同じ軸で揃う。
- 却下した案: 書いた文を蓄積して見返せるようにする — 成果物が残る達成感は強いが、伸びているかどうかは分からない。後から足せる。
- 却下した案: ストリークやポイント — 継続には効くが、学習の中身と無関係な数字になる。

## 第 3 部: 統合後の決定

## 2026-09-07 アイデアを 1 つに統合する。目的別の英単語アプリで、最初の版だけ IELTS に限定する

- 決定: 「語彙リストのライブラリ」と「IELTS アプリ」を分けず、1 つのアイデアとして `english-vocab-app` にまとめる。プロダクトは IELTS 専用ではなく目的別の英単語アプリとし、**最初の版だけ、お試しとして IELTS に限定する**。語彙データはライブラリにせずアプリに同梱する。ただし**将来ライブラリとして切り出せる設計にしておく**。
- 理由: オーナーの言葉「やっぱさ、ieltsに限定しない、でも最初だけはお試しのためieltsに限定する、そして語彙のリストもライブラリではなくまずは同梱する。しかし将来的にライブラリ化も考慮した設計にする。planの中のフォルダはわけなくて済むはず」。ディレクトリを分けたことで、同じ日の決定が 2 ファイルに散り、どちらの話か読めなくなっていた。
- 無効になる過去の決定:
  - 第 2 部「IELTS 英単語アプリを独立したアイデアとして切り出す」 — 統合により無効。
  - 第 1 部の訂正エントリが「主題はライブラリ」としていた点 — 主題はアプリであり、語彙データはその一部。

## 2026-09-10 カードの形: 表は英語の意味説明と穴埋め例文を常に両方、裏は語と短い例文

- 却下した案: 表は意味説明だけで、穴埋め文はヒントとして後から開く — 思い出す負荷は高いが、意味説明だけの段階で類義語に答えが割れる。
- 却下した案: 穴埋め文を主にし、意味説明は補助にする — 文脈重視には最も合うが、意味説明の出番が薄れる。
- 影響: `open-questions.md` の「場面に合う語は 1 つに定まるか」は、「表面から答えが一意に決まるか」という形でカード単位の品質の問題に変わる。

## 2026-09-10 答え合わせはめくって自己採点。復習の間隔は Anki と同じ考え方にする

- 決定: 表面を見て頭の中で答え、裏をめくって記憶の度合いを自分で選ぶ。その選択に応じて次の出題間隔を決める。ロジックは Anki と同じでよい。
- 理由: オーナーの言葉「自分で記憶度合いを選んで復習に役立てる。一旦、Ankiと同じロジックでいいぐらい」。実行時に AI を使わない前提で最も単純で、穴埋めに入る語形の揺れ（improve / improved）の問題も起きない。
- 却下した案: 入力して完全一致で判定する — つづりまで思い出す練習になるが、変化形を許すリストを持つか、例文の空欄を原形に限る制約が要る。
- 却下した案: 入力してから自己採点 — 語形の問題は起きないが、操作が一番多い。
- 残る論点: Anki の SM-2 と FSRS のどちらに合わせるか。

## 2026-09-10 意味説明の語彙レベル（A1〜A2、上限 B1）は生成時の目安にとどめ、機械では確かめない

## 2026-09-10 カードの項目は、表 = 英語の意味説明 + 穴埋め例文、裏 = 語 + 例文 2 本。日本語は持たない

- 決定: 表面に英語の意味説明と穴埋め例文を載せる。裏面に語と、その語を使った例文を 2 本載せる。日本語訳はカードに持たせない。

- 却下した案: Vocabulary デッキと同じく、裏面に短い日本語訳も持つ（メインセッションの推奨だった） — 意味の取り違えに答え合わせの最後で気づける。オーナーは日本語を持たない形を選んだ。
- 却下した案: 例文 1 本・日本語なし — 最初に述べた形で最も軽いが、別の場面での使い方が 1 通りしか見えない。
- 承知した上での割り切り: 意味を取り違えて覚えていても、カードの中にはそれを確かめる手段がない。

## 2026-09-10 Lint は語数・文字数に加え、判断の要らない形のチェックまで含める

- 決定: Lint で次を弾く。各項目の語数・文字数の上限、答えの漏れ（表面に答えの語やその変化形が出ている）、裏面の例文が答えの語を使っていない、例文が穴埋め文の空欄を埋めただけの焼き直し、穴埋め文に空欄マーカーがない。答えが一意に決まるか・例文が自然かといった判断の要る点は、点検用の Skill に任せる。
- 理由: どれも文字列の照合で判定でき、`tomada-routine` の `.claude/skills/anki-vocabulary/scripts/validate_phrase_cards.py` に実装がある。同リポジトリの `English/payloads/2026/09/phrase-jobposting-20260907-001.json` では、AI が生成した 6 枚のうち 5 枚で、裏面の例文に答えの語が一度も出ていなかった（`oversee` の例文が "She watches over …" など）。
- 却下した案: 語数と文字数だけ（オーナーが最初に述べた形） — Lint は最小になるが、機械で確実に止められる誤りを LLM の点検に頼ることになり、見落としがありうる。

## 2026-09-10 復習間隔のロジックは FSRS に合わせる

- 決定: Anki の新しいスケジューラである FSRS と同じ考え方で、復習の間隔を決める。評価は Again / Hard / Good / Easy の 4 段階の自己申告とする。
- 理由: 同じ定着率を少ない復習回数で出せる。公開ライブラリを使えば、自分で書く量は SM-2 より少ない。事実関係は `research/spaced-repetition-fsrs.md` で確認する。
- 却下した案: SM-2（従来の Anki） — 数十行で書け、挙動を説明しやすいが、間隔の伸び方が単純で、難しい語が何度も出続けやすい。
- 却下した案: 独自の簡易版（決まった日数で進める） — 最も軽いが、「Anki と同じ」から離れる。

## 2026-09-10 自前アプリで Anki に足すもの: 見た目と操作、目的・トピック別の絞り込み、進捗と達成感

- 決定: 自前アプリにする理由、すなわち最初の版で必ず作る部分は次の 3 つ。Anki の見た目と操作を自分好みにすること、目的・トピック別に出題範囲を絞り込めること、進捗と達成感を自分好みに見せること。
- 理由: オーナーの言葉「あくまでIELTS、TOEFLなど、いろんな目的別に使えるようにしたいってわけ。なお、将来的には海外生活で病院いくとき〜とかそういうトピックで学ぶとかもしたい。とにかくボキャブラリーを増やしたいのよ」。
- 却下した案: 生成から学習までの一本化（Anki への投入や note_id 管理の手間をなくす）を理由に含める — オーナーは選ばなかった。
- 位置づけ: 目的（IELTS / TOEFL など）に加えて、生活場面のトピック（海外生活で病院に行く、など）も将来の学習単位になる。第 1 部の「目的は語のレコードに属性として持たせる」は維持し、トピックの持ち方は `open-questions.md` に置く。最初の版を IELTS に限る決定（第 3 部）は変えていない。
- 注: 狙いの重心は「覚えた語を自分の文で使える」から「語彙を増やす」へ移っている。ただしカードは意味から語を思い出す向きなので、語を引き出す練習であることは変わらない。

## 2026-09-10 目的は語の属性として複数持てる。トピックは固定の一覧から選ぶ複数タグにする

- 決定: 1 語に目的（IELTS / TOEFL など）を複数付けられる。トピック（environment、health、hospital など）も複数付けられるタグとし、名前は固定の一覧から選ぶ。
- 理由: オーナーの言葉「目的は属性、トピックは複数タグやね。でも目的は複数もあるだろう」。`symptom` のような語は IELTS の Health にも、海外生活の病院にも属する。同じ語のカードを二重に持たずに済む。第 1 部「目的は語のレコードに属性として持たせる」とも整合する。
- 却下した案: 目的 > トピックの階層で 1 語 1 所属 — 最も分かりやすいが、複数にまたがる語を二重に持つか、どちらかに寄せることになる。
- 却下した案: 自由タグ — 柔軟だが、表記が揺れて絞り込みと集計が崩れる。
- 残る論点: 目的ごとのレベル（目標スコア）を語にどう持たせるか。`open-questions.md` に置く。

## 2026-09-10 生成 Skill は IELTS のトピック単位と目標スコア単位の両方で回す（方向づけ）

- 決定: 生成 Skill を回す単位として、IELTS のトピック（Environment など）で切る回し方と、目標スコア（IELTS 7.0 向けなど）で切る回し方の両方を持つ。
- 理由: オーナーの言葉「IELTSのトピックで切るし、目標スコア基準でも回したいよねえ」。
- 位置づけ: 方向づけ。目標スコアで切る回し方は、レベルの持ち方（未決）が決まるまで具体化できない。最初に回す量も未決。

## 2026-09-10 進捗と達成感の見せ方は、別のセッションで決める

- 決定: 進捗と達成感の作り込みは、このセッションでは決めない。別のセッションで扱う。このセッションの最後に、そのセッションに渡す依頼プロンプトを `/refining-prompts` で作る。
- 理由: オーナーの言葉「進捗と達成感といった作り込みは、別セッションで決める。最後に /refining-promptsで依頼プロンプト見せて。ここは賢いモデルの力が必要だ」。
- 却下した案: なし。このセッションで出した 3 案（トピック別の定着状態を軸にする〔メインセッションの推奨〕、学習量の記録、両方）は却下ではなく、別のセッションへの持ち越し材料とする。

## 2026-09-10 アプリは nextjs-app-template から切り出して作る

- 決定: アプリは `~/ghq/github.com/tomada1114/nextjs-app-template` を元に作る。ローカルで localhost に立ててブラウザで使う。
- 理由: オーナーの言葉「~/ghq/github.com/tomada1114/nextjs-app-templateから切る予定」。テンプレートは Next.js 16（App Router）・TypeScript・pnpm・next-intl・zod という構成。LLM 呼び出しの層は丸ごと外せる設計になっており、「アプリに AI を組み込まない」決定と合う（2026-09-10 時点の同リポジトリ README で確認）。
- 却下した案: デスクトップアプリ（Tauri など） — アプリらしく起動できるが、ビルドと配布の手間が増え、後で Web に出すときに作り直しに近くなる。
- 却下した案: スマホで使う — 隙間時間に使えるが、「ローカルで動かす」と衝突する。
- 残る論点: テンプレートにデータベースはない。カードデータ（生成物）と復習履歴をどこに置くかは `open-questions.md` に置く。

## 2026-09-10 カードデータは JSON ファイルで git 管理し、復習履歴はローカルの SQLite に置く

- 決定: 生成したカードは JSON ファイルとしてリポジトリで git 管理し、Lint もファイルに対して回す。復習履歴と FSRS の状態は、ローカルの SQLite に置く。
- 理由: 生成・修正の差分が git で読める。履歴は SQLite なら進捗の集計が書きやすく、ファイル 1 つでバックアップできる。デプロイするときは、履歴の置き場だけを差し替えればよい。
- 却下した案: 履歴をブラウザ内（IndexedDB）に置く — サーバー側に保存の仕組みが要らないが、ブラウザのデータを消すと履歴も消え、バックアップしにくい。
- 却下した案: 履歴も JSON ファイルにする — 最も単純だが、履歴が増えると重くなり、書き込みの途中で落ちると壊れやすい。

## 2026-09-10 生成 Skill の最初の 1 回は、IELTS の 2〜3 トピック × 各 30 語前後とする

- 決定: 最初に生成 Skill を回す範囲は、IELTS のトピック 2〜3 個、各 30 語前後（合計 60〜90 枚）とする。
- 理由: トピックでの絞り込みが意味を持ち、生成 → Lint → 点検の流れとカードの質を、全部自分で目を通して確かめられる量。
- 却下した案: 1 トピック 20 語で試作 — カードの質は最速で確かめられるが、絞り込みの手応えは試せない。
- 却下した案: 決めずに、プロダクト側のリポジトリで決める — 先送りする理由がない。
- 残る論点: どのトピックを選ぶか。

## 2026-09-10 語のレベルは CEFR 6 段階で 1 つだけ持ち、目標スコアは試験ごとの換算表で CEFR に変換する。出題は目標の段階と 1 つ下

- 決定: 1 語に CEFR のレベル（A1〜C2）を 1 つだけ持たせる。目標スコア（IELTS 7.0 など）は、試験ごとに 1 つ持つ換算表で CEFR に変換する。目標を選んだときは、目的が一致し、レベルが目標の段階かその 1 つ下の語を出す（IELTS 7.0 → C1 なら B2〜C1）。生成 Skill を「目標スコアで回す」ときも、同じ換算で「その目的のトピックで、目標の CEFR の語」と読み替える。
- 理由: 精度は要らないとオーナーが明言している（「正直、そんな正確じゃないてもよいかと」）。そうなると効くのは、生成のたびに同じ語の値が揺れないことになる。LLM にとって、語ごとの CEFR レベルは広く流通した概念である。一方、語と試験スコアの対応は試験の実施団体を含めて誰も作っておらず、特に 0.5 刻みの値は語の単位ではノイズになる。目標の 1 つ下まで出すのは、目標より下の段階にも抜けがあるため。換算の粗さ（例: IELTS 6.0 と 6.5 が同じ段階になる）は、オーナーが許容済み（「対応表がCEFRとかは荒いのは問題ないっす」）。
- 却下した案: 試験ごとにスコアを持つ（ielts: 7.0 など） — 生成も画面も直接的で、試験を足すたびに全語へ値を追加する手間はオーナーが許容していた（「試験の数には限りもあるから、全部に対応表を載せたり、再生成（というか追加）するのはしゃーない」）。しかし語ごとの点数は生成のたびに揺れやすい。
- 却下した案: CEFR と試験スコアの両方を持つ — 最も柔軟だが、値が食い違ったときにどちらを信じるかが決まらない。
- 却下した案: CEFR に中間段階（B1+ など）を足す — 少し細かく分けられるが、粗さが問題にならない以上は過剰で、生成時の揺れも増える。
- 却下した案: 出題は目標の段階だけ — 狙いは最も明確だが、1 つ下の段階の抜けに気づけない。
- 却下した案: 出題は目標までの全段階 — 漏れはないが、簡単な語が大半を占めて詰め込み感が出る。
- 前提の確認: 試験の実施団体がスコアと CEFR の対応表を公表しているかは、`research/exam-cefr-mapping.md` で確認中。公表されていなければ、換算表も自称で作る（レベルは自称でよいという 2026-09-10 の決定の範囲内）。
- 影響: `open-questions.md` の「IELTS のバンドと語彙の対応をどう作り、どう名乗るか」は解決する。第 1 部の「製品の軸は目的別を主、CEFR レベルを従とする」とも整合する。
