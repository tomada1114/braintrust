## カードの品質・生成の仕組み

### 表面から答えが一意に決まるかを点検 Skill でどう担保するか

- 何が決まれば決まるか: 意味説明 + 穴埋め例文という表面の形は決まったが、類義語
  （improve / enhance / boost など）が並ぶ場合に答えが本当に 1 つに絞れるかは
  カードごとに違う。機械的な Lint では判定できないため、点検用 Skill がどう
  一意性を確かめるかを決める必要がある
- 材料: `decisions.md` 第 4 部 2026-09-10「カードの形: 表は英語の意味説明と穴埋め
  例文を常に両方、裏は語と短い例文」の影響ノート（旧「場面に合う語は 1 つに定まるか」
  からの引き継ぎ）
- 状態: 未決

### 生成 Skill と点検 Skill の設計（入力単位・重複排除・再生成時の既存カードの扱い）

- 何が決まれば決まるか: 生成 Skill をどの単位（トピック単位、目標スコア単位など）で
  回すか、生成済みの語と重複しないようにどう排除するか、点検 Skill が修正を入れた
  ときに既存カードをどう扱うか（上書きか、別バージョンとして残すか）
- 材料: `decisions.md` 第 4 部 2026-09-10「カードデータは生成用の Skill を回して
  足りない範囲を埋め、生成後に点検・修正用の Skill を通す」「生成 Skill は IELTS の
  トピック単位と目標スコア単位の両方で回す（方向づけ）」
- 状態: 未決

### Lint の閾値の値

- 何が決まれば決まるか: 語数・文字数の上限など、Lint が弾く具体的な数値
- 材料: `decisions.md` 第 4 部 2026-09-10「Lint は語数・文字数に加え、判断の要らない
  形のチェックまで含める」。チェックする項目は決まったが、閾値そのものは未定。
  `tomada-routine` の `validate_phrase_cards.py` が値の参考になりうる
- 状態: 未決

### 熟語・フレーズを将来入れるときの同一性キー（見出し語 + 品詞のままでよいか）

- 何が決まれば決まるか: 語の同一性キーは「見出し語 + 品詞」と決めている。熟語や
  フレーズ（句動詞、コロケーションなど）を将来扱うとき、同じキーで足りるか、
  別のキー（フレーズ全体を主キーにするなど）が要るか
- 材料: `decisions.md` 第 1 部 2026-09-07「語の同一性のキーは『見出し語 + 品詞』と
  する」、第 4 部 2026-09-10「カードの形: 表は英語の意味説明と穴埋め例文を常に
  両方、裏は語と短い例文」（将来は語だけでなく熟語やフレーズも扱う、という言及）
- 状態: 未決

## 語彙データ

### トピックの固定一覧をどう作るか・最初の 2〜3 トピックをどれにするか

- 何が決まれば決まるか: トピックは固定一覧から選ぶ複数タグにすると決まったが、
  一覧の中身そのものと、最初に生成 Skill を回す 2〜3 トピックの選定はまだない
- 材料: `decisions.md` 第 4 部 2026-09-10「目的は語の属性として複数持てる。トピック
  は固定の一覧から選ぶ複数タグにする」「生成 Skill の最初の 1 回は、IELTS の 2〜3
  トピック × 各 30 語前後とする」（末尾に「残る論点: どのトピックを選ぶか」と明記）
- 状態: 未決

### 換算表の出典（試験スコアと CEFR の対応）

- 何が決まれば決まるか: 試験の実施団体がスコアと CEFR の対応表を公表しているか。
  公表されていなければ、換算表も自称で作ることになる
- 材料: `research/exam-cefr-mapping.md`。`decisions.md` 第 4 部
  2026-09-10「語のレベルは CEFR 6 段階で 1 つだけ持ち、目標スコアは試験ごとの
  換算表で CEFR に変換する。出題は目標の段階と 1 つ下」の前提確認として位置づく
- 状態: 解決済み（2026-09-10）。IELTS・TOEFL iBT・TOEIC・英検・Cambridge English Scale の
  いずれも、実施団体が公式の対応表を公表している。IELTS の公式ページはメインセッションが
  直接確認した（C1 の下限は 6.5 と 7.0 の間）。換算表は公式の対応表から作れる。
  ただし、どの対応表も受験者の能力の尺度であり、語ごとの難しさには触れていない。
  語ごとの CEFR レベルが自称であることは変わらない

### 将来のライブラリ化に備えて、どこまで分離しておくか

- 何が決まれば決まるか: カードデータをアプリのロジックからどこまで切り離しておくか。
  2026-09-10 の方針転換ではこの点に触れておらず、決定は撤回されていない
- 材料: `decisions.md` 第 3 部 2026-09-07「アイデアを 1 つに統合する」。切り出しが
  必要になるのは、他のアプリでこのデータを使いたくなったとき
- 状態: 未決（個人用アプリとしての優先度は下がっている可能性があるが、明示的な
  判断はしていない）

### FSRS のオプティマイザをいつ使うか

- 何が決まれば決まるか: FSRS はレビュー履歴から自分のパラメータを最適化できるが、
  最適化にはある程度の復習件数が要る。最初はデフォルトパラメータで始め、
  どの時点でオプティマイザに切り替えるか
- 材料: `decisions.md` 第 4 部 2026-09-10「復習間隔のロジックは FSRS に合わせる」、
  `research/spaced-repetition-fsrs.md`
- 状態: 未決

## 前提の検証

### そもそも作るか（Anki の Vocabulary デッキで足りないか）

- 何が決まれば決まるか: 自前アプリを作る理由は、見た目と操作、目的・トピック別の
  絞り込み、進捗と達成感の 3 つに絞られている。この 3 つが実際に使われず、なくても
  困らないと分かれば、Anki の Vocabulary デッキのまま続けるという選択肢が正しくなる。
  オーナーは自前アプリを作ると既に決めているが、その前提（3 つが本当に効くか）は
  作ってみるまで検証されていない
- 材料: `decisions.md` 第 4 部 2026-09-10「オーナー自身がローカルで動かす自前アプリに
  する」「自前アプリで Anki に足すもの: 見た目と操作、目的・トピック別の絞り込み、
  進捗と達成感」
- 状態: 保留（作る方向は決定済みだが、前提の検証は未了）
