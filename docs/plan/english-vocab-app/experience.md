# english-vocab-app 体験の構想

設計レベル（画面、配色、トークン）には入らない。ここで決めるのは「どんな体験を
成立させるか」と「それは現実的か」まで。

2026-09-10 のセッションで、体験の骨格が「場面と候補語群から選んで自分の文を書く」
から「意味説明と穴埋め例文を見て語を思い出し、めくって自己採点する」単語カード型に
変わった（decisions.md 第 4 部）。2026-09-11 のセッションで、当時未決だった進捗と
達成感の見せ方が決まった（decisions.md 第 5 部）。以下は変更後の体験。

## 利用場面

- オーナーが自分のローカル環境で単語学習の時間として開く。個人用の道具であり、
  対象を広げる想定は今のところない（`overview.md`「誰の何の困りごとか」）。
- 1 回の利用は、その日の期限カードを全部こなし、新規カードを上限 N 枚まで引いたら
  終わりとする（N は設定値、初期値は 10 枚程度を想定、値は未決）。Anki と同じ
  考え方で、終わりが毎日自動で決まる（decisions.md 第 5 部 2026-09-11「1 回の
  セッションは、期限カードを全部こなし、新規カードを上限 N 枚まで引いたら終わる」）。
- 使い始めるきっかけは、今日の期限カード数だけ。ストリークやポイントは持たない
  （同「毎日開くきっかけは、今日の期限カード数だけ。ストリークやポイントは
  持たない」）。

## 中核の体験

目的（IELTS など）・トピック・目標レベルで学習範囲を選ぶ。カードの表面には英語の
意味説明と、答えを `___` で伏せた穴埋め例文が出るので、頭の中で語を思い出す。
裏面をめくると語と、その語を使った例文が 2 本出るので、自分の記憶の度合いを
Again / Hard / Good / Easy の 4 段階で自己申告する。申告に応じて FSRS が次に
その語を出す間隔を決める。手がかりを段階的に弱めていく仕組みはなく、表面の
構成は毎回同じである。

中核のループ:

- 目的・トピック・目標レベルで出題範囲を選ぶ
- カードの表面（意味説明 + 穴埋め例文）を見て語を思い出す
- 裏面をめくって語と例文 2 本を確認する
- Again / Hard / Good / Easy で自己採点する
- FSRS が次回の出題間隔を決める
- セッション終了画面で今日の差分（復習枚数、覚えている語の増減）とカーブを見る
  （decisions.md 第 5 部 2026-09-11「伸びは、日次の推移カーブとセッション終了時の
  差分で見せる」）

進捗は「今覚えている語数」として見せる。定義は、一度以上復習したカードの想起確率 R
の合計（Anki の「推定総知識量」と同じ定義）で、未復習のカードは 0 として扱う。この
値と日次カーブは、選んでいる範囲（目的・トピック・目標レベル）に追従する。目標を
選んでいるときは、目標範囲の語群に対する「今覚えている語数 / 語群の総数」を割合で
見せ、スコアの推定はしない（decisions.md 第 5 部 2026-09-11「進捗の主指標は『今
覚えている語数』」「カーブと『今覚えている語数』は、選んでいる範囲に追従させる」
「目標スコアまでの距離は、目標範囲の語群に対する『覚えている割合』だけで見せる」）。

## 便利さの定義

- **Anki の Vocabulary デッキ（現在の代替手段）に対して、見た目と操作を自分好みに
  できる。目的・トピックで出題範囲を絞り込める。進捗と達成感を自分好みに見せられる。**
  この 3 つが自前アプリを作る理由のすべてであり、それ以外で Anki に勝る点は
  ないと考えてよい（decisions.md 第 4 部 2026-09-10「自前アプリで Anki に足すもの」）。
  進捗と達成感の具体は、「今覚えている語数」・日次カーブ・目標範囲の割合を、
  学習画面で選んでいる範囲（目的・トピック・目標レベル）に追従させて学習の流れの
  中に置く点にある。Anki も統計画面でデッキや検索で絞った「推定総知識量」を出せる
  が、別画面であり、このアプリの軸に揃った表示とセッション終了時の差分は持たない
  （decisions.md 第 5 部 2026-09-11）。
- 逆に、できなくてよいこと: 自由記述の産出練習と LLM による添削（旧構想からの
  差別化要素）。実行時に AI を組み込まないと決めた時点で、この体験は範囲外になった
  （同「アプリに AI を組み込まない」）。発音・リスニングも中核ではないため、最初の
  版のカードには持たせない（decisions.md 第 6 部 2026-09-11「残る小さい未決は、
  発音だけここで決め、残りはプロダクト側リポジトリに送る」）。

## 最初の版で成立させる体験

上記の中核のループ（範囲選択 → 想起 → めくる → 自己採点 → FSRS 間隔決定 →
セッション終了画面）と、進捗と達成感の見せ方は最初の版に含める
（decisions.md 第 5 部 2026-09-11）。含めるものと捨てるものは次の通り。

- **含める:** 今日の期限カード数（開くきっかけ）、選択範囲の今覚えている語数と
  未学習の残り、日次カーブ、セッション終了画面の差分、目標範囲の覚えている割合。
- **捨てる:** 定着区分（未学習 / 学習中 / 定着）、ストリーク・ポイント、スコア
  推定、節目の演出、トピック別グラフの一覧、忘れかけ語の一覧
  （decisions.md 第 5 部 2026-09-11「最初の版で作る範囲と捨てるもの」）。
- **手がかりを段階的に弱めていく仕組み。** 旧構想の決定だったが、カード形式への
  移行で無効になった。最初の版だけでなく、今のところ体験そのものから外れている。

## 実現性

- 難しいところ:
  - **カードの品質。** 表面（意味説明 + 穴埋め例文）から答えの語が一意に決まるか
    という問題は、旧構想の「場面に合う語が 1 つに定まるか」から形を変えて残っている。
    類義語（improve / enhance / boost など）が意味説明だけでは絞れない前提で
    穴埋め文を足した。一意性は、表面だけを見せて当てはまる語をすべて挙げさせる
    「ブラインド解答」で確かめる。答え以外にも妥当な候補が出たら FIX とし、
    観点レビュー（言い換えによる答えの漏れ、例文の質、焼き直し、例文どうしの重複、
    同義語の重複の 5 観点）と合わせた独立審査 2 本を、カードを書いた実行とは別に
    毎回回す（decisions.md 第 6 部 2026-09-11「一意性は、表面だけを見せる
    「ブラインド解答」で確かめる。点検 Skill は独立した審査 2 本で構成する」）。
    どこまでを「妥当な候補」と数えるかの線引きは、最初の 1 回の結果を見て調整する
    未決事項として残る（`open-questions.md`）。
  - **答えの漏れと不自然な例文。** `tomada-routine` の運用実績で、AI 生成 6 枚中 5 枚が
    裏面の例文に答えの語を一度も使っていなかった事例が確認されている
    （decisions.md 第 4 部 2026-09-10「Lint は語数・文字数に加え、判断の要らない形の
    チェックまで含める」）。機械的な Lint で弾けるのはこの種の形の誤りまでで、
    「例文として自然か」「答えが本当に一意か」は点検用 Skill の判断に委ねる設計に
    なっている。その点検 Skill の精度が体験の質を直接左右する。
  - **点検 Skill の設計。** 生成 Skill の入力は（目的, トピック, CEFR の範囲, 語数）
    とし、生成前に既存カードの（見出し語, 品詞）一覧を渡して重複を除外する。Lint
    でもキーの重複を ERROR にする。既存の語が新しいトピックにも合う場合は、新しい
    カードを作らず既存カードへのタグ追記として提案する。既存カードの id は
    （見出し語, 品詞）から決め、点検・再生成での修正は同じ id を上書きして FSRS の
    状態を引き継ぐ。答えの語そのものが変わる修正だけ新しいカードにし、古いカードは
    退役させる（decisions.md 第 6 部 2026-09-11「生成 Skill はトピック単位で回し、
    （見出し語, 品詞）で重複を排除する。既存の語が新しいトピックにも合うときは、
    タグの追記にする」「既存カードの修正は、（見出し語, 品詞）から決まる id を
    固定したまま上書きする。履歴は git に任せる」）。
  - **トピックの固定一覧の設計。** 目的とは別にトピック（病院、環境など）を固定
    タグとして持つと決めた。一覧は education / work / business-economy /
    science-technology / environment / health / media-advertising /
    travel-tourism / cities-housing / crime-law / government-society /
    family-relationships / culture-arts / food / sport-leisure の 15 個で確定し、
    最初の生成 Skill は environment / education / health を回す（decisions.md
    第 6 部 2026-09-11「トピックの固定一覧は次の 15 個で確定する」「生成 Skill の
    最初の 1 回は、environment / education / health を各 30 語前後、IELTS の
    B2〜C1 で回す」）。
  - 実行時に AI を呼ばないため、旧構想にあった LLM のコスト・応答時間の問題は
    もう実現性の論点ではない。
  - **進捗の計算は難所ではない。** 「今覚えている語数」（想起確率 R の合計）は
    ts-fsrs の `get_retrievability(card, date)` で任意の日付について計算でき、
    範囲への追従もカード単位の集計で済む（`_autodocs/01-scheduler-api.md`、
    Context7 経由で 2026-09-11 に確認）。難しいのは日次カーブの持ち方
    （スナップショットとして記録するか、履歴から再計算するか）程度
    （decisions.md 第 5 部 2026-09-11「伸びは、日次の推移カーブとセッション
    終了時の差分で見せる」、`open-questions.md`「日次カーブの値をスナップショット
    で持つか、履歴から再計算するか」）。
- 技術スタック候補:
  - **アプリ本体:** `nextjs-app-template`（Next.js 16 / TypeScript / pnpm）を元に、
    LLM 呼び出しの層を外して使う（decisions.md 第 4 部 2026-09-10「アプリは
    nextjs-app-template から切り出して作る」）。
  - **FSRS の実装:** `ts-fsrs` が TypeScript 向けの実装として自然な候補になる
    （`research/spaced-repetition-fsrs.md`）。ただし decisions.md が決めているのは
    「FSRS と同じ考え方で間隔を決める」ことまでで、ライブラリそのものの選定は
    まだ明示的な決定ではない。
  - **カードデータ:** JSON ファイルとして git 管理し、Lint をファイルに対して回す
    （decisions.md 第 4 部 2026-09-10「カードデータは JSON ファイルで git 管理し、
    復習履歴はローカルの SQLite に置く」）。
  - **復習履歴・FSRS の状態:** ローカルの SQLite に置く（同上）。

## 想定ユーザーの広がり

個人用の道具として作ると決めたため、この問いは今のところ持たない。一次情報は
オーナー自身の観察のみで、他の学習者に同じ痛みがあるかどうかは検証の対象にしない
（`overview.md`「誰の何の困りごとか」、`open-questions.md`「解決済み・消滅」）。
