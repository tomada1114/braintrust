# english-vocab-app 体験の構想

設計レベル（画面、配色、トークン）には入らない。ここで決めるのは「どんな体験を
成立させるか」と「それは現実的か」まで。

2026-09-10 のセッションで、体験の骨格が「場面と候補語群から選んで自分の文を書く」
から「意味説明と穴埋め例文を見て語を思い出し、めくって自己採点する」単語カード型に
変わった（decisions.md 第 4 部）。以下は変更後の体験。

## 利用場面

- オーナーが自分のローカル環境で単語学習の時間として開く。個人用の道具であり、
  対象を広げる想定は今のところない（`overview.md`「誰の何の困りごとか」）。
- 1 回の利用時間は未決。オーナーが「数日でやめる」離脱を繰り返してきたことを
  踏まえると、短く区切れることが要ると考えられるが、決定はされていない
  （`open-questions.md`「1 回の利用時間」）。
- 使い始めるきっかけと、やめるタイミング: 未決。

## 中核の体験

目的（IELTS など）・トピック・目標レベルで学習範囲を選ぶ。カードの表面には英語の
意味説明と、答えを `___` で伏せた穴埋め例文が出るので、頭の中で語を思い出す。
裏面をめくると語と、その語を使った例文が 2 本出るので、自分の記憶の度合いを
Again / Hard / Good / Easy の 4 段階で自己申告する。申告に応じて FSRS が次に
その語を出す間隔を決める。手がかりを段階的に弱めていく仕組みはなく、表面の
構成は毎回同じである。

中核のループ:

- 目的・トピック・目標レベルで出題範囲を選ぶ
- カードの表面（意味説明 + 穴埋め例文）を見て語を思い出す
- 裏面をめくって語と例文 2 本を確認する
- Again / Hard / Good / Easy で自己採点する
- FSRS が次回の出題間隔を決める

## 便利さの定義

- **Anki の Vocabulary デッキ（現在の代替手段）に対して、見た目と操作を自分好みに
  できる。目的・トピックで出題範囲を絞り込める。進捗と達成感を自分好みに見せられる。**
  この 3 つが自前アプリを作る理由のすべてであり、それ以外で Anki に勝る点は
  ないと考えてよい（decisions.md 第 4 部 2026-09-10「自前アプリで Anki に足すもの」）。
- 逆に、できなくてよいこと: 自由記述の産出練習と LLM による添削（旧構想からの
  差別化要素）。実行時に AI を組み込まないと決めた時点で、この体験は範囲外になった
  （同「アプリに AI を組み込まない」）。発音・リスニングも中核ではないと考えられるが、
  明確に決めたわけではない。

## 最初の版で成立させる体験

上記の中核のループ（範囲選択 → 想起 → めくる → 自己採点 → FSRS 間隔決定）そのものは、
最初の版に含める。含めないのは次の 2 つ。

- **進捗と達成感の見せ方。** 別セッションで決める（decisions.md 第 4 部 2026-09-10
  「進捗と達成感の見せ方は、別のセッションで決める」）。最初の版では、Anki に足す
  3 つの理由のうち 1 つが未実装のまま始まることになる。
- **手がかりを段階的に弱めていく仕組み。** 旧構想の決定だったが、カード形式への
  移行で無効になった。最初の版だけでなく、今のところ体験そのものから外れている。

## 実現性

- 難しいところ:
  - **カードの品質。** 表面（意味説明 + 穴埋め例文）から答えの語が一意に決まるか
    という問題は、旧構想の「場面に合う語が 1 つに定まるか」から形を変えて残っている。
    類義語（improve / enhance / boost など）が意味説明だけでは絞れない前提で
    穴埋め文を足したが、それで実際に一意に決まるかはカードごとに点検が要る
    （decisions.md 第 4 部 2026-09-10「カードの形」の影響ノート）。
  - **答えの漏れと不自然な例文。** `tomada-routine` の運用実績で、AI 生成 6 枚中 5 枚が
    裏面の例文に答えの語を一度も使っていなかった事例が確認されている
    （decisions.md 第 4 部 2026-09-10「Lint は語数・文字数に加え、判断の要らない形の
    チェックまで含める」）。機械的な Lint で弾けるのはこの種の形の誤りまでで、
    「例文として自然か」「答えが本当に一意か」は点検用 Skill の判断に委ねる設計に
    なっている。その点検 Skill の精度が体験の質を直接左右する。
  - **点検 Skill の設計。** 生成 Skill と点検 Skill をどの単位で回すか、既存カードとの
    重複をどう避けるか、再生成のたびに既存カードをどう扱うかは未決
    （`open-questions.md`「生成 Skill と点検 Skill の設計」）。
  - **トピックの固定一覧の設計。** 目的とは別にトピック（病院、環境など）を固定
    タグとして持つと決めたが、一覧そのものと最初の 2〜3 トピックの選定は未決
    （`open-questions.md`「トピックの固定一覧をどう作るか」）。
  - 実行時に AI を呼ばないため、旧構想にあった LLM のコスト・応答時間の問題は
    もう実現性の論点ではない。
- 技術スタック候補:
  - **アプリ本体:** `nextjs-app-template`（Next.js 16 / TypeScript / pnpm）を元に、
    LLM 呼び出しの層を外して使う（decisions.md 第 4 部 2026-09-10「アプリは
    nextjs-app-template から切り出して作る」）。
  - **FSRS の実装:** `ts-fsrs` が TypeScript 向けの実装として自然な候補になる
    （`research/spaced-repetition-fsrs.md`）。ただし decisions.md が決めているのは
    「FSRS と同じ考え方で間隔を決める」ことまでで、ライブラリそのものの選定は
    まだ明示的な決定ではない。
  - **カードデータ:** JSON ファイルとして git 管理し、Lint をファイルに対して回す
    （decisions.md 第 4 部 2026-09-10「カードデータは JSON ファイルで git 管理し、
    復習履歴はローカルの SQLite に置く」）。
  - **復習履歴・FSRS の状態:** ローカルの SQLite に置く（同上）。

## 想定ユーザーの広がり

個人用の道具として作ると決めたため、この問いは今のところ持たない。一次情報は
オーナー自身の観察のみで、他の学習者に同じ痛みがあるかどうかは検証の対象にしない
（`overview.md`「誰の何の困りごとか」、`open-questions.md`「解決済み・消滅」）。
