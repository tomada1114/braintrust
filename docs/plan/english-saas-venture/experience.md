# english-saas-venture 体験の構想

設計レベル（画面、配色、トークン）には入らない。ここで決めるのは「どんな体験を
成立させるか」と「それは現実的か」まで。

## 利用場面

- **デスクトップで、座って学習する時間に使う**（2026-09-14 オーナー決定。当初「すきま時間」と
  答えたあと、デスクトップ前提でよいと訂正された）。スマホ前提の設計にはしない。
- 1 回のセッションは **3〜5 分。出題数で終わる**。終わりが明確で、「無限に学習が終わらない」
  という現行ワークフローへの不満を再生産しない。
  - 注: 3〜5 分はすきま時間を想定していた段階の回答。デスクトップ・着席前提に変わったため
    見直す余地があるが、オーナーの決定としてはこのまま扱う（open-questions.md）。
- 使い始めるきっかけは学習時間の確保そのもの。やめるタイミングはその回の出題を終えたとき。

## 中核の体験

ユーザーは状況を渡され、対象言語で書いて答える。自分が過去に詰まった・間違えた「型」が、
**同じ文ではなく、語彙も場面も違う別の問題**として戻ってくる。判定は正誤の○×ではなく、
**その問題をどの足場レベルから出せたか**（例: 語を与える → ヒント → 型の名前だけ →
足場なし）。どんな言い方であれ足場なしで出せればクリアで、○× は構造的に発生しない。
前より少ない足場でクリアできると、それが**成長**として記録される。フィードバックは
読んで終わりではなく、次に出る問題（＝次に外す足場）に反映される。

中核のループ:

- 状況が提示される（足場つき。型・ヒント・組み立ての手がかりがある）
- 対象言語で書いて答える
- どの足場レベルから出せたかを記録する。足場なしで出せればクリア（別解も足場なしなら正解）
- 詰まった点が「型」として蓄積される
- 後日、**同じ型の別問題**として戻ってくる
- 必要な足場が前より減っていれば、それが成長として記録される（前は詰まった課題を、別の問題で越えた）

**型とは**: 型（SRS で管理する単位）の器は、**「言いたい機能」ベースの閉じたカタログ**
（数十個規模、手で作る）に置く。LLM はラベルを新規生成せず、このカタログから選ぶ。
単語・コロケーション・句動詞・談話フレーズ（例: "How do I put this?"）は、すべてこの
カタログの下に収まる。**この決定は、当初の「対象はコロケーション・句動詞に限定する」を
置き換えたもの**（2026-09-14、系統 A 再開セッション）。

## 便利さの定義

- **既存の代替手段（Native Camp 受講 → AI に分析させる → Anki に入れる）と比べて楽になること:**
  - 逐語カードではないので、「同じセリフを言う場面が来ない」という無意味さが消える
  - 覚えたかどうかではなく、**別の問題で使えたか**が分かる。オーナーが唯一成長を実感できた
    形（IELTS で同レベルの別問題が解けた）と同じ構造
  - 材料作り・準備が要らない。誤りはアプリ内の出題から自動で溜まる
  - フィードバックを読んで覚える受動的な作業が消える。指摘は次の出題に反映される
- **できなくてよいこと（オーナーが明示）:**
  - **実戦（アプリの外）とつなげること。** 実際の会話で使えたかの報告も、手触りの記録も要らない
  - 進捗の受動的な可視化（バー・ストリーク・グラフ）
  - アプリの統合。狭くてよい（他のアプリとの行き来は「そこまで嫌じゃない」）
  - 音声での産出（最初の版では）

**設計上の重要な区別（2026-09-14 のヒアリングから）**: オーナーは「進捗の可視化は要らない」と
答える一方で「スコアを伸ばす、課題をクリアするクエスト感が好き」と答えた。矛盾ではなく、
**受動的に眺める可視化が嫌で、能動的に潰していく達成が好き**という区別だと読める
（Claude の読み、オーナー未確認）。

## 最初の版で成立させる体験

**含めるもの**
- 状況提示型の出題と、テキストでの産出（書く）
- 足場（型・ヒント）つきの出題。完全自由回答にはしない
- ○×ではない比較による返し
- 誤りから「型」を取り出して蓄積する
- 同じ型の別問題として再出する
- 型ごとの達成（前に詰まった課題をクリアした、という記録）
- 対象言語は**英語のみ**。ただし**仕組みは言語に依存させない**
- 誤りの供給源は 2 つ: **アプリ内の出題で出た誤り**と、**自分が書いた英文を放り込む**

**捨てるもの**
- **音声入力（ASR）。** 最初の版だけでなく、**基本的に永続的に持たない方針**
  （2026-09-14。将来的に持たせる可能性は完全には閉じないが、既定は「持たない」）。
  ASR を挟むと「発音のせいで認識されず、分かっているのに入力だけミスる」という
  体験そのものの破壊が起きるためで、実装コストとは別種の理由。
  あわせて**痛みの定義をモダリティ非依存に修正した**（言いたいことがすぐ出てこない／
  それが合っているか分からない、はテキストでも発話でも同じストレス）ため、
  テキスト産出は妥協ではなく**狙いと一致する選択**になった。
  `research/writing-to-speaking-transfer.md` が確認した DeKeyser & Suzuki (2025) の整理では、
  モダリティを超えて共有されるのは宣言的知識（言いたいことの想起）で、モダリティに
  特異的なのは手続き的な自動化だけとされる。今回定義した痛みは前者に当たる。
  **残る割り切り**: 手続き的自動化（とっさに口が動く、話しながら骨組みが崩れない）は、
  この製品では永続的に扱わない
- **実戦での使用報告、使いどころのトリガー通知。** 「アプリの外につなげる必要はない」という
  オーナーの決定による。ただしヒアリングで挙がった痛み「場面が来てもチャンスだと気づけない」は
  **最初の版では手つかずのまま残る**
- 英語以外の対象言語。オーナーが品質を判定できないため
- レッスン後のメモや AI 分析結果の貼り付け（外部連携）。「材料作りがめんどうくさい」という
  不満を再発させるため
- 初回の診断テスト。サインアップ前の壁を増やさないため

## 実現性

### 難しいところ

**技術的**
- **型の同定が最大の難所。** ただし粒度の決め方には方針がある。**粗く始め、成績が割れた型だけ
  後から割る**（`research/error-taxonomy-and-mastery-criteria.md`、Liu & Koedinger 2017）。
  同研究では、選択的に割った 58 KC が、統合した 56 KC・機械的に細かく割った 66 KC の
  両方に、BIC・交差検証のいずれでも勝った。細かさ自体は価値ではなく、実在する難易度差に
  沿ってのみ割るべきという知見で、最初から粒度を当てにいく必要はない
- **転移の判定。** ○×にしないと決めた以上「クリアした」をどう認定するかが曖昧になりやすい
  という問題は、**成長の軸を足場レベルに置く決定でおおむね解消した**（2026-09-14）。
  どんな言い方であれ足場なしで出せればクリアなので、別解を弾く問題が構造的に起きない。
  **未解決なのは具体的なしきい値**（どの段階までクリアと呼ぶか）。自由産出の習熟判定について
  公表された数値基準は存在せず、唯一公表されているのは Cognitive Tutor の BKT 95%
  （`research/error-taxonomy-and-mastery-criteria.md`）
- LLM 出力の一貫性。「毎回同じようなフィードバックで、はいはいまたこれね」という
  現行ワークフローへの不満を、同じ仕組みで再生産する危険が高い

**コンテンツ**
- 型の分類体系をどう持つか。完全に LLM 任せにすると粒度が揺れ、固定の体系を持つと
  多言語化のときに作り直しになる
- 初回に出す汎用のお題は人手で用意する必要がある（誤りがまだ無いため）

**運用**
- **LLM の呼び出しコスト（概算、2026-09-14）。** 前提: 1 セッション 5 問、1 問あたり
  出題生成＋評価の 2 呼び出し、入力 4,500 / 出力 800 トークン、月 25 セッション。
  この前提では Sonnet 5 級で月 $2 前後、Haiku 4.5 級で月 $1 前後、Opus 5 級で月 $5 前後
  （単価は `docs/landscape/2026-09-llm-apis.md`）。Clozemaster の $12.99/月 という基準なら
  どの階層でも余裕があるが、$79.99/年（実効 $6.67/月）では上位モデルが破綻する。
  含意は 3 つ。(1) 「3〜5 分・出題数で終わる」という体験上の決定が、そのままコストの
  上限装置になっている。(2) 出題生成はリアルタイム性が要らないため事前生成＋Batch
  （50% 割引）が効き、リアルタイムが要るのは評価だけ。(3) Gemini の無料枠は規約上
  "human reviewers may read, annotate, and process your API input and output"
  （https://ai.google.dev/gemini-api/terms, 発効 2026-03-23）とされており、ユーザーが
  書いた英文を投げる以上は使えない。有料枠が前提になる。
  **結論: コストは成立性のボトルネックではない。** モデル階層の割り当て・出題の
  事前生成の仕組み・ベンダー選定は `assessing-ai-architecture` の担当
- 品質の目視確認。英語のみなら本人が判定できるが、多言語に広げた時点でできなくなる
- **獲得経路が未解決のまま。** これは体験の問題ではないが、事業としての最大の穴として残る
  （`research/` 11 本、`open-questions.md`）

### 技術スタック候補

選ぶ軸: オーナーの習熟度 / 配布形態（デスクトップのウェブ、セルフサーブ課金） / コスト /
AI 側との相性。AI の構成とベンダーは `assessing-ai-architecture` で扱う。

- **候補 A: TypeScript + Next.js、マネージド Postgres、Stripe**
  - 利点: 既存アイデア（`english-vocab-app` は Next.js を想定）と地続きで習熟度が高い。
    ウェブでの配布とセルフサーブ課金が最短。LLM の SDK も揃っている
  - 欠点: サーバー側で LLM を呼ぶ設計になるため、コストがそのまま運営者負担になる
- **候補 B: Rails / Django + Postgres**
  - 利点: 課金・認証まわりの枠組みが厚い
  - 欠点: オーナーの既存アイデア群と言語がずれ、学習コストが乗る
- **候補 C: 静的 SPA + サーバーレス関数**
  - 利点: 初期コストが最小
  - 欠点: 蓄積（型・誤り・達成）が中核なのでデータベースは必須で、結局 A に寄る

**推奨は候補 A。** 理由は、この体験の核が「蓄積」と「サーバー側での LLM 呼び出し」であり、
その両方を最短で扱えること、そしてオーナーの習熟度が最も高い構成であること。
**ただしこれは推奨であって決定ではない。**

## 想定ユーザーの広がり

他人にも当てはまるかは別の問いとして `open-questions.md` に残る。現時点で分かっているのは、

その痛みに金を払うかは層によって分かれること（熱心な語学学習者層は複数の有料アプリに払う。
一方で無料手段しか挙がらない層もある）。
