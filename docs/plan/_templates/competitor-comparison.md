## ユーザーに嬉しい仕組みのパターン

複数の製品に共通して現れる形。機能名ではなく、**ユーザーの何を肩代わりしているか**を書く。

- パターン: <どういう作りか>
  - 仕組み: <なぜ嬉しいのか。ユーザーの何が省かれるか>
  - 見られた製品: <製品名>
  - 根拠: `<product-slug>.md` の該当節 / ユーザーの声 / 一次観察

## どの製品も解決していない課題

ユーザーの声か一次観察を根拠にする。機能一覧の欠落だけを根拠にしない。

- 課題: <何が解決されていないか>
  - 未解決のまま残している製品: <製品名>（調べた全製品なら「全製品」）
  - 根拠: <引用または観察> / URL: <URL> / 出典日付: YYYY-MM-DD

## このアイデアの立ち位置の選択肢

- 案 A: <どこに立つか> — トレードオフ: <得るもの / 失うもの>
- 案 B: <どこに立つか> — トレードオフ: <得るもの / 失うもの>
- 推奨: 案 <X> — <理由>

推奨であって決定ではない。オーナーが決めたと言ったときに `decisions.md` へ書く。

## グレーゾーン

調べきれなかった製品、片方の言語でしか声が拾えなかった点、出典どうしの食い違い、
一次観察を途中で止めた製品とその地点。

## 影響する論点

この結果が効く `open-questions.md` の論点。
`overview.md` の「既存プロダクトとの違い」と `experience.md` の「便利さの定義」の
どこに反映しうるかも、ここに 1 行ずつ書く（書き換えるのはオーナーが決めてから）。
