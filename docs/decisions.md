# リポジトリ運用の決定

このリポジトリ自体をどう運用するかの記録。個々のアイデアの決定は
`docs/plan/<idea-slug>/decisions.md` に書く。追記のみ。

## 2026-09-06 このリポジトリでは実装しない

- 決定: 動くコードもプロトタイプも置かない。構造を説明する擬似コードや図は可。
- 理由: 手を動かし始めると「何を作るか」の検討が実装の都合に引きずられる。考える場と作る場を物理的に分ける。
- 却下した案: 小さなプロトタイプは許可する — 「小さい」の線が引けず、なし崩しに実装リポジトリ化する。

## 2026-09-06 推奨は必ず出す。決定はオーナーが持つ

- 決定: 選択肢とトレードオフを並べたら、必ず推奨を 1 つだけ理由つきで添える。ただし推奨は決定ではなく、オーナーが明示的に決めたと言うまで決定として扱わない。
- 理由: 判断材料を出さずに選択肢だけ並べるのは壁打ちにならない。一方で推奨を決定に読み替えると、決定権が事実上 Claude に移る。
- 却下した案: 推奨は出さず選択肢だけ提示する — 中立を装うだけで、考える負荷を全部オーナーに戻すことになる。
- 却下した案: 聞かれたときだけ推奨する — 聞くかどうかの判断自体がコストで、結局出し惜しみになる。

## 2026-09-06 グローバル skill の使用を制限しない

- 決定: refining-requirements や designing-wireframes などのグローバル skill は禁止しない。使うかは判断に任せる。ただし生成物は必ず該当アイデアの `docs/plan/<idea-slug>/` 配下に置く。
- 理由: 検討の途中で要件整理や画面イメージが役に立つ場面はある。困るのは置き場所が散らかることだけなので、そこだけ縛る。
- 却下した案: このリポジトリでは禁止する — 有用な道具を理由なく落とすことになる。
- 却下した案: 卒業直前の出口でのみ許可する — 検討の途中こそ使いたい場面があり、線引きの意味がない。

## 2026-09-06 アイデアは並行して溜め、ファイル構成を固定する

- 決定: `docs/plan/<idea-slug>/` に overview.md / decisions.md / open-questions.md / research/ / handoff.md を置く。構成はアイデアによらず同じ。
- 理由: どこに何が書いてあるかが常に同じなら、セッション開始時に読む場所を迷わない。アイデアは同時に複数走る前提。
- 却下した案: アイデアごとに ADR 形式の連番ファイルを積む — ファイルが増えるばかりで、現在の全体像を読む場所がなくなる。
- 却下した案: 1 アイデア 1 ファイル — 決定・未決・調査が混ざり、追記のたびに読み直す量が増える。

## 2026-09-06 決定エントリには却下した案とその理由を書く

- 決定: decisions.md の各エントリは 決定 / 理由 / 却下した案とその理由 を含める。
- 理由: 却下理由が残っていないと、数週間後に同じ案を蒸し返して同じ議論をやり直す。
- 却下した案: 決定と理由だけ — 「なぜ他ではないか」が失われ、記録の一番使う部分が欠ける。
- 却下した案: 決定のみ — 後から読んで判断を再現できない。

## 2026-09-06 根本の問いは根拠があるときだけ出す

- 決定: 「そもそも作るべきか」「LLM が必要か」は、根拠があるとき（既存プロダクトが既に解決している、語られた痛みが LLM を必要としない、など）に出す。
- 理由: 毎回出すと儀式になって読み飛ばされ、本当に効くときに効かなくなる。
- 却下した案: アイデアごとに 1 回必ず問う — 形式化してノイズになる。
- 却下した案: 聞かれたときだけ問う — 一番聞きたくないときに出てこない、という最悪の挙動になる。

## 2026-09-06 卒業時に handoff.md を書く

- 決定: 実装へ進むと決まったアイデアは `handoff.md` を書く。決定・残った論点・制約・調査へのポインタをまとめる。
- 理由: プロダクト側リポジトリの最初のセッションがここでの検討を再現できないと、同じ議論をゼロからやり直すことになる。
- 却下した案: 状態を「実装へ」に変えてリンクを張るだけ — 読む側が複数ファイルを読み解く必要があり、結局引き継がれない。

## 2026-09-06 事実確認は先に進める。比較調査は同意を取ってから

- 決定: 事実確認（対応可否、規約、価格）は確認なしで実施する。競合調査や技術比較は、目的と範囲を提案してオーナーが同意してから始める。
- 理由: 事実確認は速く、誤った前提のまま議論が進むほうが損。比較調査は時間とトークンを使い、範囲の合意なしに始めると的外れになる。
- 却下した案: すべて確認なしで実施する — 大きな調査が勝手に走り、費用と方向性を制御できない。
- 却下した案: すべて聞いてから実施する — 5 秒で済む裏取りのたびに往復が発生し、議論が止まる。

## 2026-09-06 対象はベンダー中立

- 決定: 対象は AI を組み込んだアプリケーション全般とし、ベンダーや SDK（Claude / Gemini / OpenAI / ローカル LLM など）は選定対象として扱う。
- 理由: 「何を作るか」を考える段階で実装手段を先に固定すると、比較すべき選択肢が検討に入らない。
- 却下した案: Claude Agent SDK 専用 — 検討の入口で手段を固定してしまい、選定という論点自体が消える。
- 却下した案: Claude を主軸に、他はオプション扱い — 中立に見えて結論が最初から傾く。

## 2026-09-06 リポジトリ内に skill を 4 つ置く

- 決定: `.claude/skills/` に intaking-ideas / recording-research / assessing-ai-architecture / handing-off-plans を置く。名前は英語の動名詞。
- 理由: このリポジトリ固有の進め方なので、リポジトリと一緒に版を管理したい。名前を先に決めておけば CLAUDE.md から参照でき、後から作る側の輪郭も定まる。
- 却下した案: グローバルの `~/.claude/skills` に置く — 他のリポジトリでも読み込まれてしまい、ここ限定の運用が漏れる。
- 却下した案: 名前は作るときに決める — CLAUDE.md から参照できず、4 つの分担も曖昧なままになる。

## 2026-09-06 前提知識は docs/landscape/ に日付つきで置く

- 決定: LLM / エージェント基盤の事前調査は `docs/landscape/YYYY-MM-<topic>.md` に置く。skill は参照するだけとし、最新ファイルが 3 ヶ月より古ければ更新を提案する。
- 理由: この領域の情報は数ヶ月で陳腐化する。日付をファイル名に出しておけば、古さが読む前に分かる。
- 却下した案: skill の references/ に置く — skill の更新と知識の更新が同じ操作になり、古い知識が「skill の一部」として温存される。

## 2026-09-06 リポジトリ自身の記録は docs/ 直下に置く

- 決定: このリポジトリの運用の決定と未決は `docs/decisions.md` / `docs/open-questions.md` に置く。書式はアイデア用と同じ。
- 理由: オーナーから判断を委ねられた項目。運用の記録をアイデアの索引の中に混ぜると、アイデア一覧の意味が濁る。docs 直下なら並びが素直で、書式を共通化できる。
- 却下した案: `docs/plan/braintrust/` として自分自身を 1 アイデア扱いする — アイデア索引に実在しないプロダクトが並び、状態欄が意味を持たない。
- 却下した案: CLAUDE.md に書く — 決定の経緯と却下理由まで書くと指示文書として長くなりすぎ、読ませたい原則が埋もれる。

## 2026-09-06 体験の構想と実現性も守備範囲に含める

- 決定: AI 周りだけでなく、アプリとしての体験（利用場面、中核の体験、便利さの定義、最初の版の体験範囲）と、実現性・技術スタック候補の検討も扱う。相談相手は PdM 兼 CTO のつもりで振る舞う。深さは構想レベルまでで、画面設計・配色・トークンといった設計レベルは既存のグローバル skill に任せ、成果物はアイデアのディレクトリ配下に置く。実装物は置かない。体験の検討は持ち込みの直後、AI 構成の前に行う。専用 skill として shaping-experience を足す。
- 理由: AI の構成だけ決まっても、使い勝手とユーザーニーズが弱ければ作る意味がない。体験が決まらないと必要なモデル呼び出しも決まらない。想定ユーザーはまず自分で、後で他人に広げることもあるので、自分の観察を一次情報として扱い「他人にも当てはまるか」は別の問いとして残す。
- 却下した案: 設計レベル（tokens.css を含む）までここで行う — 「実装しない」原則を緩める必要がある。
- 却下した案: 構想レベルのみで実現性は扱わない — 技術スタック候補を事前に相談したいという要望に合わない。
- 却下した案: 順番を固定しない — 体験より先に AI 構成の話になると、手段が目的に先行する。

## 2026-09-06 5 つの skill の中身を確定する

- 決定: `.claude/skills/` の 5 スキル（intaking-ideas / shaping-experience / recording-research / assessing-ai-architecture / handing-off-plans）の手順・出力・判断基準を確定し、実ファイルとして置いた。判断基準のうち量のあるもの（LLM 要否と構成の判定、ベンダー比較軸）は `assessing-ai-architecture/references/tiers.md`、サブエージェントのブリーフは `recording-research/references/agents/fact-check.md` に置く。体験の構想と AI 構成の境界は、shaping-experience は技術スタック候補まで、モデル呼び出しとベンダーは assessing-ai-architecture、とした。
- 理由: CLAUDE.md の skills 節は適用場面しか書いておらず、実際の進め方がセッションごとに揺れていた。手順を skill 側に固定し、CLAUDE.md は原則だけを持つ形に分担する。
- 却下した案: CLAUDE.md に 5 つの手順を全部書く — 指示文書が長くなり、読ませたい原則が埋もれる。
- 却下した案: skill にテンプレート全文を複製する — 書式の正本が `docs/plan/_templates/` と 2 箇所になり、必ず食い違う。
- 却下した案: 体験と AI 構成を 1 つの skill にまとめる — 同じ決定を 2 つの経緯で書くことになり、decisions.md からどちらの議論の結果か追えなくなる。

## 2026-09-07 ユーザーニーズ調査と競合調査の skill を足す

- 決定: `.claude/skills/` に discovering-user-needs / surveying-competitors を足し、7 スキルにする。ユーザーニーズ調査は公開の声（アプリストアのレビュー、フォーラム、SNS、Q&A、ブログ）のデスクリサーチに限る。競合調査は Web 調査に加え、オーナーが同意した上位 1〜3 本を Claude in Chrome で実際に触る。どちらも比較調査として扱い、目的・範囲・エージェント数を提案してオーナーの同意を得てから走らせる。調査の並列実行は Claude Code の Dynamic Workflow（Workflow tool）で行い、この 2 スキルは Claude Code 専用とする。成果物は `research/user-needs/` と `research/competitors/` のサブディレクトリに置き、書式は `_templates/user-needs.md` / `competitor.md` / `competitor-comparison.md` に従う。
- 理由: 想定ユーザーは自分から始まるが、他人向けにも広げる可能性があり、また他人の声から自分の隠れたニーズが見つかることがある。既存プロダクトについては機能一覧ではなく「どんな UI/UX がなぜ嬉しいか」と「何が未解決か」を知りたい。広く集める作業はメインセッションでやらず並列のサブエージェントに流したほうが速く安い。
- 却下した案: インタビュー・アンケートの設計まで含める — 一次情報は得られるがオーナーの実施工数が大きく、まずデスクリサーチで足りるかを見る。
- 却下した案: LLM のペルソナで模擬ユーザーを立てる — 想像の痛みを実在の痛みと取り違える危険が大きい。
- 却下した案: 競合は Web 調査のみ — UI/UX の観察が二次情報になり、「なぜ嬉しいか」が分からない。
- 却下した案: 候補すべてを実際に触る — 時間・アカウント作成・課金の負担が大きい。
- 却下した案: 成果物を `research/` 直下に接頭辞で置く — 競合が 5〜8 ファイルになると直下が散らかる。
- 却下した案: Codex でも動くよう逐次フォールバックを書く — 並列前提の手順を逐次に書き直す分 skill が長くなる。Codex で必要になった時点で `dual-platform-skills` で橋渡しする。
